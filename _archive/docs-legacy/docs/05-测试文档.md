## 一、测试原则

### 五条原则

**原则 1：单元测试与集成测试绝不打真实接口**

原因是日配额。一个 `for` 循环的测试就能把团队一天的配额刷光。

| 测试类型 | 是否允许真实请求 |
| --- | :---: |
| 单元测试 | ❌ 绝对禁止 |
| 组件测试 | ❌ 绝对禁止 |
| 集成测试 | ❌ 绝对禁止（用 MSW 拦截） |
| 接口联调 | ✅ 允许，但**手动逐个执行** |
| E2E 测试 | ⚠️ 只在测试环境，且需人工触发 |

**原则 2：签名逻辑必须有黄金用例守护**

签名是本项目的命脉。它有官方给的标准输入输出（见 04 文档），
必须写成断言固定下来。任何人改动签名代码，这个测试会立刻报警。

**原则 3：越往下层，测试覆盖率要求越高**

| 层 | 覆盖率要求 | 理由 |
| --- | :---: | --- |
| 工具层 | ≥ 90% | 纯函数，最容易测，出错影响面最大 |
| 基础设施层 | ≥ 85% | 所有请求都经过它 |
| 服务层 | ≥ 70% | 主要是参数拼装，逻辑简单 |
| 状态层 | ≥ 70% | 缓存逻辑需要测 |
| 业务组合层 | ≥ 70% | 流程编排，重点测异常分支 |
| 视图层 | ≥ 40% | 只测关键交互，不追求高覆盖 |

**原则 4：测试要测行为，不测实现**

```typescript
// ❌ 不好：测的是内部实现细节，重构就会挂
it('调用了 sortObjectByKey 方法', () => {
  const spy = vi.spyOn(objectUtils, 'sortObjectByKey')
  buildSignature(params, key)
  expect(spy).toHaveBeenCalled()
})

// ✅ 好：测的是外部可观察的行为
it('参数顺序改变不影响签名结果', () => {
  expect(buildSignature(paramsA, key)).toBe(buildSignature(shuffledA, key))
})
```

**原则 5：每个 Bug 修复都要配一个回归测试**

修 Bug 时先写一个能复现 Bug 的失败测试，再改代码让它通过。
这样同一个 Bug 不会出现第二次。

## 二、测试分层与工具

### 工具选型

| 用途 | 工具 | 版本 | 说明 |
| --- | --- | --- | --- |
| 测试运行器 | Vitest | ^2.1 | 与 Vite 同源，共用配置，零成本接入 |
| 组件测试 | @vue/test-utils | ^2.4 | Vue 官方组件测试库 |
| DOM 环境 | happy-dom | ^15 | 比 jsdom 快，够用 |
| 接口 Mock | MSW | ^2.6 | 在网络层拦截，不侵入业务代码 |
| 覆盖率 | @vitest/coverage-v8 | ^2.1 | Vitest 内置方案 |
| E2E | Playwright | ^1.48 | 按需引入，第四阶段再上 |

### 各层测试方式对照

```
┌────────────────────────────────────────────────────────────────┐
│ 视图层  views/ components/                                      │
│   测什么：关键交互是否触发正确调用、条件渲染、表单校验提示          │
│   怎么测：@vue/test-utils 挂载组件 + mock composable             │
│   不测：CSS 样式、Element Plus 内部行为                          │
├────────────────────────────────────────────────────────────────┤
│ 业务组合层  composables/                                        │
│   测什么：loading 状态流转、异常分支、轮询次数上限、finally 复位   │
│   怎么测：直接调用 useXxx()，mock 服务层                          │
│   重点：**异常路径比正常路径更重要**                              │
├────────────────────────────────────────────────────────────────┤
│ 状态层  stores/                                                 │
│   测什么：缓存命中/过期/强制刷新、并发请求去重                     │
│   怎么测：createPinia() + mock 服务层                            │
├────────────────────────────────────────────────────────────────┤
│ 服务层  services/                                               │
│   测什么：请求方法/路径/参数是否正确、FormData 字段是否完整         │
│   怎么测：MSW 拦截请求，断言收到的 request                        │
├────────────────────────────────────────────────────────────────┤
│ 基础设施层  infra/                                              │
│   测什么：签名注入、错误归一化、blob 分支、脱敏日志                │
│   怎么测：构造 axios 实例 + MSW，断言最终发出的请求                │
│   重点：**这一层的测试最有价值**                                 │
├────────────────────────────────────────────────────────────────┤
│ 工具层  utils/ constants/                                       │
│   测什么：纯函数输入输出、边界值、异常抛出                         │
│   怎么测：直接调用函数断言返回值                                  │
│   重点：**签名黄金用例在这一层**                                 │
└────────────────────────────────────────────────────────────────┘
```

```typescript
import { beforeAll, afterAll, afterEach, vi } from 'vitest'
import { server } from './msw/server'

// ===== MSW 生命周期 =====
beforeAll(() => {
  // onUnhandledRequest: 'error' 很重要：
  // 任何没被 mock 的请求会直接让测试失败，
  // 这就杜绝了「测试意外打了真实接口」的可能，保护日配额。
  server.listen({ onUnhandledRequest: 'error' })
})

afterEach(() => {
  server.resetHandlers()
  vi.clearAllMocks()
})

afterAll(() => {
  server.close()
})

// ===== 全局环境变量 Mock =====
// 用假凭证，避免测试依赖真实 .env.local
vi.stubEnv('VITE_ENABLE_LOCAL_SIGN', 'true')
vi.stubEnv('VITE_DEV_ACCESS_TOKEN', 'Db6j0Yq0eppBb')
vi.stubEnv('VITE_DEV_SECRET_KEY', 'a735eb11da74123074675fa3522a90d1')
```

> ⚠️ `onUnhandledRequest: 'error'` 是本项目的**关键配置**。
> 它保证了任何未被 mock 的网络请求都会让测试立刻失败，
> 而不是悄悄发到真实服务器消耗配额。**不要改成 `'warn'` 或 `'bypass'`。**

### 测试结构：三段式

每个测试用例都按 **准备 → 执行 → 断言**（Arrange-Act-Assert）三段写：

```typescript
it('缓存有效期内重复调用不会重新请求', async () => {
  // 准备（Arrange）
  const store = useChannelStore()
  const spy = vi.spyOn(channelService, 'getAgentChannels')
    .mockResolvedValue([{ channel_id: '1', channel_name: '渠道A' }])

  // 执行（Act）
  await store.fetchChannels()
  await store.fetchChannels()

  // 断言（Assert）
  expect(spy).toHaveBeenCalledTimes(1)
})
```

## 五、Mock 方案

### 为什么用 MSW

MSW（Mock Service Worker）在**网络层**拦截请求，业务代码完全不知道自己被 mock 了。

对比其他方案：

| 方案 | 问题 |
| --- | --- |
| `vi.mock('axios')` | 侵入实现，测不到拦截器（而拦截器是本项目最该测的） |
| 手写 mock 服务层 | 测不到签名注入和错误归一化 |
| **MSW** | ✅ 真实走完拦截器全流程，只是最后一跳被拦截 |

MSW 让我们能断言「最终发出去的请求里签名对不对」，这正是本项目的核心风险点。

### MSW Server 配置

```typescript
// src/test/msw/server.ts
```

### 基础设施层测试（最有价值的测试）

```typescript
// src/infra/http/__tests__/interceptor-sign.spec.ts
import { describe, it, expect, beforeEach } from 'vitest'
import { http as mswHttp, HttpResponse } from 'msw'
import { setActivePinia, createPinia } from 'pinia'
import { server } from '@/test/msw/server'
import { http } from '@/infra/http'
import { buildSignature } from '@/utils/signature'

const SECRET_KEY = 'a735eb11da74123074675fa3522a90d1'

describe('签名拦截器', () => {
  beforeEach(() => {
    setActivePinia(createPinia())
  })

  it('Body JSON 请求自动注入 access_token / timestamp / signature', async () => {
    let captured: Record<string, unknown> = {}
    server.use(
      mswHttp.post('*/alliance/api/popularize_plan', async ({ request }) => {
        captured = (await request.json()) as Record<string, unknown>
        return HttpResponse.json({ success: true, msg: '', data: {} })
      }),
    )

    await http.post('/alliance/api/popularize_plan', { task_id: 'T1', keyword: '词' })

    expect(captured.access_token).toBe('Db6j0Yq0eppBb')
    expect(captured.timestamp).toEqual(expect.any(Number))
    expect(String(captured.timestamp)).toHaveLength(10)   // 秒级
    expect(captured.signature).toMatch(/^[0-9a-f]{64}$/)   // 64 位小写十六进制
  })

  it('注入的签名可被独立重算验证', async () => {
    let captured: Record<string, unknown> = {}
    server.use(
      mswHttp.post('*/alliance/api/popularize_plan', async ({ request }) => {
        captured = (await request.json()) as Record<string, unknown>
        return HttpResponse.json({ success: true, msg: '', data: {} })
      }),
    )

    await http.post('/alliance/api/popularize_plan', { task_id: 'T1', keyword: '词' })

    // 用捕获到的参数重新算一遍，应与请求携带的签名一致
    const { signature, ...rest } = captured
    expect(buildSignature(rest, SECRET_KEY)).toBe(signature)
  })

  it('GET 请求把鉴权参数注入到 query 而非 body', async () => {
    let capturedUrl = ''
    server.use(
      mswHttp.get('*/alliance/api/popularize_tasks', ({ request }) => {
        capturedUrl = request.url
        return HttpResponse.json({ success: true, msg: '', data: [] })
      }),
    )

    await http.get('/alliance/api/popularize_tasks', { params: { channel_id: 'C1' } })

    const url = new URL(capturedUrl)
    expect(url.searchParams.get('access_token')).toBe('Db6j0Yq0eppBb')
    expect(url.searchParams.get('signature')).toMatch(/^[0-9a-f]{64}$/)
  })

  it('offset 与 limit 不参与签名计算', async () => {
    const signatures: string[] = []
    server.use(
      mswHttp.get('*/alliance/api/popularize_tasks', ({ request }) => {
        signatures.push(new URL(request.url).searchParams.get('signature') ?? '')
```

## 七、接口联调用例

联调是**手动执行**的，用于验证真实接口行为。

### 🔴 联调铁律

1. **一次只调一个接口**，不要写脚本批量跑
2. **用测试账号凭证**，不要用生产凭证
3. **每次调用都记录**结果到下面的用例表
4. **失败先查文档**（03 / 04 文档的排错章节），不要立刻重试
5. 每天联调前先确认**日配额剩余**

### 联调优先级

按接口依赖顺序（见 03 文档附录 A）联调：

```
第一批（无依赖，先验证签名是否通）
  § 5.1 查询代理商渠道信息      ← 最先调这个，只要它通了说明凭证和签名对了
  § 7.1 查询推广任务列表
  § 9.1 查询榜单列表

第二批（依赖第一批的返回值）
  § 5.2 查询二代信息            需要 channel_id
  § 8.1 投放实时数据
  § 4.4 查询推广作品列表

第三批（写操作，谨慎）
  § 3.1 单个创建推广计划        会产生真实数据
  § 4.1 单个创建推广作品 v2

第四批（批量与异步）
  § 3.2 批量创建推广计划
  § 6.1 查询批量任务结果

第五批（举报类，不可撤销，最后做）
  § 15.1 文件上传
  § 11.2 评论截流词举报
  § 14.1 提交风险词
```

## 八、E2E 场景测试

第四阶段引入 Playwright，覆盖三条主流程。

### 场景 1：从零配置到创建第一个推广计划

```
1. 打开首页 → 跳转到「凭证配置」页（因为未配置）
2. 填入 access_token → 保存
3. 进入「渠道查询」页 → 看到渠道列表
4. 进入「推广任务」页 → 看到任务列表，复制一个 task_id
5. 进入「创建推广计划」页
6. 填入 task_id、选渠道、填 URL 和关键词
7. 提交 → 看到「创建成功」和 plan_id
```

**断言点**：未配置凭证时被拦截；渠道下拉有数据；成功后展示 plan_id。

### 场景 2：批量上传全流程

```
1. 进入「批量创建推广作品」页
2. 下载模板 4
3. 上传填好的 Excel
4. 提交 → 看到「批量任务创建成功」和进度提示
5. 等待轮询自动完成 → 浏览器自动下载结果文件
```

**断言点**：上传按钮在无文件时禁用；轮询期间显示进度；最终触发下载。

### 场景 3：签名错误的用户体验

```
1. 故意配置错误的 secret_key
2. 调用任意接口
3. 断言页面显示的是「签名校验失败，请检查 secret_key」
   而不是原始的「timestamp 无效」
```

**断言点**：错误提示是可读中文，包含具体的解决建议。

### E2E 注意事项

- 只在**测试环境**跑，绝不对生产环境执行
- 需要人工触发，不放进 CI 自动流程（避免消耗配额）
- 写操作类场景要用专门的测试渠道，方便事后清理

## 十、提交前检查清单

每次提 PR 前，跑一遍并逐项打勾。

### 自动检查

```bash
cd web
npm run verify
```

这一条命令等于：

```bash
npm run typecheck   # TypeScript 类型检查
npm run lint        # ESLint 检查
npm run test        # 全部单元测试
```

### 手动检查

**代码质量**

- [ ] 没有 `console.log` 残留（调试用的日志走 `infra/http/interceptor-log.ts`）
- [ ] 没有 `// TODO` 或 `// FIXME` 未处理（有的话开 Issue 跟踪）
- [ ] 没有注释掉的死代码
- [ ] 没有 `any` 类型（确实需要时用 `unknown` + 类型守卫）

**架构合规**（对照 01 文档的依赖矩阵）

- [ ] 没有下层引用上层
- [ ] 服务层/基础设施层/工具层没有 `ElMessage`
- [ ] 视图层没有 `axios` 或签名代码
- [ ] 类型定义在 `types/`，不在服务层内联
- [ ] 单个 `.vue` 文件 ≤ 300 行

**测试**

- [ ] 新增函数有对应测试
- [ ] 修 Bug 时加了回归测试
- [ ] 有 `loading` 的地方测了失败分支的复位
- [ ] 测试里没有真实网络请求（MSW 的 `onUnhandledRequest: 'error'` 会自动把关）

**安全**

- [ ] 没有硬编码凭证
- [ ] 没有提交 `.env.local`
- [ ] 新增日志输出不含敏感字段

**文档**

- [ ] 新增接口已写入 03 文档
- [ ] 新增枚举已写入 03 文档 § 二
- [ ] 联调发现的差异已回填到 03 文档附录 B
- [ ] JSDoc 注明了接口路径和文档章节号
