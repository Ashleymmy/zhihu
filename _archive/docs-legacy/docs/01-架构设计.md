## 一、为什么要分层

### 先看不分层会怎样

假设我们不分层，把所有逻辑都写在页面组件里。一个「创建推广计划」的页面会长这样：

```vue
<!-- ❌ 反面教材：所有东西堆在一起 -->
<script setup>
import axios from 'axios'
import CryptoJS from 'crypto-js'
import { ref } from 'vue'

const form = ref({ task_id: '', channel_id: '', keyword: '' })

async function submit() {
  // 1. 拼参数
  const params = { ...form.value, access_token: 'Db6j0Yq0eppBb', timestamp: Math.floor(Date.now() / 1000) }
  // 2. 排序
  const sorted = Object.keys(params).sort()
  // 3. 拼字符串
  const kvStr = sorted.map(k => `${k}=${params[k]}`).join('&')
  // 4. MD5
  const md5Str = CryptoJS.MD5(kvStr).toString().toLowerCase()
  // 5. HmacSHA256
  const signature = CryptoJS.HmacSHA256(md5Str, 'a735eb11da74123074675fa3522a90d1').toString()
  // 6. 发请求
  const res = await axios.post('https://open.zhihu.com/alliance/api/popularize_plan', { ...params, signature })
  // 7. 处理错误
  if (res.data.error) { alert(res.data.error.message) } else { alert('成功') }
}
</script>
```

这段代码能跑，但有五个致命问题：

| 问题 | 后果 |
| --- | --- |
| **密钥硬编码在前端** | 打开浏览器 F12 就能看到 `secret_key`，安全事故 |
| **签名逻辑重复 31 遍** | 31 个接口就要复制 31 次，签名规则一改要改 31 处 |
| **无法单元测试** | 签名逻辑和 UI 耦合，测签名必须渲染组件 |
| **错误处理各写各的** | 有的 `alert`，有的 `console.log`，用户体验不一致 |
| **换 UI 库要重写业务** | 业务逻辑长在组件里，组件一换全部重写 |

### 分层要达到的目标

| 目标 | 怎么实现 |
| --- | --- |
| **签名只写一次** | 抽到基础设施层的拦截器里，所有请求自动带签名 |
| **业务逻辑可测试** | 业务逻辑不依赖 DOM，用 Vitest 直接跑函数 |
| **接口变更影响面小** | 接口字段变了，只改服务层一个文件 |
| **UI 可替换** | 视图层只负责展示，换 UI 库不影响下面五层 |
| **新人能快速定位** | 有明确规则告诉你代码该放哪 |

## 二、六层架构总览

我们采用**自上而下依赖**的六层架构。上层可以调用下层，下层**绝对不能**调用上层。

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 层  视图层  View Layer                                  │
│  views/ + components/                                        │
│  职责：渲染界面、接收用户输入、把事件转交给下层                    │
│  关键词：模板、样式、表单校验（格式层面）                         │
├─────────────────────────────────────────────────────────────┤
│  第 2 层  业务组合层  Composition Layer                        │
│  composables/                                                │
│  职责：编排一个业务动作的完整流程（多个接口调用 + 状态切换）        │
│  关键词：useXxx() 函数、loading 状态、业务校验                   │
├─────────────────────────────────────────────────────────────┤
│  第 3 层  状态层  Store Layer                                 │
│  stores/                                                     │
│  职责：管理跨页面共享的数据（凭证、渠道列表、字典）                 │
│  关键词：Pinia store、缓存、持久化                              │
├─────────────────────────────────────────────────────────────┤
│  第 4 层  服务层  Service Layer                                │
│  services/                                                   │
│  职责：一个函数 = 一个接口。只做参数组装和返回值归一化              │
│  关键词：API 函数、DTO 类型、路径常量                            │
├─────────────────────────────────────────────────────────────┤
│  第 5 层  基础设施层  Infrastructure Layer                      │
│  infra/                                                      │
│  职责：HTTP 客户端、拦截器、签名注入、错误归一化、日志              │
│  关键词：Axios 实例、interceptor、统一异常                       │
├─────────────────────────────────────────────────────────────┤
│  第 6 层  工具层  Utils Layer                                  │
│  utils/ + types/ + constants/                                │
│  职责：纯函数工具、类型定义、枚举常量。不含任何业务语义             │
│  关键词：纯函数、无副作用、可独立测试                             │
└─────────────────────────────────────────────────────────────┘

           依赖方向：只能向下 ↓  禁止向上 ✗  禁止跨层跳跃 ⚠
```

### 一句话记住每一层

| 层 | 一句话 | 举例 |
| --- | --- | --- |
| 视图层 | 「长什么样」 | 创建计划的表单页面 |
| 业务组合层 | 「做这件事的步骤」 | 先查渠道 → 再创建计划 → 刷新列表 |
| 状态层 | 「大家共用的数据」 | 当前 access_token、渠道下拉选项 |
| 服务层 | 「怎么调这个接口」 | `createPopularizePlan(params)` |
| 基础设施层 | 「所有请求的公共处理」 | 自动加签名、自动报错提示 |
| 工具层 | 「不带业务的小工具」 | 时间戳格式化、字典排序 |

## 三、每一层详解

### 第 6 层 · 工具层（Utils Layer）

**最底层，先讲它，因为其他层都依赖它。**

#### 职责

放**纯函数**、**类型定义**、**常量枚举**。判断标准很简单：

> 这段代码能不能在一个完全没有 Vue、没有 Axios 的 Node 脚本里直接跑？
> 能 → 属于工具层。不能 → 不属于。

#### 包含什么

```

├── utils/                    纯函数工具
│   ├── crypto.ts             MD5 / HmacSHA256 封装
│   ├── signature.ts          签名核心算法（六步法）★最重要
│   ├── datetime.ts           时间戳与日期字符串互转
│   ├── object.ts             对象字典排序、剔除空值

│   └── validator.ts          格式校验（URL、时间戳合法性）
├── types/                    TypeScript 类型定义
│   ├── api-common.ts         统一响应包装、分页结构、错误结构
│   ├── plan.ts               推广计划相关 DTO
│   ├── composition.ts        推广作品相关 DTO
│   ├── channel.ts            渠道相关 DTO
│   ├── report.ts             数据报表相关 DTO
│   ├── content.ts            盐选/有声书/漫剧相关 DTO
│   └── risk.ts               举报风控相关 DTO
└── constants/                常量与枚举

    └── sign-rules.ts         签名排除字段清单 ★重要
```

#### 代码示例

`utils/object.ts` — 字典排序与 kv 拼接：

```typescript
/**
 * 按 key 的字典升序排序对象，返回新对象。
 * 知乎签名要求参数必须先做字典升序排序。
 *
 * @example
 * sortObjectByKey({ b: 2, a: 1 })  // => { a: 1, b: 2 }
 */
export function sortObjectByKey<T extends Record<string, unknown>>(obj: T): T {
  return Object.keys(obj)
    .sort()
    .reduce((acc, key) => {
      acc[key] = obj[key]
      return acc
    }, {} as Record<string, unknown>) as T
}

/**
 * 把对象拼成 key=value&key=value 形式的字符串。
 *
 * 注意：知乎签名要求值**不做 URL 编码**，中文原样拼接。
 * 这一点和大多数签名算法不同，很容易踩坑。
 *
 * @example
 * buildKvString({ a: 1, b: '中文' })  // => 'a=1&b=中文'
 */
export function buildKvString(obj: Record<string, unknown>): string {
  return Object.entries(obj)
    .map(([key, value]) => `${key}=${String(value)}`)
    .join('&')
}
```

`constants/sign-rules.ts` — 哪些字段不参与签名（这是本项目最容易出 bug 的地方）：

```typescript
/**
 * 全局不参与签名计算的参数名。
 *
 * 依据 OpenAPI V1.4.17 文档：
 * - signature 本身当然不参与
 * - 文件类参数（file / image）不参与
 * - 分页参数 offset / limit 明确标注"不参与签名"
 * - second_channel_id 明确标注"不参与签名"
 * - Header 类参数（X-Requested-With）不参与
 */
export const GLOBAL_SIGN_EXCLUDED_KEYS = [
  'signature',
  'file',
  'image',
  'offset',
  'limit',
  'second_channel_id',
  'X-Requested-With',
] as const

/**
 * 特定接口的额外排除字段。
 * key 为接口路径，value 为该接口额外不参与签名的字段。
 *
 * 留这个扩展点，是因为知乎不同接口的签名规则存在个体差异，
 * 后续联调发现差异时在此登记，不要去改签名算法本身。
 */
export const PER_API_SIGN_EXCLUDED_KEYS: Record<string, readonly string[]> = {
  // 示例：如果某接口发现还有别的字段不参与签名，在这里补充
  // '/alliance/api/xxx': ['some_field'],
}
```

#### 规则

- ✅ 只能 import 第三方纯库（crypto-js、dayjs）和同层文件
- ❌ 不能 import Vue、Pinia、Axios、Element Plus
- ❌ 不能有 `console.log` 之外的副作用（不发请求、不改全局状态）
- ✅ 每个导出函数必须有 JSDoc 注释和 `@example`
- ✅ 单元测试覆盖率要求 **≥ 90%**（这层最容易测，也最该测）

### 第 5 层 · 基础设施层（Infrastructure Layer）

#### 职责

**所有 HTTP 请求的公共处理都在这一层**。它像一个安检门，进出的请求都要过一遍。

具体做四件事：

1. **请求出去前**：自动注入 `access_token`、`timestamp`、`signature`
2. **响应回来后**：把知乎的两种响应格式（成功/错误）归一化成统一结构
3. **出错时**：抛出统一的异常对象，附带可读的中文提示
4. **全程**：记录日志，方便排查

#### 包含什么

```
src/infra/
├── http/
│   ├── client.ts             Axios 实例创建与基础配置
│   ├── interceptor-sign.ts   请求拦截器：注入凭证与签名 ★核心
│   ├── interceptor-error.ts  响应拦截器：错误归一化 ★核心
│   ├── interceptor-log.ts    请求/响应日志
│   └── index.ts              统一导出装配好的 client
├── error/
│   ├── ApiError.ts           自定义异常类
│   └── error-mapper.ts       错误码 → 中文文案
└── storage/
    └── secure-storage.ts     凭证的本地存储（含脱敏读写）
```

#### 代码示例

`infra/http/client.ts`：

```typescript
import axios, { type AxiosInstance } from 'axios'

/**
 * 创建 Axios 实例。
 *
 * baseURL 的取值策略（重要）：
 * - 开发环境：'/api'，由 Vite dev server 代理转发到知乎，规避 CORS
 * - 生产环境：读取 VITE_API_BASE_URL，指向我们自己的 BFF 后端
 *
 * 无论哪个环境，前端都**不直连** open.zhihu.com。
 * 原因见 docs/01-架构设计.md 的「安全边界」章节。
 */
export function createHttpClient(): AxiosInstance {
  const instance = axios.create({
    baseURL: import.meta.env.VITE_API_BASE_URL ?? '/api',
    timeout: 30_000,          // 30 秒。批量接口可能较慢，但不应超过这个值
    withCredentials: false,   // 知乎接口用 token 鉴权，不需要 cookie
    headers: {
      'Content-Type': 'application/json;charset=utf-8',
    },
  })
  return instance
}
```

`infra/http/interceptor-error.ts` — 错误归一化：

```typescript
import type { AxiosInstance } from 'axios'
import { ApiError } from '../error/ApiError'
import { mapErrorCodeToMessage } from '../error/error-mapper'

/**
 * 响应拦截器：把知乎的两种响应格式统一成一种。
 *
 * 知乎成功响应：{ success: true, msg: '...', data: {...} }
 * 知乎失败响应：{ error: { code: 400400, name: 'OpenApiParamError', message: '...' } }
 *
 * 注意：失败时 HTTP 状态码**可能仍然是 200**，所以不能只靠状态码判断成败，
 * 必须检查 body 里有没有 error 字段。这是很容易忽略的点。
 */
export function installErrorInterceptor(instance: AxiosInstance): void {
  instance.interceptors.response.use(
    (response) => {
      const body = response.data

      // 情况一：业务错误（HTTP 200 但 body 带 error）
      if (body && typeof body === 'object' && 'error' in body) {
        const { code, name, message } = body.error
        throw new ApiError({
          code,
          name,
          rawMessage: message,
          friendlyMessage: mapErrorCodeToMessage(code, message),
          requestUrl: response.config.url,
        })
      }

      // 情况二：文件流响应（批量任务结果），原样返回
      if (response.config.responseType === 'blob') {
        return response
      }

      // 情况三：正常业务数据，剥掉外壳直接返回 data
      // 注意：部分接口（如查询榜单列表）直接返回数组，没有 data 包装
      return Array.isArray(body) ? body : (body.data ?? body)
    },
    (error) => {
      // 网络层错误：超时、断网、5xx
      throw ApiError.fromAxiosError(error)
    },
  )
}
```

`infra/error/ApiError.ts`：

```typescript
/**
 * 项目统一异常类。
 *
 * 设计意图：上层代码只需要 catch ApiError 一种异常，
 * 不用关心是网络错误、业务错误还是解析错误。
 */
export class ApiError extends Error {
  readonly code: number
  readonly apiName: string
  readonly rawMessage: string
  readonly friendlyMessage: string
  readonly requestUrl?: string

  constructor(params: {
    code: number
    name: string
    rawMessage: string
    friendlyMessage: string
    requestUrl?: string
  }) {
    super(params.friendlyMessage)
    this.name = 'ApiError'
    this.code = params.code
    this.apiName = params.name
    this.rawMessage = params.rawMessage
    this.friendlyMessage = params.friendlyMessage
    this.requestUrl = params.requestUrl
  }

  /** 从 Axios 网络错误构造 */
  static fromAxiosError(error: unknown): ApiError {
    const isTimeout =
      typeof error === 'object' && error !== null && 'code' in error && error.code === 'ECONNABORTED'

    return new ApiError({
      code: isTimeout ? -1 : -2,
      name: isTimeout ? 'NetworkTimeout' : 'NetworkError',
      rawMessage: error instanceof Error ? error.message : String(error),
      friendlyMessage: isTimeout
        ? '请求超时，请检查网络后重试'
        : '网络异常，请稍后重试',
    })
  }
}
```

#### 规则

- ✅ 可以 import 工具层
- ❌ 不能 import 服务层、状态层、视图层
- ❌ 拦截器里**不要**弹 UI 提示（那是视图层的事），只抛异常
- ✅ 所有 `magic number`（超时时间、重试次数）必须定义为命名常量

> **为什么拦截器不弹提示？**
> 因为有些请求失败了不需要提示用户（比如后台静默轮询）。
> 让上层决定要不要提示，比在底层一律弹窗更灵活。

### 第 4 层 · 服务层（Service Layer）

#### 职责

**一个函数对应一个接口，一对一，不多不少。**

这一层是「接口文档的代码翻译」。看到 03 文档里有 31 个接口，
这一层就应该有 31 个导出函数。

它只做两件事：

1. 把业务参数组装成接口要求的格式
2. 把接口返回值转成前端好用的类型

它**不做**：不管 loading、不管错误提示、不管多接口编排。

#### 包含什么

```
src/services/
├── plan.service.ts             推广计划（2 个接口）
├── composition.service.ts      推广作品 v2 + v1（8 个接口）
├── channel.service.ts          代理渠道（2 个接口）
├── batch-task.service.ts       批量任务（1 个接口）
├── popularize-task.service.ts  推广任务（1 个接口）
├── report.service.ts           数据报表（1 个接口）
├── vip-content.service.ts      盐选内容榜单（4 个接口）
├── audio.service.ts            有声书（2 个接口）
├── intercept.service.ts        评论截流举报（3 个接口）
```

#### 代码示例

`services/plan.service.ts`：

```typescript
import { http } from '@/infra/http'
import { API_PATHS } from '@/constants/api-paths'
import type { CreatePlanRequest, CreatePlanResponse, BatchTaskCreated } from '@/types/plan'

/**
 * 单个创建推广计划
 *
 * 接口：POST /alliance/api/popularize_plan
 * 文档：docs/03-接口文档.md § 2.1.1
 *
 * 注意：second_channel_id 为可选参数，且**不参与签名**。
 * 签名排除逻辑已在 constants/sign-rules.ts 统一配置，此处无需特殊处理。
 */
export function createPlan(payload: CreatePlanRequest) {
  return http.post<CreatePlanResponse>(API_PATHS.PLAN_CREATE, payload)
}

/**
 * 批量创建推广计划（Excel 上传）
 *
 * 接口：POST /alliance/api/popularize_plans
 * 文档：docs/03-接口文档.md § 2.1.2
 *
 * 三个易错点：
 * 1. 必须用 FormData，不能用 JSON
 * 2. 必须带 Header: X-Requested-With = 'openApi'
 * 3. file 与 Header 参数**不参与签名**
 *
 * 返回的 batch_task_id 需要用 batch-task.service.ts 的
 * getBatchTaskResult() 去查最终结果，这是异步任务。
 */
export function createPlansBatch(params: {
  file: File
  taskId: string
  channelId: string
  popularizeType: number
  secondChannelId?: string
}) {
  const formData = new FormData()
  formData.append('file', params.file)
  formData.append('task_id', params.taskId)
  formData.append('channel_id', params.channelId)
  formData.append('popularize_type', String(params.popularizeType))
  if (params.secondChannelId) {
    formData.append('second_channel_id', params.secondChannelId)
  }

  return http.post<BatchTaskCreated>(API_PATHS.PLAN_CREATE_BATCH, formData, {
    headers: {
      'X-Requested-With': 'openApi',
      'Content-Type': 'multipart/form-data',
    },
  })
}
```

#### 规则

- ✅ 可以 import 基础设施层、工具层
- ❌ 不能 import 状态层、业务组合层、视图层
- ❌ 不能出现 `ElMessage`、`alert` 等 UI 调用
- ❌ 不能有 `ref`、`reactive` 等 Vue 响应式 API
- ✅ 每个函数必须有 JSDoc，注明**接口路径**和**03 文档章节号**
- ✅ 函数命名统一动词开头：`create` / `update` / `get` / `list` / `upload`

> **为什么服务层不能碰 Vue？**
> 因为将来开发微信小程序（`app/` 目录）时，服务层可以整个复制过去复用。
> 只要替换基础设施层的 HTTP 实现（`wx.request` 代替 `axios`），业务代码零改动。

### 第 3 层 · 状态层（Store Layer）

#### 职责

管理**跨页面共享**的数据。判断标准：

> 这个数据是否被两个以上的页面用到？
> 是 → 放 store。否 → 放组件内的 `ref` 就够了。

#### 包含什么

```
src/stores/
├── credential.store.ts    开发者凭证（access_token 等）
├── channel.store.ts       渠道列表（一代/二代），带缓存
├── dictionary.store.ts    业务字典（媒体类型、作品分类等枚举）
└── app.store.ts           全局 UI 状态（侧边栏折叠、主题）
```

#### 代码示例

`stores/channel.store.ts` — 带缓存的渠道列表：

```typescript
import { defineStore } from 'pinia'
import { ref } from 'vue'
import { getAgentChannels } from '@/services/channel.service'
import type { Channel } from '@/types/channel'

/**
 * 渠道 Store。
 *
 * 为什么要缓存？
 * 因为几乎所有接口都要传 channel_id，如果每个页面都去请求一次渠道列表，
 * 会快速消耗掉每日接口配额（见 README 红线三）。
 *
 * 缓存策略：进程内缓存 + 5 分钟过期，可手动强制刷新。
 */
export const useChannelStore = defineStore('channel', () => {
  const channels = ref<Channel[]>([])
  const loading = ref(false)
  const lastFetchedAt = ref(0)

  const CACHE_TTL_MS = 5 * 60 * 1000  // 5 分钟

  /** 缓存是否仍然有效 */
  function isCacheValid(): boolean {
    return channels.value.length > 0 && Date.now() - lastFetchedAt.value < CACHE_TTL_MS
  }

  /**
   * 获取渠道列表。默认走缓存。
   * @param force 传 true 强制重新请求
   */
  async function fetchChannels(force = false): Promise<Channel[]> {
    if (!force && isCacheValid()) {
      return channels.value
    }
    loading.value = true
    try {
      channels.value = await getAgentChannels()
      lastFetchedAt.value = Date.now()
      return channels.value
    } finally {
      loading.value = false
    }
  }

  return { channels, loading, fetchChannels }
})
```

#### 规则

- ✅ 可以 import 服务层、工具层
- ❌ 不能 import 视图层、业务组合层
- ❌ 不能存放只有单个页面用的数据（那是过度设计）
- ✅ 涉及远程数据的 store 必须实现缓存策略，减少接口调用
- ⚠️ **凭证 store 存 `access_token` 可以，但绝不存 `secret_key`**

### 第 2 层 · 业务组合层（Composition Layer）

#### 职责

**编排一个完整业务动作的流程。**

服务层的函数是「原子操作」，一次只调一个接口。
但真实业务往往需要好几步。比如「批量创建推广作品」实际流程是：

```
1. 校验用户选的 Excel 文件格式对不对
2. 调批量创建接口 → 拿到 batch_task_id
3. 轮询查询批量任务结果接口（每 3 秒一次，最多 20 次）
4. 拿到文件流 → 触发浏览器下载
5. 刷新页面上的作品列表
6. 全程管理 loading 状态和进度提示
```

这一整套流程就写在业务组合层，封装成一个 `useBatchCreateComposition()`。

#### 包含什么

```
src/composables/
├── useCredential.ts             凭证配置与校验
├── usePlanForm.ts               创建计划表单的完整流程
├── useCompositionForm.ts        创建/更新作品表单流程（v2）
├── useBatchUpload.ts            批量上传 + 轮询 + 下载 ★复杂
├── useChannelSelector.ts        渠道级联选择（一代 → 二代）
├── usePagination.ts             分页列表通用逻辑
├── useApiRequest.ts             请求状态通用封装（loading/error/data）
└── useSafeAction.ts             带确认弹窗的危险操作封装
```

#### 代码示例

`composables/useApiRequest.ts` — 最常用的一个，把 loading/error 管理标准化：

```typescript
import { ref, shallowRef } from 'vue'
import { ElMessage } from 'element-plus'
import { ApiError } from '@/infra/error/ApiError'

/**
 * 通用请求状态封装。
 *
 * 解决的问题：每个页面都要写 loading = true / try / catch / finally，
 * 重复且容易漏掉 finally 导致 loading 卡死。
 *
 * @example
 * const { data, loading, error, run } = useApiRequest(getAgentChannels)
 * await run()               // 自动管理 loading，出错自动提示
 * console.log(data.value)   // 请求结果
 */
export function useApiRequest<TArgs extends unknown[], TResult>(
  requestFn: (...args: TArgs) => Promise<TResult>,
  options: {
    /** 出错时是否自动弹提示，默认 true。静默轮询场景可设为 false */
    showErrorToast?: boolean
    /** 成功提示文案，不传则不提示 */
    successMessage?: string
  } = {},
) {
  const { showErrorToast = true, successMessage } = options

  const data = shallowRef<TResult>()
  const loading = ref(false)
  const error = shallowRef<ApiError>()

  async function run(...args: TArgs): Promise<TResult | undefined> {
    loading.value = true
    error.value = undefined
    try {
      const result = await requestFn(...args)
      data.value = result
      if (successMessage) {
        ElMessage.success(successMessage)
      }
      return result
    } catch (e) {
      const apiError = e instanceof ApiError ? e : ApiError.fromAxiosError(e)
      error.value = apiError
      if (showErrorToast) {
        ElMessage.error(apiError.friendlyMessage)
      }
      return undefined
    } finally {
      // 必须放在 finally，否则出错时 loading 会永远为 true
      loading.value = false
    }
  }

  return { data, loading, error, run }
}
```

`composables/useBatchUpload.ts` — 批量上传的完整编排：

```typescript
import { ref } from 'vue'
import { getBatchTaskResult } from '@/services/batch-task.service'
import { downloadBlob } from '@/utils/download'

/**
 * 批量任务上传 + 轮询 + 结果下载 的完整流程封装。
 *
 * 背景：知乎的批量接口是**异步**的。
 * 调用后只返回 batch_task_id，真正的处理结果要另一个接口去查，
 * 且结果是**文件流**（Content-Type: application/octet-stream）。
 *
 * 轮询参数说明：
 * - 间隔 3 秒：太快会浪费日配额，太慢用户等得急
 * - 上限 20 次（共 60 秒）：超过就提示用户稍后自行查询，不无限轮询
 */
export function useBatchUpload() {
  const POLL_INTERVAL_MS = 3_000
  const POLL_MAX_ATTEMPTS = 20

  const uploading = ref(false)
  const polling = ref(false)
  const attempts = ref(0)
  const batchTaskId = ref<string>()

  /**
   * 执行完整批量流程
   * @param uploadFn 实际调用批量接口的函数，由调用方传入
   */
  async function execute(uploadFn: () => Promise<{ batch_task_id: string }>) {
    uploading.value = true
    try {
      const { batch_task_id } = await uploadFn()
      batchTaskId.value = batch_task_id
      await pollResult(batch_task_id)
    } finally {
      uploading.value = false
    }
  }

  /** 轮询批量任务结果，成功后自动下载 */
  async function pollResult(taskId: string) {
    polling.value = true
    attempts.value = 0
    try {
      while (attempts.value < POLL_MAX_ATTEMPTS) {
        attempts.value += 1
        try {
          const blob = await getBatchTaskResult(taskId)
          downloadBlob(blob, `批量任务结果_${taskId}.xlsx`)
          return
        } catch {
          // 任务未完成时接口会报错，属于预期情况，继续等待
          await sleep(POLL_INTERVAL_MS)
        }
      }
      throw new Error(
        `轮询超过 ${POLL_MAX_ATTEMPTS} 次仍未拿到结果，` +
        `请稍后在「批量任务查询」页面用任务 ID ${taskId} 手动查询`,
      )
    } finally {
      polling.value = false
    }
  }

  return { uploading, polling, attempts, batchTaskId, execute }
}

function sleep(ms: number) {
  return new Promise((resolve) => setTimeout(resolve, ms))
}
```

#### 规则

- ✅ 可以 import 状态层、服务层、工具层
- ❌ 不能 import 视图层、不能操作 DOM
- ✅ 文件名与导出函数名统一用 `useXxx` 驼峰
- ✅ 必须返回对象（而不是数组），方便调用方按需取值和重命名
- ✅ 有 `loading` 的地方必须用 `try...finally` 复位

> **业务组合层 vs 服务层怎么区分？**
> 服务层 = 一个接口一个函数，不含流程。
> 业务组合层 = 多个步骤组成的流程，含状态。
> 如果一个动作只调一个接口且不需要 loading，可以让视图层直接调服务层，不必强行加一层。


**注意第 3 层状态层没出现在这条链路上**。因为这次操作不需要读写共享状态
（除了拦截器读了一下凭证）。这是正常的——不是每个请求都要经过所有六层。

## 六、分层规约（硬性规则）

### 依赖矩阵

行 = 谁，列 = 能不能 import。✅ 允许，❌ 禁止。

| ↓ 谁 \ 能否引用 → | 视图 | 业务组合 | 状态 | 服务 | 基础设施 | 工具 |
| --- | :---: | :---: | :---: | :---: | :---: | :---: |
| **视图层** | ✅ | ✅ | ✅ | ⚠️ | ❌ | ✅ |
| **业务组合层** | ❌ | ✅ | ✅ | ✅ | ❌ | ✅ |
| **状态层** | ❌ | ❌ | ✅ | ✅ | ❌ | ✅ |
| **服务层** | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ |
| **基础设施层** | ❌ | ❌ | ⚠️ | ❌ | ✅ | ✅ |
| **工具层** | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |

两个 ⚠️ 的说明：

- **视图层 → 服务层**：允许，但仅限「只调一个接口且不需要 loading 管理」的简单场景。
  一旦需要 loading、错误处理或多步流程，必须经过业务组合层。
- **基础设施层 → 状态层**：仅允许签名拦截器读取凭证 store。这是唯一例外，
  且必须是**只读**。除此之外基础设施层不得触碰状态层。

### 五条铁律

**铁律 1：依赖只能向下**

下层不知道上层的存在。工具层不知道有没有 Vue，服务层不知道有没有页面。

**铁律 2：签名逻辑只有一处实现**

`utils/signature.ts` 是唯一实现，`infra/http/interceptor-sign.ts` 是唯一调用点。
在任何其他地方看到 `HmacSHA256` 字样，都视为 Bug。

**铁律 3：一个接口一个服务函数**

不允许一个服务函数内部调两次 HTTP。要调两次就上升到业务组合层。

**铁律 4：UI 提示只在视图层和业务组合层**

`ElMessage` / `ElMessageBox` 不允许出现在服务层、基础设施层、工具层。

**铁律 5：类型定义统一放工具层的 `types/`**

不要在服务层文件里内联定义 `interface`。类型要能被多层共享。

## 七、分层决策树

写代码前，用这棵树判断代码该放哪：

```
我要写的这段代码……

├─ 是 HTML 模板或 CSS 样式？
│   └─ ✅ 视图层  views/ 或 components/
│
├─ 是「用户点了某个按钮之后要走的一串流程」？
│   ├─ 只调 1 个接口，不需要 loading？
│   │   └─ ✅ 视图层直接调服务层
│   └─ 调多个接口 / 需要 loading / 需要轮询？
│       └─ ✅ 业务组合层  composables/
│
├─ 是「好几个页面都要用的数据」？
│   └─ ✅ 状态层  stores/
│
├─ 是「调某一个具体接口」？
│   └─ ✅ 服务层  services/
│
├─ 是「所有请求都要做的事」（加签名、统一报错、打日志）？
│   └─ ✅ 基础设施层  infra/
│
├─ 是「输入固定就输出固定的纯函数」（算 MD5、格式化时间）？
│   └─ ✅ 工具层  utils/
│
├─ 是「接口的请求或返回数据结构」？
│   └─ ✅ 工具层  types/
│
└─ 是「固定不变的值」（接口路径、枚举、错误码）？
    └─ ✅ 工具层  constants/
```

### 几个真实场景演练

**场景 A：作品一级分类和二级分类的合法组合校验**

文档规定：一级分类「1-图文」只能配二级分类 1~4，「2-视频」只能配 5~10，「0-其他」只能配 11。

| 拆解 | 放哪一层 | 文件 |
| --- | --- | --- |
| 合法组合的映射表 | 工具层 | `constants/enums.ts` |
| 校验函数 `isValidSubType(type, subType)` | 工具层 | `utils/validator.ts` |
| 级联选择器组件（选了一级，二级只显示合法项） | 视图层 | `components/business/CompositionTypeCascader.vue` |
| 提交前的最终校验 | 业务组合层 | `composables/useCompositionForm.ts` |

**场景 B：`offset` / `limit` 不参与签名**

| 拆解 | 放哪一层 | 文件 |
| --- | --- | --- |
| 排除字段清单 | 工具层 | `constants/sign-rules.ts` |
| 剔除逻辑 | 基础设施层 | `infra/http/interceptor-sign.ts` |

视图层和服务层**完全不需要知道**这件事。这就是分层的价值。

**场景 C：日配额快用完了要提示用户**

| 拆解 | 放哪一层 | 文件 |
| --- | --- | --- |
| 计数与阈值判断 | 基础设施层 | `infra/http/interceptor-log.ts` 里累加 |
| 计数值存储 | 状态层 | `stores/app.store.ts` |
| 顶栏展示「今日已调用 N 次」 | 视图层 | `layouts/DefaultLayout.vue` |

## 八、安全边界

**这一节是整份文档最重要的部分，必须完整读完。**

### 问题所在

知乎的签名算法需要 `secret_key`。如果我们在浏览器里算签名，
`secret_key` 就必须存在于前端代码中。而前端代码是**完全公开的**——
任何人按 F12 或看打包产物就能拿到。

拿到 `secret_key` 会怎样：

- 伪造我们的身份调用所有接口
- 恶意刷爆我们的每日配额，让整个团队没法工作
- 创建垃圾推广计划、提交虚假举报，损害账号信誉

除此之外还有一个技术问题：浏览器的同源策略会拦住前端直连 `open.zhihu.com`
的请求（CORS），知乎的接口不会为我们的域名放开跨域头。

### 两个环境，两种方案

#### 开发环境：Vite Dev Proxy

开发阶段为了效率，可以用 Vite 的开发代理解决 CORS。
签名仍在浏览器算，`secret_key` 从 `.env.local` 读。

```typescript
// vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'https://open.zhihu.com',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  },
})
```

```
浏览器  →  Vite Dev Server (localhost:5173)  →  open.zhihu.com
         （签名在浏览器算）      （仅转发，解决 CORS）
```

**这个方案的适用条件，三条必须同时满足：**

1. 只在本机 `localhost` 运行，**不部署到任何可公网访问的地址**
2. 使用的是**测试账号**的凭证，不是生产账号
3. `.env.local` 已加入 `.gitignore`，绝不提交

#### 生产环境：BFF 签名代理（必须）

生产环境**必须**引入一层自己的后端。`secret_key` 只存在于后端环境变量里，
前端永远接触不到它。

```
浏览器  →  我们的 BFF 后端  →  open.zhihu.com
         （不含密钥）    （签名在此计算，密钥存服务端环境变量）
```

BFF 要做的事：

| 职责 | 说明 |
| --- | --- |
| 保管密钥 | `secret_key` 存服务端环境变量或密钥管理服务 |
| 计算签名 | 收到前端请求 → 补齐 token/timestamp → 算签名 → 转发知乎 |
| 用户鉴权 | **BFF 自己必须有登录鉴权**，否则等于把签名能力公开了 |
| 配额保护 | 按用户做限流，防止单个用户刷爆团队配额 |
| 审计日志 | 记录谁在什么时候调了什么接口，出问题能追溯 |

> ⚠️ **特别提醒**：BFF 如果不加鉴权，就变成了一个「公开的知乎签名服务」，
> 危害比直接泄露 `secret_key` 更大——因为攻击者连密钥都不用偷，
> 直接调我们的接口就行。**BFF 的登录鉴权不是可选项。**

### 环境变量约定

`.env.example`（提交 Git，作为模板）：

```bash
# ===== 提交到 Git 的样例文件，不要填真实值 =====

# 后端 API 地址
# 开发环境留空，走 Vite proxy 的 /api
# 生产环境填 BFF 地址，如 https://bff.internal.example.com
VITE_API_BASE_URL=

# 是否开启前端本地签名（仅开发环境）
# true  = 浏览器算签名（需配 VITE_DEV_SECRET_KEY）
# false = 由后端算签名（生产环境必须为 false）
VITE_ENABLE_LOCAL_SIGN=true

# 开发者 Token（非敏感，可以放前端）
VITE_DEV_ACCESS_TOKEN=

# ⚠️ 签名私钥。仅本地开发填写，且只能写在 .env.local
# 绝对不要填在这个 .env.example 里，绝对不要提交
VITE_DEV_SECRET_KEY=
```

`.gitignore` 必须包含：

```
.env.local
.env.*.local
```

### 上线检查清单

生产部署前逐项确认：

- [ ] `VITE_ENABLE_LOCAL_SIGN=false`
- [ ] `VITE_DEV_SECRET_KEY` 在生产构建中为空
- [ ] 打包产物全文搜索 `secret`、`hmac`、`HmacSHA256`，**结果应为空**
- [ ] BFF 已启用登录鉴权
- [ ] BFF 已配置按用户限流
- [ ] BFF 已开启请求审计日志
- [ ] `.env.local` 未被提交（`git log --all -- '*.env.local'` 应无结果）

## 九、错误处理架构

### 错误分三类

| 类型 | 来源 | 处理层 | 用户感知 |
| --- | --- | --- | --- |
| **格式错误** | 用户填错格式 | 视图层表单校验 | 输入框下方红字，不发请求 |
| **业务错误** | 知乎返回 `error` 字段 | 基础设施层归一化 → 业务组合层提示 | 顶部红色 Toast |
| **网络错误** | 超时、断网、5xx | 基础设施层归一化 | 顶部红色 Toast + 重试按钮 |

### 错误码映射

知乎的错误消息是英文或简略中文（如 `"timestamp 无效"`），
直接给用户看不友好。在 `infra/error/error-mapper.ts` 做翻译：

```typescript
/**
 * 错误码 → 用户友好文案 + 建议动作
 *
 * 设计原则：告诉用户「怎么办」，而不只是「错了」。
 */
const ERROR_MESSAGE_MAP: Record<number, string> = {
  400400: '请求参数有误，请检查填写内容',
  401401: '身份验证失败，请到「凭证配置」页检查 access_token 是否正确',
  403403: '没有权限操作该资源，请确认渠道 ID 是否属于你的账号',
  429429: '今日接口调用次数已达上限，请明天再试或联系知乎运营扩容配额',
  500500: '知乎服务端异常，请稍后重试',
  [-1]: '请求超时，请检查网络后重试',
  [-2]: '网络异常，请检查网络连接',
}

/** 针对特定 message 内容的精准提示，优先级高于错误码 */
const MESSAGE_KEYWORD_HINTS: Array<[RegExp, string]> = [
  [/timestamp/i, '时间戳无效。请检查本机系统时间是否准确，误差过大会导致签名失效'],
  [/signature/i, '签名校验失败。请检查 secret_key 是否正确，以及是否有参数漏算或多算'],
  [/token/i, 'access_token 无效或已过期，请到「凭证配置」页更新'],
]

export function mapErrorCodeToMessage(code: number, rawMessage: string): string {
  for (const [pattern, hint] of MESSAGE_KEYWORD_HINTS) {
    if (pattern.test(rawMessage)) return hint
  }
  return ERROR_MESSAGE_MAP[code] ?? `接口调用失败（${code}）：${rawMessage}`
}
```

> 注意：上表中除 `400400` 外的错误码是我们的**预设**。
> 官方 PDF 只明确给出了 `400400 / OpenApiParamError`。
> 联调过程中遇到新的错误码，请补充到这张表并同步更新 03 文档的错误码章节。

## 十、实战：新增一个接口要改哪些文件

假设知乎新增了一个接口「查询推广计划详情」`GET /alliance/api/popularize_plan/:plan_id`。

按顺序改这 5 个文件（自下而上，符合依赖方向）：

### 步骤 1 · 工具层：登记接口路径

```typescript
// src/constants/api-paths.ts
export const API_PATHS = {
  // ...已有路径
  PLAN_DETAIL: (planId: string) => `/alliance/api/popularize_plan/${planId}`,
} as const
```

### 步骤 2 · 工具层：定义类型

```typescript
// src/types/plan.ts
/** 推广计划详情。字段依据 docs/03-接口文档.md § 2.1.3 */
export interface PlanDetail {
  plan_id: string
  task_id: string
  channel_id: string
  keyword: string
  content_url: string
  popularize_type: number
  created_at: string
}
```

### 步骤 3 · 服务层：写接口函数

```typescript
// src/services/plan.service.ts
/**
 * 查询推广计划详情
 *
 * 接口：GET /alliance/api/popularize_plan/:plan_id
 * 文档：docs/03-接口文档.md § 2.1.3
 */
export function getPlanDetail(planId: string) {
  return http.get<PlanDetail>(API_PATHS.PLAN_DETAIL(planId))
}
```

### 步骤 4 · 视图层：加页面

```vue
<!-- src/views/plan/PlanDetailView.vue -->
<script setup lang="ts">
import { onMounted } from 'vue'
import { useRoute } from 'vue-router'
import { getPlanDetail } from '@/services/plan.service'
import { useApiRequest } from '@/composables/useApiRequest'

const route = useRoute()
const { data, loading, run } = useApiRequest(getPlanDetail)

onMounted(() => run(route.params.planId as string))
</script>
```

### 步骤 5 · 视图层：注册路由

```typescript
// src/router/index.ts
{
  path: '/plan/:planId',
  name: 'PlanDetail',
  component: () => import('@/views/plan/PlanDetailView.vue'),
  meta: { title: '推广计划详情' },
}
```

### 注意：签名相关代码一行都没改

因为签名是拦截器统一处理的。这就是分层的收益——
**新增接口的成本是线性的，不会因为接口变多而变复杂。**

同时别忘了两件事：

1. 在 `docs/03-接口文档.md` 补充 § 2.1.3 章节
2. 在 `docs/05-测试文档.md` 补充对应测试用例
