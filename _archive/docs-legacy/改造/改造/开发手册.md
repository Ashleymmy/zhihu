## 第一章：项目背景与目标

### 1.1 我们要解决什么问题？

**现状**：
- 知乎官方每天通过邮件发送收益数据
- 数据是**按关键词汇总**的（不是按达人的）
- 比如：关键词"知乎推广工具"产生了 5000 元收益

**问题**：
- 这 5000 元应该分给谁？分多少？
- 因为有多个达人在用这个关键词发作品

**我们的解决方案**：
```
建立一套"归因系统"，自动计算每个达人应该拿多少钱

步骤：
1. 达人在系统里"登记作品"（说明用了哪个关键词）
2. 管理员上传邮件数据（关键词的总收益）
3. 系统自动计算（根据作品数量和质量）
4. 应用定价规则（比如达人拿 60%，团长抽 10%）
5. 生成最终收益记录
```

---

### 1.2 为什么要做这个改造？

**原因 1**：知乎的 API 大部分不能用
- ❌ 不能自动查询收益
- ❌ 不能自动查询审核状态
- ✅ 只能创建计划和关键词

**原因 2**：知乎只给汇总数据，不给明细
- 邮件里只有"关键词 + 总收益"
- 没有"哪个达人赚了多少"

**原因 3**：我们需要自己做归因
- 必须自己记录达人的作品
- 必须自己计算分配比例

---

### 1.3 项目目标（你要完成什么）

**核心目标**：
```
让这条链路能跑通：

邮件数据 → 系统自动归因 → 达人看到收益 ✅
```

**具体要做的**：
1. ✅ 达人能登记作品（标题、链接、质量数据）
2. ✅ 管理员能导入邮件数据（上传 Excel）
3. ✅ 系统能自动归因（计算每个达人分多少）
4. ✅ 系统能应用定价规则（60% 给达人，团长抽 10%）
5. ✅ 达人能在前端看到收益

## 第二章：整体架构理解

### 2.1 数据流向（从头到尾）

```
┌─────────────────────────────────────────────────┐
│              完整的数据流                         │
└─────────────────────────────────────────────────┘

1️⃣ 知乎官方发邮件
   ↓ （Excel 附件）
   关键词: 知乎推广工具
   收益: 5000 元

2️⃣ 管理员上传到系统
   ↓ （写入数据库）
   attribution_tasks 表
   id=1, keyword="知乎推广工具", total_revenue=500000（分）

3️⃣ 系统查询作品
   ↓ （从数据库读取）
   creator_works 表
   达人A: 5个作品，质量分2500
   达人B: 3个作品，质量分1500

4️⃣ 系统计算归因
   ↓ （归因算法）
   达人A: 2500元（50%）
   达人B: 1500元（30%）
   
   写入 → attribution_results 表

5️⃣ 生成结算批次
   ↓ （创建批次）
   settlement_batches 表
   settlement_items 表
   
   达人A: source_amount = 2500.0000
   达人B: source_amount = 1500.0000

6️⃣ 应用定价规则（自动）
   ↓ （调用现有逻辑）
   达人A: 2500 × 0.6 = 1500元
   团长抽成: 1500 × 0.1 = 150元
   达人A最终: 1350元

7️⃣ 写入收益表
   ↓
   earnings 表
   
   达人A: 1350元
   团长X: 150元
   达人B: 810元
   ...

8️⃣ 达人查看
   ↓
   前端显示收益
```

**重点理解**：
- **步骤 1-4**：这是新增的（归因系统）
- **步骤 5-7**：这是现有的（定价系统，复用）
- **步骤 8**：这是现有的（前端展示，复用）

---

### 2.2 核心概念解释

#### 概念 1：归因收益

**是什么**：归因系统计算出来的"达人应该拿的金额"

**例子**：
```
关键词总收益: 5000元
达人A的归因收益: 2500元（因为他的作品占50%）
```

**对应字段**：`attribution_results.allocated_revenue`

---

#### 概念 2：定价规则

**是什么**：公司对下游账号的定价比例

**例子**：
```
达人规则: 60% percentage
  意思：达人拿归因收益的 60%
  
团长规则: 10% percentage
  意思：团长从达人应得中抽 10%
```

**对应表**：`pricing_rules`（已存在，不需要改）

---

#### 概念 3：来源金额

**是什么**：定价规则的输入（= 归因收益）

**为什么**：
```
归因收益（2500元）
  ↓ 映射为
来源金额（2500元）
  ↓ 应用定价规则
达人应得（1500元）
```

**对应字段**：`settlement_items.source_amount`

---

#### 概念 4：最终入账

**是什么**：扣除团长抽成后，达人真正拿到的钱

**例子**：
```
达人应得: 1500元
团长抽成: 150元（10%）
达人最终: 1350元 ← 这就是最终入账
```

**对应字段**：`earnings.amount`

---

### 2.3 为什么要分两层？

**第 1 层：归因引擎（你要写的）**
```
职责：计算"关键词收益"应该怎么分给达人
输入：关键词总收益（5000元）
输出：每个达人的归因收益（2500元、1500元）
```

**第 2 层：定价规则（已有的，复用）**
```
职责：计算"归因收益"扣除定价后是多少
输入：达人的归因收益（2500元）
输出：达人应得（1500元）+ 团长抽成（150元）
```

**为什么这样分**：
- ✅ 归因算法和定价规则可以**独立调整**
- ✅ 定价规则由管理员在数据库配置，**不需要改代码**
- ✅ 如果归因算法要调整，**只改第 1 层**
- ✅ 如果定价比例要调整，**只改数据库配置**

| 表名 | 作用 | 举例 |

| `attribution_results` | 记录归因结果 | 达人A 分到 2500元 |
| `keyword_bindings` | 记录关键词绑定 | 达人A 绑定了"知乎推广工具" |
| `creator_works` | 记录作品 | 达人A 发布了 5 个作品 |

#### 怎么做？

**步骤 1：创建迁移文件**
```bash
cd server

# 创建文件
mkdir -p migrations
touch migrations/010_attribution_core.sql
```

**步骤 2：编写 SQL**
```sql
-- server/migrations/010_attribution_core.sql

-- 归因任务表
CREATE TABLE IF NOT EXISTS attribution_tasks (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  data_date DATE NOT NULL COMMENT '数据日期',
  keyword VARCHAR(128) NOT NULL COMMENT '关键词',
  total_revenue BIGINT NOT NULL COMMENT '总收益（分）',
  status ENUM('pending', 'completed', 'failed') DEFAULT 'pending',
  settlement_batch_id BIGINT NULL COMMENT '结算批次ID',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  
  UNIQUE KEY uk_date_keyword (data_date, keyword),
  INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='归因任务';
```

**为什么这样写**：
- `id`：每条记录的唯一编号（自动增长）
- `data_date`：哪一天的数据
- `keyword`：关键词名称
- `total_revenue`：总收益（用"分"存储，避免小数精度问题）
- `status`：状态（pending=待处理，completed=已完成，failed=失败）
- `UNIQUE KEY`：同一天同一关键词只能有一条记录
- `INDEX`：加快按状态查询的速度

#### 怎么做？

```typescript
// server/src/services/creator-works.service.ts

import { rows, withTransaction } from '../db';
import { AuthUser } from '../types';
import { ResultSetHeader } from 'mysql2/promise';

/**
 * 计算作品质量分
 * 
 * 为什么要计算质量分？
 * - 归因时需要根据作品质量分配收益
 * - 质量高的作品应该分得更多
 * 
 * 公式：
 * 质量分 = 浏览量 × 0.5 + 点赞数 × 2 + 转发数 × 5
 * 
 * 为什么这样设置权重？
 * - 浏览量最多，但价值相对低（0.5）
 * - 点赞表示认可，价值中等（2.0）
 * - 转发最有价值，能带来更多曝光（5.0）
 */
function calculateQualityScore(work: {
  viewCount: number;
  likeCount: number;
  shareCount: number;
}): number {
  return (
    work.viewCount * 0.5 +
    work.likeCount * 2.0 +
    work.shareCount * 5.0
  );
}

/**
 * 达人提交作品
 * 
 * 流程：
 * 1. 接收达人提交的作品信息
 * 2. 计算质量分
 * 3. 写入数据库
 */
export async function submitWork(
  user: AuthUser,  // 当前登录的达人
  input: {
    title: string;        // 作品标题
    url: string;          // 作品链接
    platform: string;     // 发布平台（抖音/小红书等）
    keyword: string;      // 使用的关键词
    publishedAt: string;  // 发布时间
    viewCount?: number;   // 浏览量（可选）
    likeCount?: number;   // 点赞数（可选）
    shareCount?: number;  // 转发数（可选）
  }
) {
  // 第 1 步：计算质量分
  const qualityScore = calculateQualityScore({
    viewCount: input.viewCount || 0,
    likeCount: input.likeCount || 0,
    shareCount: input.shareCount || 0
  });
  
  // 第 2 步：写入数据库
  return withTransaction(async (conn) => {
    // withTransaction 是什么？
    // - 保证操作的原子性
    // - 如果中间出错，会自动回滚
    
    const [result] = await conn.query<ResultSetHeader>(
      `INSERT INTO creator_works 
       (work_title, work_url, platform, keyword, creator_id,
        view_count, like_count, share_count, quality_score, 
        published_at, status)
       VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, 'approved')`,
      [
        input.title,
        input.url,
        input.platform,
        input.keyword,
        user.sub,  // 当前登录达人的 ID
        input.viewCount || 0,
        input.likeCount || 0,
        input.shareCount || 0,
        qualityScore,
        input.publishedAt
      ]
    );
    
    // 第 3 步：返回结果
    return {
      id: String(result.insertId),  // 新插入记录的 ID
      qualityScore                   // 计算出的质量分
    };
  });
}

/**
 * 查询我的作品列表
 * 
 * 为什么要这个接口？
 * - 达人需要看到自己登记了哪些作品
 * - 方便核对和管理
 */
export async function listMyWorks(user: AuthUser) {
  return rows(
    `SELECT id, work_title, work_url, platform, keyword, 
            view_count, like_count, share_count, quality_score,
            published_at, created_at
     FROM creator_works
     WHERE creator_id = ?
     ORDER BY created_at DESC
     LIMIT 100`,  // 只返回最近 100 条
    [user.sub]
  );
}
```

**重点理解**：
1. **质量分公式**：可以调整权重，根据实际情况优化
2. **withTransaction**：保证数据一致性，出错会自动回滚
3. **status='approved'**：现阶段直接通过，不需要审核（简化）

```typescript
// server/src/routes/creator-works.ts

import { Router } from 'express';
import { requireAuth } from '../middleware/auth';
import { submitWork, listMyWorks } from '../services/creator-works.service';

const router = Router();

/**
 * POST /api/v1/creator-works
 * 提交作品
 * 
 * 谁能调用？
 * - 只有登录的达人
 * 
 * 请求体示例：
 * {
 *   "title": "知乎推广全攻略",
 *   "url": "https://douyin.com/video/123",
 *   "platform": "douyin",
 *   "keyword": "知乎推广工具",
 *   "publishedAt": "2025-01-20T10:00:00Z",
 *   "viewCount": 10000,
 *   "likeCount": 500
 * }
 */
router.post('/', requireAuth, async (req, res, next) => {
  try {
    // 调用服务层
    const result = await submitWork(req.user!, req.body);
    
    // 返回结果
    res.json(result);
  } catch (error) {
    // 如果出错，交给错误处理中间件
    next(error);
  }
});

/**
 * GET /api/v1/creator-works
 * 查询我的作品
 */
router.get('/', requireAuth, async (req, res, next) => {
  try {
    const list = await listMyWorks(req.user!);
    res.json(list);
  } catch (error) {
    next(error);
  }
});

export default router;
```

**重点理解**：
1. **requireAuth**：必须登录才能调用
2. **req.user**：当前登录的用户信息
3. **async/await**：异步操作，等待完成后才继续
4. **try/catch**：捕获错误，避免程序崩溃

```vue
<script setup lang="ts">
/**
 * 为什么用 setup？
 * - Vue 3 的组合式 API
 * - 代码更简洁，逻辑更清晰
 */

import { ref, onMounted } from 'vue';
import { http } from '@/utils/http';  // 封装的 HTTP 请求工具
import { ElMessage } from 'element-plus';

// ref 是什么？
// - Vue 3 的响应式数据
// - 数据变化时，页面会自动更新

const keywords = ref([]);  // 我的关键词列表
const works = ref([]);     // 我的作品列表
const form = ref({         // 表单数据
  title: '',
  url: '',
  platform: '',
  keyword: '',
  publishedAt: '',
  viewCount: 0,
  likeCount: 0,
  shareCount: 0
});

/**
 * 加载我的关键词
 * 
 * 为什么要加载？
 * - 只能选择已绑定的关键词
 * - 从后端 API 获取
 */
async function loadKeywords() {
  try {
    // http.get 是什么？
    // - 发送 GET 请求到后端 API
    // - 返回 JSON 数据
    keywords.value = await http.get('/api/v1/keyword-bindings');
  } catch (error) {
    ElMessage.error('加载关键词失败');
  }
}

/**
 * 加载我的作品
 */
async function loadWorks() {
  try {
    works.value = await http.get('/api/v1/creator-works');
  } catch (error) {
    ElMessage.error('加载作品失败');
  }
}

/**
 * 提交作品
 */
async function submit() {
  try {
    // 发送 POST 请求
    await http.post('/api/v1/creator-works', form.value);
    
    // 提示成功
    ElMessage.success('提交成功');
    
    // 重置表单
    reset();
    
    // 重新加载作品列表
    loadWorks();
  } catch (error) {
    ElMessage.error('提交失败');
  }
}

/**
 * 重置表单
 */
function reset() {
  form.value = {
    title: '',
    url: '',
    platform: '',
    keyword: '',
    publishedAt: '',
    viewCount: 0,
    likeCount: 0,
    shareCount: 0
  };
}

/**
 * onMounted 是什么？
 * - 页面加载完成后自动执行
 * - 用于初始化数据
 */
onMounted(() => {
  loadKeywords();
  loadWorks();
});
</script>

}
```

## 第六章：常见问题解答

### Q1：为什么要分 P0/P1/P2？

**A**：因为项目已返工 3 次，需要降低风险

- **P0（9天）**：只做核心链路，快速上线验证
- **P1（按需）**：重要功能，P0 稳定后再做
- **P2（可选）**：锦上添花，可能不做

**好处**：
- 如果需求又变了，只影响 P0（9 天成本）
- 不会浪费 P1/P2 的开发时间

---

### Q2：为什么要复用定价规则？

**A**：因为系统已经有完整的定价体系

- ✅ 不需要重新写定价逻辑
- ✅ 定价规则在数据库配置，改配置不改代码
- ✅ 归因算法和定价规则独立演进

**对比**：
```
如果不复用：
  归因引擎 + 定价逻辑 + 团长抽成 = 10 天

复用后：
  归因引擎（对接现有） = 7 天
  
节省 3 天！
```
