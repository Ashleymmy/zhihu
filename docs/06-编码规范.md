> 带「建议」的是倾向性约定，有更好的理由可以偏离。

## 一、命名规范

### 文件命名

| 类型 | 规则 | 示例 | 反例 |
| --- | --- | --- | --- |
| Vue 页面组件 | 大驼峰 + `View` 后缀 | `PlanCreateView.vue` | `plan-create.vue` |
| Vue 可复用组件 | 大驼峰 | `ChannelSelect.vue` | `channelSelect.vue` |
| Vue 布局组件 | 大驼峰 + `Layout` 后缀 | `DefaultLayout.vue` | `layout.vue` |
| 服务层 | 小写 + `.service.ts` | `plan.service.ts` | `planApi.ts` |
| 状态层 | 小写 + `.store.ts` | `channel.store.ts` | `channelStore.ts` |
| 业务组合层 | `use` + 大驼峰 | `useBatchUpload.ts` | `batch-upload.ts` |
| 工具函数 | 小写连字符 | `signature.ts`、`sign-rules.ts` | `Signature.ts` |
| 类型定义 | 小写连字符 | `api-common.ts` | `ApiCommon.ts` |
| 测试文件 | 被测文件名 + `.spec.ts` | `signature.spec.ts` | `signature.test.ts` |

### 变量与函数命名

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 变量 | 小驼峰 | `channelId`、`planList` |
| 常量 | 大写下划线 | `MAX_IMAGE_SIZE_BYTES`、`POLL_INTERVAL_MS` |
| 函数 | 小驼峰，动词开头 | `buildSignature`、`fetchChannels` |
| 布尔值 | `is` / `has` / `can` / `should` 开头 | `isValidCombo`、`hasNextPage`、`canUpdate` |
| 类 | 大驼峰 | `ApiError` |
| 枚举 | 大驼峰，成员大驼峰 | `CompositionType.ImageText` |
| 类型/接口 | 大驼峰 | `CreatePlanRequest` |
| Pinia store | `use` + 大驼峰 + `Store` | `useChannelStore` |
| Composable | `use` + 大驼峰 | `useApiRequest` |

### 服务层函数动词约定

**必须**使用统一动词，保持可预测性：

| 动词 | 用于 | 示例 |
| --- | --- | --- |
| `get` | 获取单个资源 | `getPlanDetail`、`getBatchTaskResult` |
| `list` 或 `getXxxList` | 获取列表 | `listCompositions` |
| `create` | 创建 | `createPlan`、`createCompositionV2` |
| `update` | 更新 | `updateCompositionV2` |
| `upload` | 上传文件 | `uploadFile` |
| `submit` | 提交不可撤销操作 | `submitRiskWord` |

批量操作**必须**加 `Batch` 后缀：`createPlansBatch`、`createCompositionsBatchV2`。

### 接口字段命名：保持后端原样

⚠️ **这是本项目的重要约定。**

知乎接口用的是 `snake_case`（下划线），我们**不转成 camelCase**：

```typescript
// ✅ 正确：与接口字段一字不差
export interface CreatePlanRequest {
  task_id: string
  channel_id: string
  content_url: string
  popularize_type: number
  keyword: string
  second_channel_id?: string
}

// ❌ 错误：转成驼峰会带来三个问题
export interface CreatePlanRequest {
  taskId: string
  channelId: string
}
```

**为什么不转驼峰？**

1. **签名依赖字段名**。签名是按 key 字典排序拼接的，字段名改了签名就错了。
   如果转驼峰，就要在发请求前再转回来，多一层转换多一处出 bug 的地方
2. **排查问题时可直接对照**。看到报错说 `content_url` 无效，代码里搜 `content_url` 就能找到
3. **对照 03 文档零心智负担**。文档写 `composition_sub_type`，代码就是 `composition_sub_type`

**唯一例外**：我们自己定义的、不发给接口的变量，用小驼峰。

```typescript
// 服务层函数参数是我们自己的抽象，可以用驼峰
export function createPlansBatch(params: {
  file: File
  taskId: string        // ✅ 我们自己的参数，用驼峰
  channelId: string
}) {
  const formData = new FormData()
  formData.append('task_id', params.taskId)     // 发出去时用下划线
  formData.append('channel_id', params.channelId)
}
```

## 二、TypeScript 规范

### 禁止 `any`

```typescript
// ❌ 禁止
function parse(data: any) { return data.foo }

// ✅ 用 unknown + 类型守卫
function parse(data: unknown) {
  if (typeof data === 'object' && data !== null && 'foo' in data) {
    return data.foo
  }
  return undefined
}

// ✅ 或用泛型
function parse<T>(data: T): T { return data }
```

ESLint 已开启 `@typescript-eslint/no-explicit-any` 为 `error`。
确实无法避免时，写 `// eslint-disable-next-line` 并**注明原因**。

### 类型定义放 `types/`，不内联

```typescript
// ❌ 不好：内联在服务层，别的地方要用就得重复定义
// services/plan.service.ts
export function createPlan(payload: {
  task_id: string
  channel_id: string
}) { }

// ✅ 好：定义在 types/，多层可共享
// types/plan.ts
export interface CreatePlanRequest {
  task_id: string
  channel_id: string
}

// services/plan.service.ts
import type { CreatePlanRequest } from '@/types/plan'
export function createPlan(payload: CreatePlanRequest) { }
```

### 用 `import type` 导入纯类型

```typescript
// ✅ 明确标注是类型导入，构建时会被完全擦除
import type { CreatePlanRequest } from '@/types/plan'
import type { AxiosInstance } from 'axios'

// 混合导入时分开写
import { defineStore } from 'pinia'
import type { Store } from 'pinia'
```

### 常量对象用 `as const`

```typescript
// ✅ as const 让类型收窄为字面量联合类型
export const MEDIA_TYPES = ['KOC抖音', 'KOC小红书'] as const
export type MediaType = typeof MEDIA_TYPES[number]
// MediaType = 'KOC抖音' | 'KOC小红书'

// ❌ 不加 as const，类型是宽泛的 string[]
export const MEDIA_TYPES = ['KOC抖音', 'KOC小红书']
```

### 枚举：数字用 `enum`，字符串用 `as const`

```typescript
// ✅ 数字枚举用 enum，因为接口传的是数字
export enum CompositionType {
  Other = 0,
  ImageText = 1,
  Video = 2,
}

// ✅ 字符串集合用 as const，比 string enum 更轻量
export const MEDIA_TYPES = ['KOC抖音', 'KOC快手'] as const
export type MediaType = typeof MEDIA_TYPES[number]
```

### 可选字段与可能为 null 的字段要区分

```typescript
export interface PopularizeTaskResponse {
  /** 可选：字段可能不存在 */
  is_first?: boolean

  /** 可为 null：字段一定存在，但值可能是 null */
  data: PopularizeTask[] | null
}
```

03 文档明确指出 § 7.1 的 `data` 无数据时返回 `null`，这类情况**必须**在类型上体现出来，
让 TypeScript 强制你做空值处理。

### 函数返回类型：公共 API 必须显式标注

```typescript
// ✅ 导出的函数必须写返回类型，这是给调用方看的契约
export function buildSignature(
  params: Record<string, unknown>,
  secretKey: string,
): string {
  // ...
}

// 内部小函数可以省略，让 TS 推断
function sleep(ms: number) {
  return new Promise((resolve) => setTimeout(resolve, ms))
}
```

## 三、Vue 组件规范

### 必须用 `<script setup lang="ts">`

```vue
<script setup lang="ts">
// ✅ 唯一允许的写法
</script>
```

不使用 Options API，不使用 `defineComponent`。

### 块顺序：script → template → style

```vue
<script setup lang="ts">
// 1. 逻辑
</script>

<template>
  <!-- 2. 模板 -->
</template>

<style scoped>
/* 3. 样式 */
</style>
```

理由：读代码时先看逻辑再看结构，符合理解顺序。

### `<script setup>` 内部顺序

```vue
<script setup lang="ts">
/**
 * 1. 文件头注释：这个组件是干什么的、对应哪个接口、哪个文档章节
 */

// 2. 类型导入
import type { CreatePlanRequest } from '@/types/plan'

// 3. 框架导入
import { ref, reactive, computed, onMounted } from 'vue'

// 4. 第三方库导入
import type { FormInstance, FormRules } from 'element-plus'

// 5. 项目内导入（按层级从下到上）
import { createPlan } from '@/services/plan.service'
import { useApiRequest } from '@/composables/useApiRequest'
import ChannelSelect from '@/components/business/ChannelSelect.vue'

// 6. defineProps / defineEmits
const props = defineProps<{ planId?: string }>()
const emit = defineEmits<{ success: [planId: string] }>()

// 7. 常量
const POPULARIZE_TYPE_KOC_SEARCH = 0

// 8. 响应式状态
const formRef = ref<FormInstance>()
const form = reactive<CreatePlanRequest>({ /* ... */ })

// 9. 计算属性
const canSubmit = computed(() => !!form.task_id && !!form.channel_id)

// 10. composable 调用
const { data, loading, run } = useApiRequest(createPlan)

// 11. 方法
async function handleSubmit() { /* ... */ }

// 12. 生命周期
onMounted(() => { /* ... */ })
</script>
```

### Props 用类型声明，不用运行时声明

```typescript
// ✅ 好：类型声明，TS 友好
const props = defineProps<{
  channelId: string
  disabled?: boolean
}>()

// ✅ 需要默认值时
const props = withDefaults(defineProps<{
  channelId: string
  disabled?: boolean
}>(), {
  disabled: false,
})

// ❌ 不好：运行时声明，类型信息弱
const props = defineProps({
  channelId: { type: String, required: true },
})
```

### 单文件 300 行上限

超过 300 行**必须**拆分。拆分方向：

1. 逻辑太多 → 抽到 `composables/`
2. 模板太长 → 抽子组件到 `components/`
3. 一个页面做太多事 → 拆成多个路由页面

### 组件通信：props down, events up

```vue
<!-- 父组件 -->
<ChannelSelect v-model="form.channel_id" @change="handleChannelChange" />
```

不要用 `provide/inject` 传业务数据（除了主题、国际化这类全局配置）。
跨组件共享数据用 Pinia store。

### 模板中避免复杂表达式

```vue
<!-- ❌ 不好：逻辑写在模板里，没法测试 -->
<span>{{ list.filter(i => i.status === 1).length > 0 ? '有待审核' : '无' }}</span>

<!-- ✅ 好：抽成 computed -->
<span>{{ pendingLabel }}</span>
```

```typescript
const pendingLabel = computed(() =>
  list.value.some((i) => i.status === AuditStatusResponse.Reviewing) ? '有待审核' : '无',
)
```

## 四、样式规范

### 必须加 `scoped`

```vue
<style scoped>
/* 避免样式泄漏影响其他组件 */
</style>
```

需要覆盖 Element Plus 内部样式时用 `:deep()`：

```vue
<style scoped>
.form-wrapper :deep(.el-form-item__label) {
  font-weight: 500;
}
</style>
```

### 用 CSS 变量，不硬编码颜色和间距

```css
/* src/styles/variables.css */
:root {
  /* 间距 */
  --space-xs: 4px;
  --space-sm: 8px;
  --space-md: 16px;
  --space-lg: 24px;
  --space-xl: 32px;

  /* 语义色 */
  --color-danger: #f56c6c;
  --color-warning: #e6a23c;
  --color-success: #67c23a;
  --color-text-primary: #303133;
  --color-text-secondary: #909399;
  --color-border: #dcdfe6;

  /* 圆角 */
  --radius-sm: 4px;
  --radius-md: 8px;
}
```

```vue
<style scoped>
/* ✅ 好 */
.card {
  padding: var(--space-md);
  border: 1px solid var(--color-border);
  border-radius: var(--radius-md);
}

/* ❌ 不好：数字散落各处，改设计要全局搜 */
.card {
  padding: 16px;
  border: 1px solid #dcdfe6;
}
</style>
```

### 类名用 kebab-case

```vue
<template>
  <div class="plan-create-form">
    <div class="plan-create-form__header">
```

建议用 BEM 风格的双下划线表示子元素，避免嵌套过深的选择器。

### 无障碍要求

| 要求 | 做法 |
| --- | --- |
| 图片必须有 `alt` | `<img :src="url" alt="剧目头图">` |
| 图标按钮必须有 `aria-label` | `<ElButton aria-label="删除">` |
| 表单必须有关联 label | Element Plus 的 `ElFormItem label` 已处理 |
| 颜色不能是唯一信息载体 | 状态标签除了颜色还要有文字 |
| 键盘可达 | 不要用 `div` 做按钮，用 `<button>` 或 Element 组件 |

## 五、注释规范

### 文件头注释

**必须**：服务层函数、composable、页面组件。

```typescript
/**
 * 单个创建推广计划
 *
 * 接口：POST /alliance/api/popularize_plan
 * 文档：docs/03-接口文档.md § 3.1
 *
 * 注意：second_channel_id 为可选参数，且不参与签名。
 */
export function createPlan(payload: CreatePlanRequest) { }
```

三要素：**做什么**、**接口路径**、**文档章节号**。有坑再加「注意」。

### 工具函数注释

**必须**包含 `@example`：

```typescript
/**
 * 把对象拼成 key=value&key=value 形式的字符串。
 *
 * 注意：知乎签名要求值不做 URL 编码，中文原样拼接。
 * 这一点和大多数签名算法不同，很容易踩坑。
 *
 * @example
 * buildKvString({ a: 1, b: '中文' })  // => 'a=1&b=中文'
 */
export function buildKvString(obj: Record<string, unknown>): string { }
```

### 注释写「为什么」，不写「是什么」

```typescript
// ❌ 无用注释：代码本身就能看出来
// 把 loading 设为 true
loading.value = true

// ✅ 有用注释：解释了不明显的原因
// 必须放在 finally，否则出错时 loading 会永远为 true，按钮卡在转圈状态
finally {
  loading.value = false
}
```

### 用统一标记标注特殊情况

| 标记 | 用途 | 示例 |
| --- | --- | --- |
| `⚠️` | 容易踩的坑 | `⚠️ 参数顺序：消息在前，密钥在后` |
| `🔴` | 严重风险 | `🔴 返回文件流，必须设置 responseType: 'blob'` |
| `TODO` | 待完成，**必须**关联 Issue 号 | `// TODO(#42): 拿到模板后补列校验` |
| `FIXME` | 已知缺陷 | `// FIXME(#43): status 枚举待联调确认` |

`TODO` 和 `FIXME` **必须**带 Issue 号，否则永远不会被处理。

### 不要留注释掉的死代码

```typescript
// ❌ 禁止
// const oldSignature = md5(kvStr)
// return oldSignature
return hmacSha256Hex(md5Str, secretKey)
```

需要历史版本就查 Git，不要留在代码里。

## 七、Git 协作规范

### 分支模型

```
main                    生产分支，受保护，只接受 PR 合入
  │
  ├── develop           开发主干（可选，团队小可省略）
  │
  ├── feat/plan-create        新功能
  ├── fix/signature-timestamp 修 Bug
  ├── docs/api-update         文档
  ├── refactor/http-client    重构
  ├── test/signature-cases    补测试
  └── chore/deps-upgrade      杂务
```

**约束**：

- **禁止直接 push 到 `main`**
- 分支名用小写连字符，`type/简短描述`
- 一个分支只做一件事，别把重构和新功能混在一个 PR

### Commit Message 规范

采用 Conventional Commits：

```
<type>(<scope>): <subject>

<body>

<footer>
```

**type 取值：**

| type | 用于 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 Bug |
| `docs` | 只改文档 |
| `style` | 格式调整，不影响逻辑 |
| `refactor` | 重构，不改功能 |
| `test` | 加测试或改测试 |
| `chore` | 构建、依赖、工具配置 |
| `perf` | 性能优化 |

**scope 取值（对应架构分层或业务模块）：**

```
plan  composition  channel  report  risk  intercept  content  audio  comic
sign  http  store  utils  docs
```

**示例：**

```
feat(sign): 实现签名六步法与黄金用例测试

按 docs/04-签名机制.md 实现 buildSignature，
用官方 PDF § 1.2 示例数据验证，MD5 与签名输出一致。

同时提供 buildSignatureWithTrace 用于排错时打印中间值。

Refs: #12
```

```
fix(http): 修复 offset/limit 误参与签名导致分页接口失败

原因：sign-rules.ts 的排除清单漏了分页参数。
按 docs/03-接口文档.md 补充 offset 与 limit。

Fixes: #34
```

**约束：**

- subject 用**中文**，不超过 50 字，不加句号
- subject 用**祈使句**（「修复 XX」而不是「修复了 XX」）
- body 说明**为什么**这么改，不是重复改了什么
- 破坏性变更在 footer 写 `BREAKING CHANGE:`

### 提交前钩子

用 husky + lint-staged，把检查前置：

```json
{
  "lint-staged": {
    "*.{ts,vue}": ["eslint --fix", "prettier --write"],
    "*.{json,md,css}": ["prettier --write"]
  }
}
```

```bash
# .husky/pre-commit
npx lint-staged

# .husky/pre-push
npm run typecheck && npm run test
```

> `pre-push` 跑测试而不是 `pre-commit`，因为测试较慢，
> 每次 commit 都跑会打断心流。

### PR 规范

**PR 标题**：与 commit subject 同规范，不超过 70 字。

**PR 描述模板**（建议放到 `.github/pull_request_template.md`）：

```markdown
## 改了什么

（一两句话说清）

## 为什么这么改

（背景、原因，关联的需求或 Issue）

## 怎么验证的

- [ ] `npm run verify` 通过
- [ ] 手动测试了 XX 场景
- [ ] 联调了 XX 接口（如涉及）

## 影响范围

（涉及哪些层、哪些模块，是否有破坏性变更）

## 相关文档

（是否需要同步更新 docs/？已更新哪些？）
```

**PR 约束：**

- 单个 PR 改动不超过 **500 行**（不含自动生成文件）
- 超了就拆成多个 PR，方便 Review
- 必须至少 **1 人 Approve** 才能合入
- CI 必须全绿

### 什么不能提交

`.gitignore` 必须包含：

```
# 依赖
node_modules/

# 构建产物
dist/
coverage/

# 环境变量 ★ 重要
.env.local
.env.*.local

# 编辑器
.DS_Store
*.swp
.idea/

# 日志
*.log
npm-debug.log*
```

**永远不要提交：**

| 项 | 原因 |
| --- | --- |
| `.env.local` | 含 `secret_key` |
| 任何含真实凭证的文件 | 安全事故 |
| `node_modules/` | 体积巨大 |
| `dist/` | 构建产物应由 CI 生成 |
| 大于 1 MB 的二进制文件 | 撑爆仓库（Excel 模板除外，那是必要资产） |

**提交前自查：**

```bash
# 看清楚将要提交什么
git diff --cached --stat

# 检查是否误加了敏感文件
git diff --cached --name-only | grep -iE "\.env|secret|credential"
```

## 八、Code Review 清单

Reviewer 对照这份清单看 PR。分四类，**架构与安全是硬拦项**。

### 🔴 安全（发现即打回）

- [ ] 没有硬编码的 `secret_key` 或 `access_token`
- [ ] 没有提交 `.env.local` 或任何含凭证的文件
- [ ] 新增日志不输出敏感字段（或已脱敏）
- [ ] 没有把签名逻辑写到视图层
- [ ] 新增的网络请求走 `infra/http`，不是裸 `axios` / `fetch`

### 🔴 架构（违反分层即打回）

对照 [01 文档的依赖矩阵](./01-架构设计.md#依赖矩阵)：

- [ ] 没有下层引用上层
- [ ] 工具层没有 import Vue / Pinia / Axios / Element Plus
- [ ] 服务层、基础设施层没有 `ElMessage` 等 UI 调用
- [ ] 视图层没有直接 import `infra/`
- [ ] 一个服务函数只调一个接口（多接口编排应在 composable）
- [ ] 类型定义在 `types/`，没内联在服务层
- [ ] 接口路径登记在 `constants/api-paths.ts`
- [ ] 枚举登记在 `constants/enums.ts`

### 🟡 质量

- [ ] 没有 `any`
- [ ] 没有 `console.log`
- [ ] 没有注释掉的死代码
- [ ] `TODO` / `FIXME` 都带了 Issue 号
- [ ] 有 `loading` 的地方用了 `try...finally`
- [ ] 可能为 `null` 的接口字段做了空值兜底（如 § 7.1 的 `data`）
- [ ] 单个 `.vue` 文件不超过 300 行
- [ ] 服务层函数的 JSDoc 写了接口路径和文档章节号
- [ ] 工具函数有 `@example`
- [ ] 新增函数有对应单元测试
- [ ] 修 Bug 时加了回归测试

### 🟡 业务正确性

- [ ] 参数是否与 03 文档一致（字段名、类型、必填性）
- [ ] 签名相关：该参与的参与了，不该参与的排除了
- [ ] 用的是 v2 接口，不是 v1
- [ ] 时间戳是秒级
- [ ] 分类组合校验用了 `isValidCompositionTypeCombo`
- [ ] 不可撤销操作（举报类）加了二次确认
- [ ] 批量接口带了 `X-Requested-With: openApi` header
- [ ] blob 响应设了 `responseType: 'blob'`

### 🟢 文档

- [ ] 新增/变更接口已更新 03 文档
- [ ] 架构调整已更新 01 文档
- [ ] 联调发现的差异已回填 03 文档附录 B
- [ ] 任务状态已更新 02 文档

### Review 沟通建议

给 Reviewer 的建议：

| 情况 | 怎么说 |
| --- | --- |
| 必须改 | 「这里违反了 01 文档的依赖矩阵，服务层不能 import store，建议…」（给出依据和方案） |
| 建议改 | 「这块如果抽成 computed 会更好测，你看要不要调整？」（留决定权） |
| 只是疑问 | 「这里为什么要用 shallowRef 而不是 ref？」（先问再判断） |
| 做得好 | 「这个错误处理考虑得很细，边界都覆盖了」（正反馈也要给） |

给 PR 作者的建议：

- 收到意见先理解意图，不急着辩护
- 不同意就说理由，Review 是讨论不是审判
- 改完回复「已按建议修改」并说明改法，方便 Reviewer 复查
- 争议较大的设计问题，拉个短会当面说清，不要在 PR 里长篇论战

## 附录：新人第一个 PR 的建议

第一个 PR 建议做小而完整的事，把整套流程走通：

1. 从 `main` 拉分支：`git switch -c feat/xxx`
2. 写代码，边写边跑 `npm run test:watch`
3. 提交前跑 `npm run verify`
4. 按 Conventional Commits 写 commit message
5. push 并开 PR，填完模板
6. 等 Review，改完再推
7. 合入后删除分支

推荐的第一个任务：从 02 文档阶段一里挑一个 `utils/` 的工具函数
（比如 A07 `utils/object.ts`），因为它是纯函数、好测、不依赖其他人的进度。
