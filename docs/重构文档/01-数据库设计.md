## 一、设计原则与约束

### 1.1 设计原则

| 原则 | 说明 | 实施要求 |
|------|------|---------|
| **租户与角色隔离** | 用户、MCN、项目三层范围共同约束 | 非 Admin 查询必须同时带 `user_id` 与 `project_id`，并校验 `project_members` |
| **审计追溯** | 关键操作记录完整日志，可追溯 | 订单、结算、收益调整必须有日志表 |
| **来源与账本分离** | 来源批次、来源行、规则版本、账本分录分表存储 | 原始来源不可被团长或达人读取；用户收益只读 `earnings_ledger` |
| **性能优先** | 高频查询必须有索引，避免全表扫描 | 查询响应时间 < 100ms（95 分位） |
| **幂等设计** | 相同来源或请求多次执行结果一致 | 使用非空 `dedup_key` / `source_item_key` 唯一索引；不得依赖 nullable unique |
| **不可变账本** | 已入账金额不得原地修改或删除 | 更正时追加 reversal 与 replacement 分录 |
| **软删除边界** | 主数据可软删除，财务事实不可删除 | `users`、`orders` 可软删除；来源批次、审批和账本永久保留 |

### 1.2 技术约束

- **数据库**：MySQL 8.0（InnoDB 引擎）
- **字符集**：utf8mb4，排序规则 utf8mb4_unicode_ci
- **时区**：统一使用 UTC，应用层转换为本地时间
- **主键**：使用 BIGINT UNSIGNED AUTO_INCREMENT
- **时间戳**：created_at、updated_at 使用 DATETIME(3)（毫秒精度）
- **来源与计算金额**：`unit_price`、`source_amount`、`calculated_amount` 等权威来源和计算中间值使用 `DECIMAL(18, 4)`，API 使用固定 4 位十进制字符串；严禁浮点计算
- **审批后资金金额**：应付、订单审批快照、结算、提现、退款与支付使用 `BIGINT *_amount_fen`；订单草稿仍属于来源/计算层，API 的最终值使用 JSON 安全整数并显式带 `Fen` 后缀
- **舍入审计**：从 `DECIMAL(18, 4)` 进入整数分只允许 `HALF_UP`，同时保存精确金额、`*_amount_fen`、`rounding_mode`、`rounding_delta`、规则版本与操作者
- **命名规范**：snake_case，表名复数形式

## 三、核心表设计

### 3.1 用户与权限域

以下按业务阅读顺序展示，代码块不是可直接拼接执行的单一脚本。`users.mcn_account_id` 与 `mcn_accounts.owner_user_id` 构成有意的业务双向关联，正式 migration 必须先建立无循环外键的两张表，再用 `ALTER TABLE` 添加约束；禁止依赖关闭 `FOREIGN_KEY_CHECKS` 绕过顺序。

#### users - 用户表

**用途**：存储 Admin、团长、达人的账户信息

```sql
CREATE TABLE users (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY COMMENT '用户 ID',
  username VARCHAR(50) NOT NULL UNIQUE COMMENT '用户名（登录用）',
  email VARCHAR(100) NOT NULL UNIQUE COMMENT '邮箱',
  phone VARCHAR(20) DEFAULT NULL COMMENT '手机号',
  password_hash VARCHAR(255) NOT NULL COMMENT 'bcrypt 哈希密码',
  role_id BIGINT UNSIGNED NOT NULL COMMENT '角色 ID（外键 roles.id）',
  
  -- 基础信息
  nickname VARCHAR(50) DEFAULT NULL COMMENT '昵称',
  avatar_url VARCHAR(255) DEFAULT NULL COMMENT '头像 URL',
  real_name VARCHAR(50) DEFAULT NULL COMMENT '真实姓名',
  id_card_ciphertext VARBINARY(512) DEFAULT NULL COMMENT '身份证号 AES-256-GCM 密文',
  id_card_iv BINARY(12) DEFAULT NULL COMMENT '身份证号随机 IV',
  id_card_auth_tag BINARY(16) DEFAULT NULL COMMENT '身份证号认证标签',
  id_card_key_version SMALLINT UNSIGNED DEFAULT NULL COMMENT '身份证号密钥版本',
  
  -- 业务字段
  parent_user_id BIGINT UNSIGNED DEFAULT NULL COMMENT '上级用户 ID（达人归属团长、团长归属 Admin）',
  mcn_account_id BIGINT UNSIGNED DEFAULT NULL COMMENT 'MCN 账户 ID',
  zhihu_channel_id VARCHAR(50) DEFAULT NULL COMMENT '知乎渠道 ID（团长/达人专用）',
  
  -- 状态字段
  status ENUM('active', 'inactive', 'banned') DEFAULT 'active' COMMENT '账户状态',
  email_verified_at DATETIME(3) DEFAULT NULL COMMENT '邮箱验证时间',
  last_login_at DATETIME(3) DEFAULT NULL COMMENT '最后登录时间',
  last_login_ip VARCHAR(45) DEFAULT NULL COMMENT '最后登录 IP',
  
  -- 审计字段
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  deleted_at DATETIME(3) DEFAULT NULL COMMENT '软删除时间',
  
  INDEX idx_role_id (role_id),
  INDEX idx_parent_user_id (parent_user_id),
  INDEX idx_mcn_account_id (mcn_account_id),
  INDEX idx_status (status),
  INDEX idx_deleted_at (deleted_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户表';
```

#### project_members - 项目成员表

```sql
CREATE TABLE project_members (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  project_id BIGINT UNSIGNED NOT NULL COMMENT '项目 ID',
  user_id BIGINT UNSIGNED NOT NULL COMMENT '用户 ID',
  member_role ENUM('owner', 'admin', 'member', 'viewer') NOT NULL DEFAULT 'member' COMMENT '项目内角色',
  
  joined_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '加入时间',
  left_at DATETIME(3) DEFAULT NULL COMMENT '离开时间',
  
  UNIQUE KEY uk_project_user (project_id, user_id),
  FOREIGN KEY fk_project (project_id) REFERENCES projects(id) ON DELETE CASCADE,
  FOREIGN KEY fk_user (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='项目成员表';
```

> **隔离约束**：业务 service 不得只凭角色或 `parent_user_id` 推导项目范围。每次读取、导出、汇总和队列任务都必须先解析 `project_members(project_id, user_id)`，然后在最终 SQL 中同时绑定 `project_id` 与可见 `user_id`；无成员记录时 fail closed。

#### mcn_accounts - MCN 账户表（目标 DDL）

```sql
CREATE TABLE mcn_accounts (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  account_key VARCHAR(64) NOT NULL COMMENT '稳定业务键',
  account_name VARCHAR(128) NOT NULL COMMENT 'MCN 名称',
  owner_user_id BIGINT UNSIGNED NOT NULL COMMENT '账户负责人',
  status ENUM('active', 'suspended', 'archived') NOT NULL DEFAULT 'active',
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_mcn_accounts_key (account_key),
  KEY idx_mcn_accounts_owner (owner_user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='MCN 账户';

-- 两表均创建成功后再添加循环关联；失败时整次 migration 保持未完成。
ALTER TABLE users
  ADD CONSTRAINT fk_users_mcn_account
  FOREIGN KEY (mcn_account_id) REFERENCES mcn_accounts(id) ON DELETE RESTRICT;

ALTER TABLE mcn_accounts
  ADD CONSTRAINT fk_mcn_accounts_owner
  FOREIGN KEY (owner_user_id) REFERENCES users(id) ON DELETE RESTRICT;
```

fresh migration 的顺序固定为：`roles/permissions` → `users`（暂不含 MCN FK）→ `mcn_accounts`（暂不含 owner FK）→ 上述两个 `ALTER TABLE` → `projects` → `project_members` → 其余业务表。首个租户的数据引导先创建 `mcn_account_id=NULL` 的 owner user，再创建 MCN，最后回填 user 的 `mcn_account_id`；全程不得写入悬空 ID。

MCN 与项目是多对多业务关系时应新增显式关联表，不得把 `mcn_account_id` 当作项目权限；项目可见性仍以 `project_members` 为准。

#### token_sessions - Refresh Token 会话表（目标 DDL）

```sql
CREATE TABLE token_sessions (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

订单草稿只保存来源字段与服务端派生的 `DECIMAL(18, 4)`：客户端可提交每项 `raw_amount/unit_price` 与订单级 `discount_amount`，但 `order_items.calculated_amount`、`orders.original_amount`、`orders.calculated_amount` 均由服务端精确十进制计算。未知的 `calculatedAmount`、`*AmountFen`、`roundingMode` 或 `roundingDelta` 请求字段必须拒绝，不能静默忽略。

`draft → pending` 只提交并锁定精确草稿，不生成整数分。Admin 执行 `pending → active` 是订单金额审批边界：事务内从明细重算并核对 `calculated_amount`，再生成 `payable_amount_fen = HALF_UP(calculated_amount × 100)`，验证 JSON 安全整数范围，并原子记录 `rounding_mode`、`rounding_delta`、审批人、时间、`request_id` 与 calculation snapshot。支付和退款只能消费该审批快照，分别写 `payment_amount_fen` 与 `refunded_amount_fen`；不得反向覆盖草稿来源或精确计算值。

`uk_orders_amount_approval_request` 允许多个未审批草稿为 `NULL`，但上述 CHECK 强制已审批订单使用非空请求 ID，因此它只在真正的审批边界承担幂等唯一性，不依赖 nullable unique 去重草稿。

```

创建提现工单时必须冻结审批策略版本和级数；默认 Level 1 为业务复核、Level 2 为财务批准。审批事务锁定工单并校验 `approval_level = current_approval_level + 1`、策略版本、乐观锁版本、项目成员关系及该级权限；每次只能追加当前级的一条事实。申请人以及该工单所消费账本分录关联的任一 `source_batches.uploaded_by` 均不得审批，同一审批人不得占两个级别。最后一级成功后才把状态快照更新为 `approved`；任一级拒绝后，修改必须新建工单或业务修订版本并重新走完整审批，禁止覆盖旧事实。

当前目标对象尚未定义“提现金额 → `earnings_ledger` 分录”的不可变分摊关系；在新增该关联及其到 `source_batches` 的可追溯查询前，无法机械证明“来源批次上传人不得审批”。`D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 任一未通过时，不得启用生产提现审批或打款。该分摊对象、余额占用/释放规则及复合外键属于 `A-001-SPEC` 的目标规格；未来 migration、运行时一致性和 route coverage 属于 `A-001-CONFORMANCE`/后续迁移验收，不是规格冻结前提。

删除只允许申请人对尚无任何审批、支付或退款事实的 `draft/pending_approval` 工单执行软删除。该检查与 `deleted_at` 更新必须在同一事务中完成；一旦存在关联事实即 fail closed。Admin 也没有物理删除财务事实的业务能力，break-glass DBA 仅用于经双人审批和审计的紧急处置。

## 四、数据中继核心逻辑

### 4.1 启动 Gate `D-001` 与来源适配器

官方 OpenAPI V1.4.17 的 `/data_report/real_time_data` 是有延迟的运营指标接口，**不是结算依据**；该版本没有披露原始单价或收益结算 API。因此不得把 `daily_metrics.earning`、点击量、转化量或推算单价直接写入用户余额。

`D-001-DECISION` 的通过条件（用户书面确认来源、字段、周期、币种、修订与冲正规则均须具备）：

1. 业务负责人书面确认结算权威来源、字段口径、周期、币种、修订与冲正规则。

`D-001-DECISION` 未关闭前，财务范围只允许 Mock、协议设计与非财务工作；即使隔离沙箱也不得实施实际 adapter、匿名样例导入、审批、中继或对账。仅在该 Gate 关闭后，以下实际工程才可在隔离沙箱形成 READINESS 证据，且不授权生产资金链；生产结算、余额、提现和打款仍须同时满足 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6。

`D-001-READINESS` 的通过条件（实际 adapter、匿名样例、审批、幂等、中继、冲正和对账均须具备）：

1. 首个实际 adapter 固定为 Admin 上传、校验并审批的匿名 XLSX 结算批次，并经版本化两级中继；批次审批人与上传人必须分离。
2. 至少完成匿名样例导入、重复文件、重复来源行、跨项目引用、金额汇总、冲正、幂等重放、审计和对账测试。

**生产资金放行（不属于 `D-001-READINESS` 通过条件）**：仅当 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 均通过，生产结算生成、余额展示、提现与打款功能才可启用；任一未通过时全部保持关闭。

未来如取得官方结算 API，只新增版本化 `official_api` adapter，输出同一 `earning_source_items` 规范模型；不得绕过批次审批和账本入账流程。

写入规则：

- `source_batches.status='approved'` 才能生成分录；批次整体在一个 posting job 中幂等处理。
- 团长和达人分别生成独立分录；达人分录通过 `parent_entry_id` 关联团长分录，不共享可变金额列。

- 数据库账户应撤销该表的业务 `UPDATE` / `DELETE` 权限；只有迁移/DBA 紧急流程例外并强制审计。

#### 查询模型与隔离边界

不创建声称“自动按当前用户过滤”的团长/达人普通视图；MySQL 视图不知道请求用户身份，只按角色过滤会造成横向越权。

所有应用查询必须满足：

```sql
SELECT id, posted_at, amount, currency, entry_kind
FROM earnings_ledger
WHERE project_id = :authorized_project_id
  AND beneficiary_user_id IN (:authorized_user_ids)
ORDER BY posted_at DESC, id DESC;
```

`:authorized_user_ids` 必须由当前认证用户、`project_members` 和已验证的上下级关系在服务端计算，客户端传入的 `user_id` 只能作为范围内筛选条件。团长/达人响应不得 join 或返回 `earning_source_items.raw_payload`、`source_amount` 或来源单价。

### 4.2 数据中继计算流程

```
Admin 上传 XLSX / 未来 official_api adapter
  → 创建 source_batches(uploaded) 与不可变 earning_source_items
  → schema、合计、重复键、项目归属校验
  → 独立 Admin 审批 source_batches(approved)
  → posting job 按 project_id、earning_type、用户范围和生效时间选择 published relay_configs 版本
  → 受限 AST 解释器计算并按 DECIMAL 规则舍入
  → 幂等追加 leader earnings_ledger
  → 幂等追加 creator earnings_ledger，并关联 parent_entry_id
  → 对账通过后 source_batches(posted)
  → API 查询再次绑定 project_id + authorized_user_ids
```

任一步失败都不得把批次部分标记为 `posted`。重试复用同一 `external_batch_key`、`source_item_key` 和 `dedup_key`，已存在分录返回幂等成功。来源或规则错误进入“冲正 + 替换”流程，不修改历史行。

## 五、索引设计

### 5.1 索引设计原则

1. **主键索引**：所有表自动创建主键索引（BIGINT UNSIGNED AUTO_INCREMENT）
2. **唯一索引**：业务唯一标识字段（如 order_no、zhihu_plan_id）
3. **外键索引**：外键字段自动创建索引
4. **查询索引**：高频查询条件字段（如 user_id、status、created_at）
5. **联合索引**：多字段联合查询场景（遵循最左前缀原则）

### 5.2 关键索引清单

| 表名 | 索引名 | 字段 | 类型 | 用途 |
|------|--------|------|------|------|
| users | idx_role_id | role_id | 普通 | 按角色查询用户 |
| users | idx_parent_user_id | parent_user_id | 普通 | 查询团长下的达人 |
| orders | idx_buyer_user_id | buyer_user_id | 普通 | 查询用户订单 |
| orders | idx_status | status | 普通 | 查询特定状态订单 |
| settlements | idx_user_id | user_id | 普通 | 查询用户结算单 |
| settlements | idx_period | period_start, period_end | 联合 | 按周期查询结算单 |
| source_batches | uk_source_batches_external | project_id, adapter_key, external_batch_key | 唯一联合 | 批次幂等 |
| earning_source_items | uk_earning_source_items_key | batch_id, source_item_key | 唯一联合 | 来源行幂等，不受 NULL 语义影响 |
| relay_configs | idx_relay_configs_match | project_id, target_role, earning_type, status, effective_from | 联合 | 规则匹配 |
| earnings_ledger | uk_earnings_ledger_dedup | dedup_key | 唯一 | 分录幂等 |
| earnings_ledger | idx_earnings_ledger_scope | project_id, beneficiary_user_id, posted_at, id | 联合 | 强制项目与用户范围查询 |

### 5.3 慢查询优化

**预期慢查询场景**：
1. 数据看板日期范围查询（跨月查询）
2. 收益明细导出（大批量数据）
3. 结算单生成（聚合计算）

**优化策略**：
- 数据看板：使用 Redis 缓存近 7 天数据
- 收益导出：异步任务 + 分页查询
- 结算单：提前预计算，存储在 settlements 表

## 六、数据迁移方案

### 6.1 迁移工具选择

当前 `server` 使用自研 SQL runner：`server/scripts/migrate.ts` 顺序执行 `server/migrations/NNN_name.sql`，并写入 `schema_migrations`。

复合外键必须在被引用的唯一键和父表创建完成后再建立。当前目标 DDL 的先决键审计如下；fresh/upgrade CI 必须从 `information_schema.REFERENTIAL_CONSTRAINTS` 与 `STATISTICS` 复核名称、列序和唯一性：

| 被引用键 | 依赖表 | 顺序要求 |
|----------|--------|----------|
| `project_members.uk_project_user(project_id, user_id)` | `orders`、`settlements`、`withdrawals`、`source_batches`、`relay_configs`、`earnings_ledger`、审批表 | `projects/users → project_members → 依赖表` |
| `orders.uk_orders_id_project(id, project_id)` | 后续 `refunds` / payment snapshot | `orders → 退款/支付迁移` |
| `settlements.uk_settlements_id_project(id, project_id)` | `settlement_approvals` | `settlements → settlement_approvals` |
| `withdrawals.uk_withdrawals_id_project(id, project_id)` | `withdrawal_approvals` | `withdrawals → withdrawal_approvals` |
| `source_batches.uk_source_batches_id_project(id, project_id)` | `earning_source_items` | `source_batches → earning_source_items` |
| `earning_source_items.uk_earning_source_items_id_project(id, project_id)` | `earnings_ledger` | `earning_source_items → earnings_ledger` |
| `relay_configs.uk_relay_configs_id_project(id, project_id)` | `earnings_ledger` | `relay_configs → earnings_ledger` |

任一复合 FK 找不到列序完全一致的 `PRIMARY/UNIQUE` 索引时，migration 必须失败；不得退化为无约束普通索引或临时关闭外键检查。

```bash
# 在 server 目录执行向前迁移
npm run migrate
```

**现状限制**：runner 会忽略 `*.down.sql`，项目没有可执行的 `migration:revert`；同时 MySQL DDL 可能隐式提交，不能把现有 `beginTransaction()` 当成完整原子回滚保证。上线前必须补齐以下迁移 Gate：

- 每个迁移有向前 SQL、经审核的恢复/回退步骤和数据兼容说明。
- 在空库验证全量建库，在当前生产快照副本验证增量升级。
- 对不可逆数据转换先做影子列、回填、双读校验，再切换；不得直接覆盖旧财务数据。
- 演练备份恢复并记录实际耗时；没有可执行回退路径的迁移不得进入生产窗口。
- 测试清库/重建脚本必须同时校验 `NODE_ENV=test`、数据库名 allowlist（例如 `_test` 后缀）和允许的 host，并要求显式 destructive-test 开关；任一不满足立即退出，禁止对配置中的真实库执行 `DROP`、`TRUNCATE` 或批量 `DELETE`。

### 6.2 迁移脚本示例

```sql
-- server/migrations/004_earnings_ledger_v2.sql（命名示意，尚未实现）
-- 1. 只新增 v2 表和索引，不删除 earnings / daily_metrics。
CREATE TABLE source_batches (...);
CREATE TABLE earning_source_items (...);
CREATE TABLE relay_configs (...);
CREATE TABLE earnings_ledger (...);

-- 2. 数据回填由可重入脚本执行；每批记录 checkpoint 和校验摘要。
-- 3. 应用切读后经过完整结算周期与对账，另起迁移删除废弃字段。
```

不得把上述省略号文件直接提交或执行；正式迁移必须展开完整 DDL，并由 CI 在真实 MySQL 8.0 上执行 fresh、upgrade、idempotency 和 restore drill。

### 6.3 历史数据迁移

历史迁移按以下阶段执行，任何阶段失败都停止切流：

1. 冻结源表结构快照、行数、关键金额合计和哈希；测试数据与可审计业务数据分开标识。
2. 先补 `mcn_accounts`、`project_members`、`token_sessions` 等主数据结构，再回填明确映射的数据。
3. 旧 `daily_metrics.earning` 只迁移为运营指标，禁止转换为结算来源。
4. 旧 `earnings` 在业务确认来源口径后，作为专用 `legacy_import` batch 导入；每行生成非空 `source_item_key`，并经双人审批后生成账本分录。
5. 逐项目校验来源合计 = 团长/达人分录与规则预期，且原分录 + 冲正分录净额正确。
6. 新旧读取进行影子对比；达到验收阈值后切换，旧表保持只读直至审计保留期结束。

验收证据至少包括：迁移前后行数、按 `project_id` / `user_id` 的金额合计、重复键计数、孤儿外键计数、随机样本追溯链，以及备份恢复演练输出。

### 7.2 敏感字段加密

**需要加密的字段**：

- `users.password_hash`：使用 bcrypt/Argon2id 单向哈希，不属于可逆加密。
- 身份证号、收款账号、联盟 access token / secret、回调 secret：使用 AES-256-GCM 信封加密。
- 收款账号禁止以明文列、JSON、日志、审计 detail 或错误信息落盘；查询响应只返回脱敏值。

**存储契约**：每个敏感字段独立保存 `ciphertext`、`iv`、`auth_tag`、`key_version`。二进制列最低容量为 `VARBINARY(512)`（长 secret 可用 `MEDIUMBLOB`）、`BINARY(12)`、`BINARY(16)`、`SMALLINT UNSIGNED`；不得使用可能截断密文或标签的短字符列。`iv` 每次加密随机生成且同一 key 下不可复用。

**密钥契约**：数据密钥不与数据库同库保存；通过 KMS/密钥环按 `key_version` 获取。AAD 至少绑定环境、表、主键、`project_id`、字段名和 key version，防止密文跨行替换。轮换采用“新写新版本、后台重加密、保留旧版本只解密”的流程，并记录审计。

当前 `server/migrations/001_init.sql` 的 `withdrawal_requests.pay_account` 仍是明文列，`callback_secrets` 也没有 `key_version`；它们是上线阻断项，不得因本节已有目标设计而视为修复完成。

### 7.3 SQL 注入防护

**所有查询使用参数化查询**：
```typescript
// ❌ 错误示例：字符串拼接
const username = req.body.username;
const sql = `SELECT * FROM users WHERE username = '${username}'`; // 危险！

// ✅ 正确示例：参数化查询
const username = req.body.username;
const result = await queryRunner.query(
  'SELECT * FROM users WHERE username = ?',
  [username]
);
```

### 7.4 行级权限控制

**业务层实现**（不依赖数据库 Row-Level Security）：

```typescript
interface AuthorizedScope {
  projectId: string;          // 由服务端解析并验证 project_members
  userIds: string[];          // 当前用户及其在该项目内可见的下级
}

// repository 方法只接收 AuthorizedScope，不接收裸客户端 projectId/userId。
// 最终 SQL 必须同时包含：WHERE project_id = ? AND user_id IN (...)
```

- “Admin”也必须显式选择项目并写审计；只有经过单独审批的跨项目报表可扩大范围。
- 队列任务、导出、WebSocket 推送、缓存 key 和统计聚合遵守同一范围，不能只保护 HTTP controller。
- 资源不存在与无权访问统一返回 404，避免枚举其他项目 ID。
- `relay_*` 普通视图不能提供请求级身份隔离；如将来使用数据库安全视图，必须有独立连接身份与专项验证，仍不得替代应用授权。
