## 0. 文档优先级与锁定决策

发生冲突时按以下顺序处理：

1. 用户已确认且在本节锁定的决策；
2. 经评审批准的 v2 API、数据库、安全与测试契约；
3. 本文的测试分层、环境隔离和质量门；
4. 当前代码与当前测试，仅用于盘点迁移起点；
5. v1 文档、旧示例和《文档审核报告》，仅保留历史参考价值。

以下规则已锁定，实施不得通过降低门槛、跳过或伪造结果来绕过：

- 三个前端应用必须分别完成构建、角色隔离、核心流程、响应式和回滚测试。
- 目标角色固定为 `admin | leader | creator`；迁移映射固定为 `boss -> admin`、`leader -> leader`、`member -> creator`。
- Access Token 只存运行时内存；Refresh Token 只存在于 `Secure; HttpOnly; SameSite` Cookie，且不得出现在 JSON。
- Logout 必须验证服务端撤销当前 Refresh Token 家族，不能只断言页面跳转或前端清空状态。
- 公共认证端点统一为 `/api/v1/auth/login|refresh|logout|me`。
- BFF 公开请求与响应字段统一 camelCase。来源/中间金额使用固定 4 位十进制字符串；订单激活及其他业务审批边界之后才使用 `*AmountFen` 安全整数。
- 成功响应固定为 `code: 0/message/data/meta?/requestId/timestamp`，列表固定为 `data: T[]` 加顶层 `meta`；失败响应使用非零稳定整数 `code` 与 `message/details?/requestId/timestamp`。
- 官方 upstream 的 `success/data/error` 结构只能存在于 Transport Adapter 边界及其测试，禁止透传到 BFF Consumer、公共 Mock 或 View。
- 订单 create 返回 `draft` 且无 `*AmountFen`，submit 只执行 `draft -> pending`，只有 Admin 的 `/api/v1/admin/orders/:id/activate` 执行 `pending -> active` 并生成 `payableAmountFen`。结算、提现采用可配置多级审批，默认至少“业务复核 → 财务批准”两级；两者不得复用订单 activate 的单级边界。
- 财务审批测试必须覆盖冻结的策略版本和当前级次、申请人/来源批次上传人不得自批、同一人不得占两个独立级次、重复与并发幂等、驳回、撤回，以及最后一级、`D-001-DECISION`、`D-001-READINESS`、P0-008 和 M6 任一未通过时不得打款。`D-001-DECISION` 未关闭前，财务测试只允许 Mock、协议设计与非财务范围，不能以沙箱名义实施或运行实际 adapter、匿名样例导入、审批、中继或对账；关闭后才可在隔离沙箱验证 READINESS 工程证据。
- 金额转换统一使用 `HALF_UP`，必须测试舍入边界、安全整数上限和 `roundingDelta` 审计。
- 收益状态统一为 `pending | confirmed | paid`；旧 `locked/settled` 只在兼容 Adapter 测试中出现。
- 声明为 `implemented` 的切片中，Mock 和真实服务必须通过同一份运行时 Schema Contract Test；`planned` operation 只做 `A-001-SPEC` 的 Schema/Fixture 静态验证。
- 默认使用临时 Testcontainers 数据库；外部测试库和破坏性清理必须通过双重安全门。
- 未产生可追溯测试证据的项目保持“实施中”或“阻塞”，不得标记完成。

## 一、现状基线与测试目标

### 1.1 当前测试现状

截至本文修订时，仓库声明的能力如下：

| 范围 | 当前事实 | 缺口与处理 |
|---|---|---|
| `platform/` | `test` 脚本只编译 2 个工具文件，再用 Node Test Runner 执行 2 个 `.mjs` 测试 | 仅视为迁移起点；尚未声明 Vitest、Vue Test Utils、Playwright、coverage、lint 或可访问性依赖与脚本 |
| `server/` | 声明 Vitest 2.1.8、MSW 2.7.0、Supertest 7.0.0，并有 unit/integration 脚本 | 不能据此推断 Contract、数据库隔离、完整集成或发布门已经通过 |
| Monorepo | 目标 `apps/`、`packages/` 和根 Turbo 任务尚未成为当前 `platform/` 的完成态 | 按《03-前端架构设计.md》分阶段落地，先冻结契约再迁移测试 |
| E2E | 当前目标依赖和脚本未落库 | 建立 Playwright 多项目矩阵，覆盖 3 个应用、双语和响应式 |
| 性能与安全 | 当前没有可作为发布证明的统一脚本、环境基线和报告 | 在独立环境执行并归档原始结果，不能用开发机单次请求代替 |

上表只陈述可从当前清单确认的事实。没有执行记录、报告和 CI 链接时，不得把“已声明依赖”写成“已通过测试”。

### 1.2 质量目标

- 在契约冻结阶段尽早发现 Envelope、分页、角色、状态和字段命名漂移。
- 在单元与组件层快速验证纯逻辑、页面状态和交互可访问性。
- 在集成层验证真实 Router、Middleware、数据库、Cookie 和 Token 撤销行为。
- 在 E2E 层证明各角色只能进入自己的应用、路由和数据范围。
- 在性能层证明规定数据规模与并发下的 P95、P99、错误率和 WebSocket 稳定性。
- 在迁移期间同时证明新路径正确、旧入口可兼容、回滚路径可执行。

### 1.3 测试分层

| 层级 | 主要对象 | 外部依赖 | 失败定位目标 |
|---|---|---|---|
| 静态检查 | TypeScript、ESLint、格式与依赖边界 | 无 | 编译、规范、越界 import |
| 单元测试 | 纯函数、Adapter、Store、Service、权限与金额计算 | 无或内存替身 | 单个规则 |
| 组件测试 | Vue 组件、Composable、加载/空态/错误态 | MSW 或注入 Service | 组件行为和语义 |
| Contract Test | Schema、Envelope、分页、事件和第三方 Adapter | Mock 与真实 BFF | 契约漂移 |
| 集成测试 | Express 路由、Middleware、数据库、Redis、Token 家族 | 临时容器 | 服务协作与持久化 |
| E2E | 浏览器、3 个应用、BFF、WebSocket | 完整临时环境 | 用户流程与角色边界 |
| 非功能测试 | 性能、安全、可访问性、恢复能力 | 专用环境 | 发布风险 |

单元测试数量可以最多，但不能用大量单元测试替代 Contract、真实数据库、浏览器或负载证据。

## 三、测试环境、数据与数据库安全

### 3.1 环境分级

| 环境 | 用途 | 数据策略 | 允许的写入 |
|---|---|---|---|
| 进程内 | 单元、组件、Schema | 固定 Fixture | 仅内存 |
| PR 临时环境 | Contract、集成、E2E | 每次创建并销毁 | 允许测试写入 |
| 性能专用环境 | API、WebSocket、稳定性 | 版本化大数据集 | 允许压测写入 |
| Staging | 发布候选回归与人工验收 | 脱敏合成数据 | 按测试租户隔离 |
| Production | 只读合成监测 | 专用合成账号 | 禁止破坏性测试 |

所有报告必须记录 Commit SHA、镜像摘要、依赖锁文件摘要、数据库版本、测试数据版本、区域、机器规格和开始/结束时间。跨环境结果不得直接混算。

### 3.2 数据库安全硬规则

1. 集成测试默认启动临时 Testcontainers，并在测试结束后销毁容器。
2. 无法使用临时容器而连接外部数据库时，数据库名必须以 `_test` 结尾；只设置 `NODE_ENV=test` 不构成安全证明。
3. 外部测试库若要执行表级清空、重建 Schema 等破坏性清理，必须同时设置 `ALLOW_DESTRUCTIVE_TEST_DB=true`。
4. 禁止读取当前开发或生产配置后执行 `TRUNCATE`、`DROP` 或全表删除。
5. 优先使用每测试事务回滚、唯一 Schema 或销毁临时容器；共享外部库的破坏性清理只是受控例外。
6. 启动测试前打印脱敏后的 Host、Port 和数据库名；命中生产域名、生产 Secret 或名称不合规时立即失败。

外部测试库安全门示例：

```typescript
interface DatabaseSafetyInput {
  databaseUrl: string
  ephemeralContainer: boolean
  destructiveCleanup: boolean
}

export function assertSafeTestDatabase(input: DatabaseSafetyInput): void {
  if (input.ephemeralContainer) return

  const parsed = new URL(input.databaseUrl)
  const databaseName = decodeURIComponent(parsed.pathname.replace(/^\//, ''))

  if (!databaseName.endsWith('_test')) {
    throw new Error('外部测试数据库名必须以 _test 结尾')
  }

  if (
    input.destructiveCleanup &&
    process.env.ALLOW_DESTRUCTIVE_TEST_DB !== 'true'
  ) {
    throw new Error('外部测试库破坏性清理未显式授权')
  }
}
```

该安全门在建立连接前执行，不能在清理语句之后补做检查。

### 3.3 Fixture 与 Factory

- ID 使用固定前缀加测试运行 ID，便于清理和追踪。
- `unitPrice/rawAmount/calculatedAmount` Fixture 使用固定 4 位字符串并覆盖格式边界；业务边界后的 Fixture 才使用 `*AmountFen`，并覆盖 0、安全整数上限、超范围和非整数拒绝。
- 时间由可注入 Clock 控制，覆盖 UTC、`Asia/Shanghai`、日界线和过期边界。
- 每个角色至少有“本人数据、同级他人数据、下级数据、无权限数据”集合。
- 密码、Token、知乎授权和提现账户全部使用合成值，日志断言需验证脱敏。
- 大数据集使用确定性 Seed 和版本号，失败后可复现同一分布。

## 四、单元与组件测试

### 4.1 单元测试重点

**共享 Contract 与 Adapter**：

- 唯一 BFF Envelope 的成功、失败、缺字段、稳定错误码和未知顶层字段拒绝；
- `data` 数组与 `meta.page/pageSize/total` 分页组合；
- BFF camelCase 边界、官方 upstream `success/data/error` 的 Adapter 消化和禁止透传；
- 收益状态 `pending/confirmed/paid` 及旧状态兼容映射；
- 未知角色、未知状态和不合法金额必须产生可观测 Contract Error。

**认证与权限**：

- Access Token 到期、单飞 Refresh、Refresh 失败和并发 401；
- `boss/member` 迁移为 `admin/creator`，未知角色拒绝；
- Router Meta、服务端 RBAC 和行级权限矩阵；
- Logout 调用失败时不能伪造服务端已撤销状态。

**领域逻辑**：

- 订单状态机、幂等键、重复提交和非法跃迁；
- `DECIMAL(18,4)` 字符串校验、精确计算、`HALF_UP`、安全整数分和舍入差额审计；
- 收益确认、结算、提现、支付、费率和累计误差；结算/提现默认两级审批策略快照、逐级跃迁、职责分离，以及由 `D-001-DECISION`、`D-001-READINESS`、P0-008 和 M6 共同约束的打款 fail-closed；
- Leader 与 Creator 数据范围和授权项目范围；
- WebSocket `eventId` 去重、乱序、补偿游标和退避上限；
- i18n Key、日期、数字、货币和时区格式。

状态 Adapter 示例：

```typescript
import { describe, expect, it } from 'vitest'
import { toEarningsStatus } from '../src/earnings-status'

describe('toEarningsStatus', () => {
  it.each([
    ['pending', 'pending'],
    ['locked', 'confirmed'],
    ['confirmed', 'confirmed'],
    ['settled', 'paid'],
    ['paid', 'paid']
  ] as const)('把 %s 归一为 %s', (input, expected) => {
    expect(toEarningsStatus(input)).toBe(expected)
  })

  it('拒绝未知状态', () => {
    expect(() => toEarningsStatus('unexpected')).toThrow('未知收益状态')
  })
})
```

订单激活金额边界示例：

```typescript
import { describe, expect, it } from 'vitest'
import {
  calculateOrderActivationAmount,
  decimal4Schema
} from '../src/money-contract'

describe('订单激活金额边界', () => {
  it.each([
    ['0.0049', 0, '-0.0049'],
    ['0.0050', 1, '0.0050'],
    ['12.3449', 1234, '-0.0049'],
    ['12.3450', 1235, '0.0050']
  ] as const)('激活时按 HALF_UP 转换 %s', (calculatedAmount, payableAmountFen, roundingDelta) => {
    expect(calculateOrderActivationAmount(calculatedAmount)).toStrictEqual({
      payableAmountFen,
      roundingMode: 'HALF_UP',
      roundingDelta
    })
  })

  it('拒绝非固定 4 位字符串和 JS number', () => {
    expect(decimal4Schema.safeParse('12.34').success).toBe(false)
    expect(decimal4Schema.safeParse(12.34).success).toBe(false)
  })

  it('拒绝舍入后超出 JS 安全整数的结果', () => {
    expect(() => calculateOrderActivationAmount('90071992547409.9150'))
      .toThrow('payableAmountFen 超出 JS 安全整数范围')
  })
})
```

金额测试还必须断言：

- 数据库 `DECIMAL(18,4)` 经 Driver 读取后仍为固定 4 位字符串，未经过浮点往返；
- 前端代码没有对 `unitPrice/rawAmount/calculatedAmount` 使用 `Number`、`parseFloat`、一元 `+` 或原生浮点算术；
- 订单创建请求拒绝客户端提交 `calculatedAmount`、任意 `*AmountFen`、`roundingMode` 或 `roundingDelta`；
- submit 只锁定精确草稿并进入 `pending`；Admin activate 在事务内重算，再从 `calculatedAmount` 生成 `payableAmountFen`；
- 激活审计记录原值、`HALF_UP`、最终整数分、固定 4 位 `roundingDelta`、操作者、时间与 `requestId`；
- 订单、结算、提现、退款、支付的出站 `*AmountFen` 均通过 `Number.isSafeInteger`。

### 4.2 组件测试重点

每个业务页至少验证：

- loading、empty、error、retry 和 success 五态；
- 表单必填、格式、服务端字段错误、重复提交锁和取消；
- 403 保留会话并显示 `requestId`，401 Refresh 失败才回登录；
- 角色无权限时入口、操作和数据均不可用；
- 手机布局下抽屉、表格替代视图、Modal 和主要操作不溢出；
- `zh-CN/en-US` 文案切换后布局、插值、日期、货币均正确；
- 键盘顺序、可见焦点、Accessible Name、错误提示关联和焦点回退；
- 组件卸载后释放 Observer、Timer、WebSocket 订阅和事件监听器。

结算与提现审批组件还必须验证：冻结的 `approvalPolicyVersion`、`requiredApprovalLevels`、`currentApprovalLevel` 和 `version` 可见；业务复核与财务批准时间线不会跳级；申请人、来源批次上传人或已占用其他独立级次的审批人看不到可执行的批准入口；最后一级前以及 `D-001-DECISION`、`D-001-READINESS`、P0-008 或 M6 任一未通过时打款按钮禁用并显示原因；驳回或撤回后旧操作不可继续；重复点击只发送一个请求，并发 `409` 后刷新到服务端最终状态。

MSW Handler 必须先通过导出的响应 Schema 校验再返回，测试不得手写另一套 Envelope。网络错误、超时、500、非法响应和请求取消均应有显式用例。

### 4.3 覆盖率门槛

| 范围 | Lines | Statements | Functions | Branches |
|---|---:|---:|---:|---:|
| 全仓目标 | >= 80% | >= 80% | >= 80% | >= 75% |
| Contract、认证、权限、金额、状态机 | >= 90% | >= 90% | >= 90% | >= 85% |

- 新增或修改的关键分支必须有行为断言，不能只追求行命中。
- 覆盖率下降会阻断合并，豁免必须有负责人、原因和到期日。
- 安全关键行为仍需 Contract、集成和 E2E 证据；高覆盖率不能替代这些层级。
- 不允许用排除注释隐藏应测逻辑，也不允许提交只有快照、没有行为断言的核心流程测试。

### 5.1 单一 Contract 来源

`packages/shared-contracts` 导出运行时 Schema、推导类型和 Adapter。以下消费者必须加载同一版本：

- 前端 Service 与 MSW Handler；
- BFF Serializer 与 Router 测试；
- WebSocket Publisher/Consumer；
- OpenAPI 生成和 Contract 报告。

`A-001-SPEC` 的 M0 目标契约冻结只要求唯一 `operationId`、完整 Schema/权限/错误/幂等/审计、稳定 Test ID、共享 Mock Fixture 与 target registry 的静态验证。注册表中的 `planned` operation 只能做 Schema/Fixture 静态 Contract，不能要求真实 route 或真实 BFF Contract Test，也不能计为 implemented。

`A-001-CONFORMANCE` 只覆盖注册表中声明为 `implemented` 的切片：实际 route 无未登记项、runtime spec 无不存在的 implemented operation、Mock 与真实 BFF 共用同一 Schema，并通过真实 BFF Contract Test。每个里程碑按已实施切片累计，M6 才要求全部 Required implementation 为 100%。

成功与失败响应固定验证：

```typescript
interface ApiEnvelope<T> {
  code: 0
  message: string
  data: T
  meta?: {
    page: number
    pageSize: number
    total: number
  }
  requestId: string
  timestamp: number
}

interface ApiFailure {
  code: number
  message: string
  details?: Record<string, string[]>
  requestId: string
  timestamp: number

```

列表接口还必须验证：`data` 是数组、`meta` 位于顶层且必填、页码边界稳定、空页语义一致。失败 `code` 必须是非零稳定整数，不能把失败包装为空列表。三类 strict Schema 均拒绝未声明的顶层字段。

唯一 Wire Contract 断言示例：

```typescript
import { describe, expect, it } from 'vitest'
import {
  apiFailureSchema,
  orderListEnvelopeSchema
} from '@zhihu/shared-contracts'

describe('BFF Wire Contract', () => {
  it('列表只使用 data 数组和顶层 meta', () => {
    const wire = {
      code: 0,
      message: 'ok',
      data: [],
      meta: { page: 1, pageSize: 20, total: 0 },
      requestId: 'req-contract-1',
      timestamp: 1786896000000
```

1. MSW Fixture 先由目标 Schema 解析，再交给组件和 E2E Mock 使用；

### 5.4 订单激活与财务多级审批集成测试

#### 5.4.1 订单提交与独立激活边界

订单 create 返回 `draft`，submit 进入 `pending`，Admin activate 才进入 `active` 并产生 `payableAmountFen`：

```typescript
import request from 'supertest'
import { describe, expect, it } from 'vitest'
import {
  orderActivationEnvelopeSchema,
  orderDraftEnvelopeSchema,
  orderPendingEnvelopeSchema
} from '@zhihu/shared-contracts'
import {
  createIntegrationApp,
  issueAccessToken,
  seedProject,
  seedUser
} from '../support/integration-fixtures'

describe('订单 create -> submit -> activate', () => {
  it('只在 pending -> active 时生成可审计的 payableAmountFen', async () => {
    const { app, roundingAuditRepository } = await createIntegrationApp()
    const admin = await seedUser({ role: 'admin' })
    const creator = await seedUser({ role: 'creator' })
    const project = await seedProject({ ownerId: admin.id })
    const accessToken = await issueAccessToken(admin)
    const payload = {
      orderType: 'promotion',
      buyerUserId: creator.id,
      items: [{
        itemType: 'promotion',
        itemId: project.id,
        itemName: '测试推广任务',
        rawAmount: '10.0000',
        unitPrice: '12.3445'
      }]
    }

    const createResponse = await request(app)
      .post('/api/v1/admin/orders')
      .set('Authorization', `Bearer ${accessToken}`)
      .send(payload)
      .expect(201)

    const draft = orderDraftEnvelopeSchema.parse(createResponse.body)
    expect(draft.data.status).toBe('draft')
    expect(draft.data.items[0]).toMatchObject({
      ...payload.items[0],
      calculatedAmount: '123.4450'
    })
    expect(draft.data.calculatedAmount).toBe('123.4450')
    expect(draft.data).not.toHaveProperty('payableAmountFen')

    const submitResponse = await request(app)
      .post(`/api/v1/admin/orders/${draft.data.id}/submit`)
      .set('Authorization', `Bearer ${accessToken}`)
      .send({ version: draft.data.version })
      .expect(200)

    const pending = orderPendingEnvelopeSchema.parse(submitResponse.body)
    expect(pending.data.status).toBe('pending')
    expect(pending.data).not.toHaveProperty('payableAmountFen')
    expect(pending.data).not.toHaveProperty('roundingMode')

    const activationResponse = await request(app)
      .post(`/api/v1/admin/orders/${draft.data.id}/activate`)
      .set('Authorization', `Bearer ${accessToken}`)
      .send({ version: pending.data.version })
      .expect(200)

    const active = orderActivationEnvelopeSchema.parse(activationResponse.body)
    expect(active.code).toBe(0)
    expect(active.data.status).toBe('active')
    expect(active.data.payableAmountFen).toBe(12345)
    expect(Number.isSafeInteger(active.data.payableAmountFen)).toBe(true)
    expect(active.data.roundingMode).toBe('HALF_UP')
    expect(active.data.roundingDelta).toBe('0.0050')

    const audit = await roundingAuditRepository.findByRequestId(
      active.requestId
    )
    expect(audit).toMatchObject({
      sourceCalculatedAmount: '123.4450',
      roundingMode: 'HALF_UP',
      payableAmountFen: 12345,
      roundingDelta: '0.0050'
    })
  })
})
```

```typescript
        .set('Idempotency-Key', `${resource.id}-level-2`)
        .send({
          version: first.data.version,
          approvalPolicyVersion: 7,
          approvalLevel: 2
        })
        .expect(200)

      const final = financeApprovalEnvelopeSchema.parse(finalResponse.body)
      expect(final.data).toMatchObject({
        status: 'approved',
        approvalPolicyVersion: 7,
        requiredApprovalLevels: 2,
        currentApprovalLevel: 2
      })
      expect(await financeApprovalRepository.listActors(resource.id)).toStrictEqual([
        { level: 1, userId: businessReviewer.id, policyVersion: 7 },
        { level: 2, userId: financeApprover.id, policyVersion: 7 }
      ])
    })
  }
)
```

`FIN-APPROVAL-002`～`007` 每次除响应外还要断言资源行、审批不可变历史、payment intent/流水和适用审计事件；`FIN-APPROVAL-008` 额外断言 `D-001-DECISION`、`D-001-READINESS`、P0-008、M6 每个非空失败 Gate 子集的精确 `failedGates`、零 payment intent/支付流水/余额占用/生产资金状态写入，以及恰好一条含同一 `requestId` 和相同 `failedGates` 的 `finance.gate_rejected` 审计事件。只验证按钮隐藏不算权限或 Gate 测试。撤回的 HTTP `operationId` 尚待 `A-001-SPEC` 冻结，在此之前 `FIN-APPROVAL-006` 先落为领域 Service Integration，不得伪造候选端点或标记 API 覆盖已通过；真实 route/BFF 覆盖只在该切片被声明 `implemented` 后计入 `A-001-CONFORMANCE`。

每个资源执行以下多角色矩阵：

| 场景 | Admin | Leader | Creator |
|---|---|---|---|
| 查看本人数据 | 允许 | 允许 | 允许 |
| 查看授权团队数据 | 按权限 | 允许下属范围 | 拒绝 |
| 查看无关用户数据 | 按审计权限 | 拒绝 | 拒绝 |
| 创建或审批平台级资源 | 允许 | 拒绝 | 拒绝 |
| 修改授权项目内容 | 按权限 | 按授权 | 按授权 |

测试必须验证 HTTP 状态、失败 Envelope、数据库无越权写入、审计事件和响应无敏感数据。前端隐藏按钮不算权限测试。

### 5.5 WebSocket Contract 与集成

每种事件验证：

- `type/eventId/occurredAt` 和资源 ID Schema；
- Access Token 建连、到期重连、无权限订阅和服务端关闭码；
- 重复 `eventId` 只应用一次，乱序事件不会回退状态；
- `lastEventId` 补拉断线期间事件，补拉失败显示离线状态；
- 订单、结算、提现和通知更新后按资源 ID 增量刷新；
- 未知事件版本被隔离并记录，不导致页面崩溃；
- 心跳超时、网络切换、浏览器休眠恢复和指数退避上限。

Publisher 和 Consumer 使用同一事件 Schema。WebSocket 只提供变更信号，最终状态仍由受权限保护的 HTTP 查询确认。

### 6.6 WebSocket 与迁移兼容 E2E

## 八、性能、容量与稳定性

### 8.1 测试环境基线

性能报告必须记录：

- 应用、BFF、数据库、Redis 和 WebSocket 服务版本；
- CPU、内存、磁盘、网络、实例数和自动扩缩容状态；
- 数据集版本、缓存预热策略和测试账号分布；
- 监控面板时间窗、Trace 样本和资源饱和点。

本地开发机结果只能用于调试，不能作为发布验收证据。正式基线在与生产拓扑等比或明确换算的专用环境执行。

### 8.2 基准数据量

最低合成数据集：

| 实体 | 数量 |
|---|---:|
| 用户 | 10,000 |
| 项目 | 5,000 |
| 订单 | 100,000 |
| 结算 | 100,000 |
| 收益明细 | 1,000,000 |
| 数据中继日志 | 5,000,000 |

数据分布要包含热点 Leader、大团队、长尾 Creator、跨月结算、异常状态和大分页。不得只生成均匀小记录来规避真实查询压力。

### 8.3 HTTP 负载模型与门槛

标准场景：

1. 预热 5 分钟，不计入门槛；
2. 5 分钟从 0 Ramp 到 100 并发用户；
3. 100 并发用户稳定运行 30 分钟；
4. 2 分钟降载并观察队列排空；
5. 读写比例按生产观测值配置；无观测值时暂用 80:20 并在评审中确认。

验收门槛：

- API P95 < 500 ms；
- API P99 < 1 s；
- HTTP 错误率 < 0.5%；
- 关键写操作业务成功率 >= 99.5%；
- 数据库连接池、事件循环延迟、队列深度和内存无持续恶化；
- 同一幂等键重复写入不会产生重复订单、结算或提现。

k6 阈值示意：

```javascript
export const options = {
  stages: [
    { duration: '5m', target: 100 },
    { duration: '30m', target: 100 },
    { duration: '2m', target: 0 }
  ],
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<1000'],
    http_req_failed: ['rate<0.005']
  }
}
```

脚本必须包含登录、列表、详情和代表性写入，不能用单一健康检查代表业务性能。结果按端点和角色拆分，聚合值不能掩盖慢接口。

### 8.4 WebSocket 容量与恢复

最低场景：

- 10 分钟 Ramp 到 1,000 个并发连接，稳定保持 30 分钟；
- 按订单、结算、提现和通知的预期峰值发送消息；
- 随机断开 10% 连接、服务滚动重启和 Access Token 刷新；
- 验证 `eventId` 去重、补偿游标、心跳和退避。

验收门槛：

- 消息端到端延迟 P95 < 1 s；
- 至少 95% 的断开连接在 10 秒内恢复；
- 未授权或跨角色消息数为 0；
- 重复应用事件数为 0，补偿后缺失事件数为 0；
- 30 分钟稳定阶段无持续增长的 Socket、Timer、监听器或内存泄漏。

### 8.5 前端体验与耐久性

- Mobile Web Vitals：LCP P75 <= 2.5 s、INP P75 <= 200 ms、CLS P75 <= 0.1；
- 首屏和核心路由分别记录压缩资源体积，超出预算阻断并说明增量来源；
- 360 px 中端移动设备配置下执行冷启动、慢速网络和弱 CPU 场景；
- Dashboard 连续切换路由、语言和筛选 30 分钟，无持续内存增长；
- WebSocket 重连、图表 Resize 和页面卸载后资源计数回到基线范围。

**合并阻断**：

- TypeScript 或 lint Error；
- Unit、Component、Contract 或 Integration 失败；
- 覆盖率低于门槛；
- 任一应用构建失败；
- i18n Key 不对称、严重可访问性问题或新旧 Contract 不一致；
- 数据库安全门未执行或目标信息不明确。

**发布阻断**：

- 任一核心 E2E、三角色隔离、Logout 撤销或旧 URL 兼容失败；
- API P95/P99、错误率、WebSocket 或 Web Vitals 超过门槛；
- 存在未处置 High/Critical 漏洞；
- 灰度指标、Feature Flag 或回滚演练缺少证据；
- 测试报告与候选镜像摘要不一致。

失败检查不得由同一提交的空白重跑覆盖。确认是基础设施瞬时故障时最多自动重试 1 次，并同时保存首轮失败证据；可重复的产品失败必须修复。

### 9.3 Flaky Test 与豁免

- Flaky Test 首次确认后立即建档，记录负责人、失败率、影响范围和修复期限。
- 隔离只允许从普通反馈队列移到专门阻断队列，不能静默跳过发布关键流程。
- 认证、权限、支付金额、结算、提现、数据安全和迁移回滚用例不得豁免。
- 临时阈值豁免需研发、测试和责任域 Owner 联合批准，并写明到期日。
- 到期未修复时自动恢复阻断，不允许无限延期。

### 9.4 证据与保留

每次候选发布归档：

- JUnit、coverage、Playwright Trace、截图和视频；
- Contract Schema 版本、OpenAPI Diff 和 Mock/真实服务比对结果；
- k6 原始结果、监控面板、慢 Trace 和数据库指标；
- 安全扫描、SBOM、人工可访问性记录；
- Commit SHA、镜像摘要、配置摘要、测试数据版本；
- 已知失败、豁免、负责人、截止时间和回滚决策。

普通 PR 证据至少保留 30 天，发布候选证据至少保留 1 年；若合规要求更长，以合规要求为准。

## 十二、报告与问题披露规则

测试报告必须区分以下状态：

| 状态 | 判定 |
|---|---|
| Passed | 已在指定 Commit、镜像和环境实际执行，断言及门槛通过，证据可访问 |
| Failed | 已执行且出现产品、契约、性能或安全失败 |
| Blocked | 因环境、权限、依赖或硬性前置条件无法执行 |
| Not Run | 尚未执行，不能并入通过率 |
| Not Applicable | 经评审确认不适用，并记录理由和批准人 |

报告至少披露：

1. 计划用例数、实际执行数和未执行原因；
2. 失败详情、复现条件、Owner 和目标修复日期；
3. Flaky、重试、隔离和豁免情况；
4. 环境、数据、版本、配置和候选镜像差异；
5. Contract、覆盖率、性能、安全和可访问性原始证据；
6. 灰度观察、回滚演练和遗留风险；
7. 当前代码尚未具备的依赖、脚本与测试层级。

本 v2 文档取代 v1 中与上述规则冲突、不安全、字段命名不一致或未经执行即声称通过的示例。它定义目标测试体系与发布门槛，不代表当前仓库已经达到这些门槛。
