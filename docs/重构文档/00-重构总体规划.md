## 一、重构背景与目标

### 1.1 业务战略调整

**核心业务定位变更**：
- **此前**：单纯的知乎 API 接口调试台 + 简单的后台管理
- **现在**：知乎推广业务的 **SaaS 运营平台**，面向三类用户（Admin/团长/达人），支持账号矩阵运营和增值服务销售

**商业模式**：
```
双线盈利模型：
┌─────────────────────────────────────────────────┐
│ 线路一：自营账号矩阵 → 知乎推广收益              │
│ 线路二：SaaS 订阅 + 增值服务 → 团长/达人付费      │
└─────────────────────────────────────────────────┘
```

### 1.2 重构目标（SMART 原则）

| 维度 | 目标 | 验收标准 |
|------|------|---------|
| **功能完整性** | 覆盖已批准的三角色业务范围 | `04-功能模块清单.md` 中标为 Required 的条目均具备 DB/API/UI/Test 证据，且不存在 P0/P1 未关闭项 |
| **数据中继** | 知乎收益数据可控分发 | 自定义单价规则生效，团长/达人看到的收益与 Admin 配置一致 |
| **角色隔离** | 三角色独立系统 | 三个前端项目独立部署，互不影响，数据权限严格隔离 |
| **交付质量** | 以可复现证据准入 | typecheck、自动化测试、格式检查、权限负向测试、迁移演练和性能门槛全部有命令、数据集与实际结果 |
| **开发窗口** | 依赖优先、Gate 驱动 | 7 周、约 35 个工作日为目标窗口，不是上线承诺；任一 exit gate 未通过即顺延 |

### 1.3 关键业务需求与财务数据源 Gate

#### Gate D-001：可结算财务数据源（总称；P0，待用户确认）

**锁定边界**：官方实时指标只用于运营观察，**不可直接作为结算依据**。在官方提供并验证可结算 API 前，建议使用“Admin 审核的 XLSX 结算批次导入适配器”作为财务收益源；适配器必须可替换，以便未来切换到官方结算 API。

为避免把业务决定与工程就绪混为一谈，D-001 拆为两个独立子 Gate：

- **D-001-DECISION**：用户书面确认权威来源、字段口径、结算周期、币种、修订与冲正规则；该 Gate 只证明业务决定，不证明 adapter 已可运行。该 Gate 未关闭前，财务范围只允许 Mock、协议设计与非财务工作；即使标为隔离沙箱，也不得运行实际 adapter、匿名样例导入、审批、中继或对账。
- **D-001-READINESS**：仅在 `D-001-DECISION` 关闭后，实际 adapter、匿名样例、审批、幂等、中继、冲正和对账这七项工程证据才能在隔离沙箱形成；该 Gate 只依赖这七项工程证据关闭。

```text
官方实时指标 ───────────────→ 运营看板（只读、标注“不可结算”）

Admin 导入 XLSX 结算批次
    ↓  格式校验、去重、批次哈希、人工复核
已批准结算批次（唯一可结算输入）
    ↓
后端中继层（单价转换 + 多级利润分配 + 审计）
    ├→ Admin：批次原始值、配置、计算链与差异
    ├→ 团长：按团长规则计算后的收益
    └→ 达人：从所属团长链路二次分发后的收益
```

**D-001-DECISION exit gate**：用户书面确认数据源方案、字段口径、周期、币种、修订与冲正规则。在该子 Gate 通过前，不得把任何来源标为权威结算来源；财务范围只允许 Mock、协议设计和非财务工作，即使隔离沙箱也不得运行实际 adapter、匿名样例导入、审批、中继或对账。该 Gate 通过后，才可在隔离沙箱实施上述实际工程以积累 READINESS 证据；它仍不等同于已具备生产资金链运行资格，生产结算、余额、提现和打款仍必须同时满足 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6。

**D-001-READINESS exit gate**：实际 adapter、匿名样例、审批、幂等、中继、冲正和对账七项工程证据均可复现；该 Gate 的关闭只依赖这七项工程证据。

**READINESS 工程边界**：`D-001-DECISION` 未通过前只允许 Mock、协议设计和非财务工作，即使隔离沙箱也不得实施实际 adapter、匿名样例导入、审批、中继或对账；仅在 `D-001-DECISION` 关闭后，才允许在隔离沙箱形成上述 READINESS 证据。

**生产资金放行**：仅当 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 全部通过，才可启用生产结算、余额展示、提现或打款；任一未通过时生产资金链保持 `BLOCKED`，不得承诺或执行。

**D-001 总 Gate**：仅作为两个子 Gate 的聚合称呼；不得用总称状态替代任一子 Gate 的证据。

**P0-008 目标模型（归属 `A-001-SPEC`）**：M0 只冻结“提现工单 → 收益账本分录 → 来源批次”的目标对象、不可变分摊、余额占用/释放、部分分摊、并发防双花、撤回/驳回释放、支付失败恢复和冲正约束；这属于目标规格，不证明 migration、运行时一致性或 P0-008 已关闭。目标模型及其关联可追溯到 `source_batches.uploaded_by` 前，`D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 任一未通过时，提现审批与打款必须 fail closed。

**已锁定的中继要求**：
- Admin 对下级团长和达人拥有定价配置权，但每次计算必须保留生效配置快照和完整上下级链路。
- 团长/达人永远看不到官方原始指标或已批准批次的原始财务值。
- 收益计算只在后端执行，前端只展示对应角色可见结果。
- 历史重算生成新版本，不覆盖旧计算日志；重算结果经复核后才能替代当前版本。

## 三、重构核心决策

### 3.1 架构决策记录（ADR）

#### ADR-001：三个完全独立的前端项目

**决策**：拆分 `platform/` 为三个独立项目：`platform-admin/`、`platform-leader/`、`platform-creator/`

**理由**：
1. **功能差异大**：三角色的数据源、业务逻辑、UI 设计完全不同
2. **独立迭代**：达人端可以快速迭代新功能，不影响 Admin 稳定性
3. **部署隔离**：Admin 部署到内网，团长/达人部署到公网，安全域不同
4. **品牌差异**：未来可为不同客户定制不同的团长端品牌

**代价**：
- 代码复用需要抽取共享组件库
- 部署和运维成本增加
- 构建时间增加

**缓解方案**：
- 创建 `packages/shared-components/` 共享组件库
- 使用 Turborepo/Nx 管理 Monorepo
- Docker Compose 统一编排三个前端

#### ADR-002：已批准结算批次的中继计算完全由后端负责

**决策**：所有可结算收益的单价转换、上下级利润分配在后端完成，前端只展示角色可见结果。官方实时指标与财务结算批次严格分流，权威来源受 `D-001-DECISION` 约束，实际数据链受 `D-001-READINESS` 约束。

**理由**：
1. **安全性**：前端计算逻辑可被逆向，泄露定价规则
2. **一致性**：避免前后端计算逻辑不一致导致的数据差异
3. **可审计**：后端日志记录每一笔计算，便于对账
4. **灵活性**：单价规则调整后可后台批量重算历史数据

    userId: string,
    userRole: 'admin' | 'leader' | 'creator'
  ): Promise<RelayedEarnings> {
    // 1. 校验批次已由 Admin 批准且未撤销
    // 2. 解析用户归属链并固定配置版本
    // 3. 依次计算团长收益与达人二次分发收益
    // 4. 追加不可变计算日志，返回角色可见结果

#### ADR-003：对 `z-*` 页面分级迁移并整合到项目管理

**决策**：目标入口统一到 `/dashboard/projects/novel-promo/zhihu-story`，但不得把页面存在等同于能力已迁移。每个模块先按 `official-supported`（有当前官方接口证据）、`legacy`（旧页面/旧契约，仅兼容维护）或 `custom`（本地自建能力）分类；只有具备 DB/API/UI/Test 证据并通过验收的 `official-supported`/`custom` 条目才能下线对应旧路由。

#### ADR-005：统一 BFF Wire Contract 与金额分层

**决策**：所有 BFF JSON endpoint（健康检查和二进制下载除外）使用同一 Wire Envelope。成功响应固定为 `code/message/data/meta?/requestId/timestamp`，列表使用 `data: T[]` 与顶层 `meta`，失败响应使用稳定非零整数 `code`、`message/details?/requestId/timestamp`；知乎 upstream 的 `success/data/error` 只能由 Adapter 消化，禁止透传到 View、Store、Mock 或公共响应。

金额按两个阶段处理：来源与计算中间值使用 `DECIMAL(18,4)` 对应的固定 4 位十进制字符串，禁止 JavaScript 浮点运算；进入经评审冻结的审批边界后，服务端才按 `HALF_UP` 生成安全整数 `*AmountFen`，并记录原值、结果、舍入差额、规则版本、操作者和 `requestId`。字段级细则分别以 `01` 第 1.2 节、`02` 第 1.3～1.4 节、`03` 第 4 节和 `05` 第 4～5 节为准。

**当前状态**：上述内容是 v2 目标契约，不代表当前 `platform/server` 已实现。`A-001-SPEC` 的关闭条件仅是目标 OpenAPI 3.1、唯一 `operationId`、完整 Schema/权限/错误/幂等/审计、稳定 Test ID、共享 Mock Fixture 与目标注册表的静态冻结。对已声明 `implemented` 的切片，Mock/真实 BFF Contract Test、数据库字符串往返和金额审批审计测试属于 `A-001-CONFORMANCE` 的实施证据；`planned` operation 和未来未实现路由不得使 M0 等待。

## 六、里程碑与交付计划

### 6.1 七周目标窗口与依赖顺序

**排期口径**：7 周、约 35 个工作日是当前目标窗口，不是上线日期承诺。按单一主执行者每周最多 5 个工作日估算，不假设同一人并行完成多条关键路径；某周 exit gate 未通过时，未完成项顺延，禁止通过删测试、降权限或跳过迁移演练压缩工期。

| 周次 | 依赖与目标 | 本周最小产出 | Exit gate（全部满足才进入下一关键路径） |
|------|-----------|-------------|----------------------------------------|
| **Week 1 · M0 规格冻结与安全基线** | 无前置 | v2 文档基线；Feature 追踪表；`A-001-SPEC` 目标契约与 P0-008 目标对象冻结；唯一 BFF Envelope、金额分层、角色/状态/事件 Schema；测试库防误清修复 | `A-001-SPEC` 的 OpenAPI 3.1、唯一 `operationId`、完整 Schema/权限/错误/幂等/审计与 Test ID 通过静态冻结；M0 不要求未来全部路由真实存在，也不要求全部真实 BFF Contract Test；已实施切片另按 `A-001-CONFORMANCE` 验证；默认 Testcontainers，外部库 `_test` allowlist 与显式 destructive 开关在连接前硬拒绝危险目标；`D-001-DECISION` 未通过时财务只允许 Mock、协议设计和非财务工作，不得以沙箱名义实施实际 adapter、匿名样例导入、审批、中继或对账；`D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 任一未通过时生产结算、余额、提现和打款保持 `BLOCKED` |
| **Week 2 · M1 基础、账户与项目** | M0 | Monorepo/三前端骨架；认证/RBAC；MCN/子账号最小模型；项目、成员和课程最小闭环 | 三前端可独立登录；跨角色负向用例通过；账户授权与项目成员关系有 DB/API/Test 证据 |
| **Week 3 · M2 财务输入与中继** | M1 的用户归属、账户、项目关系，且 `D-001-DECISION` 已关闭 | 运营指标 D+1 日批；仅在隔离沙箱实施 XLSX 批次实际 adapter、批准/撤销/版本模型、团长→达人中继与不可变日志 | `D-001-DECISION` 未关闭时不启动实际 adapter、匿名样例导入、审批、中继或对账；关闭后，隔离沙箱可完成匿名样例导入、去重、审批、两级中继计算和对账以积累 `D-001-READINESS` 证据，但不启用生产资金链。`D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 任一未通过时，真实结算、余额、提现和打款保持 `BLOCKED`；实时指标无法进入结算表，历史重算不覆盖旧日志 |
| **Week 4 · M3 订单、结算与提现** | M2 | 统一订单状态机；Admin/Leader/Creator 权限；可配置财务多级审批；结算与提现沙箱流程 | 状态迁移表全覆盖；越权、重复审批、并发审批和回滚用例通过；`D-001-DECISION`、`D-001-READINESS`、P0-008 或 M6 任一未通过时打款接口保持禁用 |
| **Week 5 · M4 推广受支持范围** | M1 的账户/项目；M0 的官方能力核对 | official-supported 模块闭环；legacy/custom 模块迁移清单；原 `z-*` 路由兼容/下线策略 | 每个宣称支持的模块均有官方依据、API/UI/Test；未支持模块明确显示 unavailable，不以占位页计完成 |
| **Week 6 · M5 体验与迁移演练** | M1～M4 | 响应式布局；`zh-CN`/`en-US`；WebSocket 通知；完整历史数据迁移预演 | 指定桌面/移动视口通过；两种 locale 关键流程通过；断线重连/鉴权测试通过；迁移总数、金额校验和、孤儿记录均对账 |
| **Week 7 · M6 发布候选** | M0～M5 均已通过 | 回归、安全、性能、恢复演练；部署与用户文档；真实业务验收报告 | Required 追踪项 100% 有证据；P0/P1 为 0；格式/typecheck/test 全绿；性能与恢复门槛通过；人工验收签字 |

**当前启动边界**：现阶段只允许启动 M0 的规格冻结与安全修复。`A-001-SPEC`、统一 Contract 目标 Schema 与测试库隔离 Gate 未关闭前，不得以目标文档为由启动 M1～M6 全量交付；不涉及实现的调研、盘点和修复设计可继续。M0 可以在 `D-001-DECISION` 尚未关闭时完成规格冻结，但财务范围仅限 Mock、协议设计和非财务工作，即使沙箱也不得实施实际 adapter、匿名样例导入、审批、中继或对账；`D-001-DECISION` 关闭后才可在隔离沙箱形成 `D-001-READINESS` 证据。无论何时，`D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 任一未通过时，真实结算、余额、提现和打款都保持 `BLOCKED`；已实施切片的真实一致性另由 `A-001-CONFORMANCE` 管理。

**生产 Gate**：M6 只表示形成发布候选，不自动等于上线。`D-001-DECISION`、`D-001-READINESS`、`A-001-SPEC`、`A-001-CONFORMANCE`（M6 汇总 Required implementation 为 100%）、P0-008 目标模型与运行一致性、隔离数据库测试、完整迁移演练、资金链人工验收、性能/安全门槛和回滚演练任一未通过时，不得承诺上线日期，也不得启用生产结算、余额、提现或打款。

### 7.2 质量保障措施

**代码层面**：
1. **TypeScript 严格模式**：`strict: true`，禁止 `any`
2. **ESLint + Prettier**：统一代码风格，自动格式化
3. **Git Hooks**：提交前自动运行 lint 和 type-check
4. **Code Review**：所有代码必须经过审查才能合并

**测试层面**：
1. **单元测试**：核心服务覆盖率 ≥ 70%
2. **集成测试**：追踪矩阵中所有 Required API 必须有成功、校验失败和越权测试证据
3. **Mock 测试**：业务流程先用 Mock 数据验证
4. **真实测试**：Mock 通过后再对接真实 API

**文档层面**：
1. **文档先行**：代码开发前必须完成设计文档
2. **文档审核**：设计文档需经人工审核通过
3. **文档同步**：代码变更必须同步更新文档

#### C.2 开放 Gate

1. **`D-001-DECISION` / `D-001-READINESS`**：前者仅以用户对权威来源、字段、周期、币种、修订与冲正规则的书面确认关闭；前者未关闭时只允许 Mock、协议设计和非财务工作，即使隔离沙箱也不得实施实际 adapter、匿名样例导入、审批、中继或对账。前者关闭后，后者才可在隔离沙箱以实际 adapter、匿名样例、审批、幂等、中继、冲正和对账证据关闭。`D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 任一未通过时，生产结算、余额、提现和打款均不得上线。
2. **`A-001-SPEC` / `A-001-CONFORMANCE`**：前者冻结目标契约，后者按已实施切片核验运行一致性；二者均不授权把 planned operation 宣称为 implemented。
3. **创意工具 URL**：真实 URL 由产品后续提供；占位 URL 只能用于沙箱，不得将占位跳转记为功能完成。
