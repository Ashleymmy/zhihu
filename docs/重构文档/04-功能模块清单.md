### 1.2 状态口径与当前基线

| 状态 | 判定规则 |
|------|---------|
| `IMPLEMENTED` | Required 的 DB/API/UI/Test 均有可运行证据，且验收命令实际通过 |
| `PARTIAL` | 已有一部分代码或旧能力，但缺少至少一层证据，或契约仍冲突 |
| `MISSING` | v2 Required 范围尚无可用实现 |
| `BLOCKED` | 存在未决业务 Gate、安全风险或外部依赖，禁止进入生产链路 |

附录 A 的 DB/API/UI/Test 单元使用另一组**目标规格标签**，不得与上述当前实现状态混用：

| 目标规格标签 | 判定规则 |
|-------------|---------|
| `TARGET-SPECIFIED` | v2 文档已定义目标对象、候选路径/页面或测试层，并给出可定位章节；仍不代表代码存在 |
| `TARGET-GAP` | 已知需要该单元，但稳定对象、`operationId`、Route/Component 或 Test ID 尚未冻结 |
| `NOT-APPLICABLE` | 经矩阵明确该层不适用，并说明替代证据；不能用来掩盖缺口 |

### 1.3 唯一追踪规则

1. 每个功能必须有稳定 `Feature ID`，并记录 `Required?`、分类、DB、API、UI、Test、状态和 Evidence。
2. `02-API接口契约.md` 当前约 161 条只是候选 inventory。目标 API 数量与 Endpoint ID 只能在其 `A-001-SPEC` OpenAPI 3.1 Gate 关闭后由唯一 `operationId` 注册表机械生成；冻结前本文只引用候选 method+path/章节，不报告总数。当前实现状态、route/spec 双向 coverage 与真实 BFF Contract Test 只属于 `A-001-CONFORMANCE`，目标已登记不得提升为 `IMPLEMENTED`。
3. `DB/API/UI/Test` 任一 Required 单元为 `TARGET-GAP` 时，功能最高只能标 `PARTIAL`；存在业务或安全 Gate 时保持 `BLOCKED`。
4. 页面存在、Mock 可点击、类型检查通过或旧接口存在，均不能单独证明 v2 功能完成。
5. 每次状态变更必须附命令输出、测试名、截图或人工验收记录；没有 Evidence 不得升级状态。
6. 所有 BFF JSON endpoint 使用唯一 Envelope：成功 `code/message/data/meta?/requestId/timestamp`，列表为 `data: T[]` 加顶层 `meta`，失败为稳定非零整数 `code` 与 `message/details?/requestId/timestamp`；upstream `success/data/error` 只能存在于 Adapter 内。
7. 来源与计算中间金额使用固定 4 位十进制字符串及后端 `DECIMAL(18,4)`；经冻结的审批边界后才由服务端按 `HALF_UP` 生成安全整数 `*AmountFen`，并保留原值与差额审计。目标契约不等于当前代码已落实。
8. 所有 API 目标规格列引用 `A-001-SPEC`；当前 Evidence、route/spec coverage 与真实 BFF Contract Test 引用 `A-001-CONFORMANCE`。legacy 路由必须标为 `legacy/deprecated`，不得用候选路径或 Mock 代替运行证据。

## 三、功能模块详细清单

### 3.1 核心业务功能

#### 3.1.1 数据中继与收益管理

**功能描述**：以 `00` 的 `D-001-DECISION`/`D-001-READINESS` 为边界，将运营实时指标与可结算财务批次分流，并对已批准批次执行团长→达人两级计算。

**子功能**：
1. **运营指标同步**（Admin 专属，只读）
   - 按 D-004 执行 D+1 日批：每天同步前一自然日官方运营指标
   - 以自然日、项目和来源生成稳定幂等键；迟到数据走补跑，不重复累计
   - 所有 DTO/UI 明示 `settlementEligible=false`
   - 支持手动补同步并记录同步日志
   - 禁止写入结算批次、结算单或可提现余额

2. **可结算批次导入与审批**（Admin 专属；`D-001-DECISION` 未通过时为 `BLOCKED`，仅可 Mock/协议设计，不能因标为沙箱而实施实际 adapter、匿名样例导入、审批、中继或对账；该 Gate 关闭后，`D-001-READINESS` 未通过时只可在隔离沙箱积累工程证据，生产资金仍由四项 Gate 阻断）
   - XLSX 模板校验、批次哈希、幂等导入、错误行报告
   - Admin 复核、批准、撤销和修订版本；只有批准版本可进入中继
   - 未来官方结算 API 通过同一 adapter contract 接入，不改变下游计算接口

3. **收益配置管理**（Admin 专属）
   - 目标维度支持角色/用户；作用域严格使用 D-002 的全局/项目/渠道三选一
   - 配置优先级、重叠检测与确定性回退
   - 生效日期控制
   - 历史配置与计算时配置快照查询

4. **收益计算引擎**（后端服务）
   - 从已批准批次依次计算团长收益和所属达人二次分发收益
   - Required 范围只启用固定单价和百分比；自定义公式在安全 DSL、精度和超时规则通过复审前为 `MISSING`
   - 追加不可变计算日志，记录批次、配置版本和上下级链
   - 历史重算生成新版本，经复核后切换，不覆盖旧日志

5. **收益查询**（三角色）
   - Admin：查看批准批次原始值、计算链和中继结果
   - Leader：查看自己+下级达人的中继收益
   - Creator：查看自己的中继收益
   - 按日期、项目、渠道筛选
   - 收益趋势图表

**Required 数据对象**（最终名称以 `01` v2 DDL 为准）：
- 运营指标表（明确不可结算）
- 结算导入批次、批次明细、审批/撤销记录
- 收益配置与配置版本快照
- 不可变中继计算日志及当前生效版本指针

**API 追踪**：`02` 第 8 节已定义财务批次、配置、两级中继、重算和查询候选契约；唯一 Endpoint ID 与目标数量仍受 `A-001-SPEC` OpenAPI 3.1 冻结 Gate 约束；真实路由覆盖与 BFF Contract Test 另记入 `A-001-CONFORMANCE`。

#### 3.1.2 订单管理

**功能描述**：推广订单全生命周期管理

**子功能**：
1. **订单列表**（三角色）
   - 列表展示（表格）
   - 筛选：状态、时间范围、项目、任务
   - 排序：创建时间、更新时间、订单金额
   - 分页

2. **订单详情**（三角色）
   - 基本信息展示
   - 关联推广计划/任务
   - 收益明细
   - 状态变更记录

3. **订单创建**（Admin/Leader）
   - Admin 可为任意授权用户创建
   - Leader 可为自己和下级达人创建
   - Creator 不可创建（由上级分配）

4. **订单编辑**（Admin/Leader）
   - Admin 可编辑任意订单
   - Leader 仅可编辑自己或所属团队范围内、且处于允许修改状态的订单
   - Creator 只读，不可创建、编辑或删除订单
   - v2 唯一状态机：`draft → pending → active → completed → settled`；`pending/active → cancelled`；已结算退款使用 `partially_refunded/refunded`，非法逆向迁移返回冲突错误

5. **订单删除**（Admin）
   - 软删除
   - 仅 Admin 可删除
   - 批量删除支持
   - 仅 `draft/cancelled` 可删除；Leader/Creator 无删除权限
   - 更新、状态迁移和批量操作必须带 `version`，冲突返回 `409`
   - `draft → pending` 只锁定固定 4 位的来源/计算金额；Admin 执行 `pending → active` 是金额审批边界，服务端重算后按 `HALF_UP` 生成安全整数 `*AmountFen`，客户端不得覆盖计算结果

**涉及表**：
- `orders`（订单表）
- `order_items`（订单明细）
- v2 必须补齐项目/任务关联、`version`、状态迁移审计和退款记录；以 `01` 修订后的 DDL 为准

**API 追踪**：`02` 第 4.2 节及三角色 candidate inventory 已定义目标路径、状态与权限；唯一 `operationId`、完整 Schema 和目标数量在 `A-001-SPEC` 关闭后生成，不在本文手工填写；候选路径不代表 implemented。

#### 3.1.3 结算管理

**功能描述**：仅消费经 `D-001-READINESS` 验收的已批准批次和已复核中继版本的结算、提现与打款流程；只有 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 均通过时，生产结算、余额、提现和打款才可启用，任一未通过时整个资金链为 `BLOCKED`。

**子功能**：
1. **结算单管理**（三角色）
   - 按可配置周期生成结算单，默认每月 1 日生成上月结算
   - 结算单列表（状态筛选）
   - 结算单详情（收益明细）
   - Admin 调整必须填写原因、保留前后值并重新进入多级审批
   - 舍入前 `calculatedAmount` 保持固定 4 位字符串；审批后 `payableAmountFen` 由服务端按 `HALF_UP` 生成，并记录 `roundingDelta`、规则版本、操作者与 `requestId`

2. **提现申请**（Leader/Creator）
   - 发起提现申请
   - 填写提现账户信息
   - 上传收款凭证（可选）
   - 查看提现记录

3. **提现多级审批**（Admin 财务角色）
   - 待审批列表
   - 默认至少“业务复核→财务批准”两级，级数与角色可配置
   - 每级支持审批、拒绝、退回与备注，并记录操作者、时间和版本
   - 批量操作必须逐项校验当前级次；禁止跳级、重复审批和自审自批
   - 只有最终批准且 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 全部通过后才允许进入打款

4. **提现记录**（三角色）
   - Admin：全局提现记录
   - Leader/Creator：自己的提现记录
   - 状态追踪：申请中 → 审批中 → 已打款 / 已拒绝

**涉及表**：
- `settlements`（结算单）
- `settlement_items`（结算明细）
- `withdrawals`（提现申请）
- Required：审批流程定义、审批实例/步骤、收款凭证、打款幂等记录和状态变更审计

**API 追踪**：`02` 第 4.3 节与三角色 candidate inventory 已拆分结算、提现、多级审批和打款目标；唯一 `operationId` 与 Test ID 在 `A-001-SPEC` 冻结时登记，已实施 route/spec 和 BFF Contract Test 另记入 `A-001-CONFORMANCE`。

#### 3.1.4 推广管理（知乎故事）

**功能描述**：统一目标入口，但逐项核验能力来源。存在旧页面只证明历史代码存在，不证明当前官方 API 支持或 v2 已迁移。

**分类定义**：

- `official-supported`：当前官方文档/真实联调证明确认支持；可按官方契约建设。
- `legacy`：旧页面、旧接口或历史实验能力；兼容期只读/受控，不计作 v2 完成。
- `custom`：本地自建业务能力；必须拥有独立 DB/API/UI/Test，不伪装成官方功能。

| Feature ID | 模块 | v2 分类 | 当前状态 | 目标入口与处置 |
|------------|------|---------|----------|----------------|
| PROMO-001 | 推广任务 | `official-supported` 候选，待锁定官方版本证据 | `PARTIAL` | `tasks`；核验 CRUD/状态能力，不能以旧页代验收 |
| PROMO-002 | 推广计划 | `official-supported` 候选，待锁定官方版本证据 | `PARTIAL` | `plans`；创建与本地落库采用幂等/outbox |
| PROMO-003 | 推广作品 | `official-supported` 候选，待锁定官方版本证据 | `PARTIAL` | `works`；上传、审核、删除分别核验，不默认全部支持 |
| PROMO-004 | 盐选榜单 | `legacy` | `PARTIAL` | `ranking`；官方证据不足时保持 unavailable/只读 |
| PROMO-005 | 评论截流 | `legacy`，规则配置可拆为 `custom` | `PARTIAL` | `intercept`；官方查询与本地规则分开追踪 |
| PROMO-006 | 风险举报 | `legacy` | `PARTIAL` | `risk`；查询、申诉能力逐项核验 |
| PROMO-007 | 有声书 | `legacy` | `PARTIAL` | `audiobook`；不宣称已迁移 |
| PROMO-008 | 漫画 | `legacy` | `PARTIAL` | `comic`；不宣称已迁移 |
| PROMO-009 | 内容标签 | `legacy` | `PARTIAL` | `content-tag`；管理能力需官方证据 |
| PROMO-010 | 产品库 | `legacy` | `PARTIAL` | `products`；查询能力需官方证据 |
| PROMO-011 | 素材库 | `custom` 候选 | `PARTIAL` | `materials`；补本地文件、权限和审计模型 |

**数据策略**：禁止使用“全部直调、不落库”的笼统规则。每个模块分别决定官方源、必要本地快照、outbox、缓存和审计；任何运营收益字段均标记不可结算，不能进入 `D-001-READINESS` 的权威财务链。

**API 追踪**：仅为核验通过的 `official-supported`/`custom` 条目分配 Required 端点；`legacy` 端点单独登记兼容期，不计作新功能完成。

**迁移 exit gate**：官方文档版本/路径、请求响应样例、角色范围、DB 策略、UI 状态和自动化测试六项齐全后，单个模块才可由 `PARTIAL` 升为 `IMPLEMENTED` 并下线旧路由。

### 4.3 推进规则

- 下游可以做接口草图或 Mock，但上游 exit gate 未通过时不得标 `IMPLEMENTED`，不得接入生产数据。
- D-001 总称不阻塞非财务基础工作；M0 先关闭 `A-001-SPEC` 的目标 OpenAPI/Contract/测试库 Gate。M0 可以在 `D-001-DECISION` 开放时完成规格冻结，但该 Gate 未关闭时财务范围只允许 Mock、协议设计和非财务工作，即使隔离沙箱也不得实施实际 adapter、匿名样例导入、审批、中继或对账。关闭后，才可在隔离沙箱以实际 adapter、匿名样例、审批、幂等、中继、冲正和对账证据评审 `D-001-READINESS`；`D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 任一未通过时，生产结算、余额、提现和打款始终保持 `BLOCKED`，不能反向阻断 M0 规格冻结。
- 账户/项目必须先于推广；基础归属和中继必须先于结算。任何倒序排期需更新 `00` 并由用户确认。

## 六、验收标准

### 6.1 功能验收标准

#### 6.1.1 通用标准

| 验收项 | 可判定标准 |
|--------|------------|
| **操作完整性** | 仅对附录 A 明确要求 C/R/U/D 的资源验收对应操作；只读、审计、结算记录不得为凑“CRUD”提供删除接口 |
| **权限隔离** | 每个 Required API 至少覆盖 Admin/Leader/Creator 的允许角色、拒绝角色和跨 owner/项目访问；预期状态码与响应字段写入测试 |
| **删除与审计** | 用户、订单、结算等按矩阵执行软删除；订单仅 Admin 且仅 `draft/cancelled` 可删；财务批次、审批和计算日志不可覆盖删除 |
| **校验** | 前后端使用同一字段约束；必填、边界、枚举、金额精度、重复请求均有确定错误码和自动化用例 |
| **交互性能** | 以 `05` 第 8 节为唯一性能口径：API P95 < 500ms、P99 < 1s、HTTP 错误率 < 0.5%、关键写操作业务成功率 ≥ 99.5% |
| **100 并发模型** | 专用性能环境；10,000 用户、5,000 项目、100,000 订单、100,000 结算、1,000,000 收益明细、5,000,000 中继日志；预热 5 分钟、5 分钟 Ramp 到 100 并发、稳定 30 分钟、降载观察 2 分钟；无观测值时读写 80:20；无重复写入或金额不平 |
| **大文件/导出** | 不计入交互 API 门槛；使用异步任务，返回 job ID，并验收进度、失败、重试、权限和下载过期策略 |

#### 6.1.2 核心功能验收

| 功能模块 | 可判定标准 |

### 附录 C：已确认约束的落地解释

本节保留用户原答案，但将其转换为可实现约束；不得由审核报告另行赋值。

1. **子账号权限**：首版采用粗粒度功能角色，但后端行级 owner/组织/项目校验仍为 Required；“数据来自 Admin”不能作为省略权限检查的理由。
2. **结算周期**：可配置，默认每月 1 日生成上月结算；修改周期需审计且不追溯改变已生成结算单。
3. **提现限额**：Admin 可配置，默认不设最低/最高值；即使无限额也必须校验余额、精度、正数和单据幂等。
4. **软删除保留**：物理清理为可开启项，默认不删除；启用前必须定义保留期、归档、法务/财务例外和恢复流程。
5. **并发控制**：订单使用 `version` 乐观锁；财务审批/余额扣减使用数据库事务与行锁/等价原子条件，且有并发测试。
6. **通知渠道**：站内 WebSocket 为 D-009 Required；邮件/短信/企业微信作为可配置 adapter，不阻塞首版。
7. **导出**：工单类列表进入导出范围；权限、脱敏、异步 job、过期下载和审计均需测试。
8. **批量操作**：单次最多 100 条；服务端强制限制并逐项返回成功/失败，不能只依赖前端。
