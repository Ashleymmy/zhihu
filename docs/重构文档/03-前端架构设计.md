## 0. 文档优先级与锁定决策

发生冲突时按以下顺序处理：

1. 用户已确认且在本节锁定的决策；
2. 经评审批准的 v2 API、数据库、安全和测试契约；
3. 本文的目标架构、迁移与验收规则；
4. 当前代码，仅用于盘点迁移起点和兼容行为；
5. v1 文档、旧示例和《文档审核报告》，仅保留历史参考价值。

以下决策已锁定，实施不得降级：

- 三个完全独立的前端应用：Admin、Leader、Creator 分别构建、部署和回滚。
- 所有应用支持响应式移动端，至少覆盖手机竖屏、平板和桌面。
- 首发语言为 `zh-CN` 与 `en-US`，功能、路由错误页和通知不得只覆盖单一语言。
- 订单、结算、审批等状态变更通过 WebSocket 实时通知；断线重连和事件补偿属于交付范围。
- 目标角色统一为 `admin | leader | creator`。旧值迁移映射固定为 `boss -> admin`、`leader -> leader`、`member -> creator`。
- Access Token 为短时凭证，只保存在运行时内存；Refresh Token 只由服务端通过 `Secure; HttpOnly; SameSite` Cookie 管理。
- Logout 必须调用服务端撤销 Refresh Token 家族，不能只清理浏览器状态。
- View 不解析 snake_case、不拼装响应 Envelope、不维护状态枚举映射；转换集中在共享 Contract/Adapter 层。
- BFF 对外只有一种 Wire Contract：成功、列表与失败均使用本文固定 Envelope；官方 upstream 的 `success/data/error` 结构只能由 Adapter 消化，禁止透传。
- 来源与中间金额使用固定 4 位十进制字符串；订单激活及其他业务审批边界之后才生成 `*AmountFen` 安全整数，并按 `HALF_UP` 舍入和记录差额审计。
- 结算与提现采用可配置财务多级审批，默认至少“业务复核 → 财务批准”两级；订单 activate 仍是独立的单级 Admin 金额边界，不得复用或伪装成财务审批级次。

## 三、应用内分层

每个应用遵循以下依赖顺序：

```text
View
  -> Page Composable / Page Store
    -> Domain Service
      -> Contract Adapter
        -> HTTP / WebSocket Transport
```

职责：

- **View**：渲染、收集输入、触发命令；不得直接解析 Wire 数据。
- **Page Composable/Store**：页面状态、加载/空态/错误态和取消请求。
- **Domain Service**：业务用例编排，不依赖 UI。
- **Contract Adapter**：Envelope、分页、角色、状态和 snake/camel 转换。
- **Transport**：认证头、Cookie、超时、重试、追踪 ID 和网络错误。
- **Utils**：无副作用纯函数。

禁止事项：

- View 中出现 `as any`、`response.data.data` 或 snake_case 字段。
- 用空 PATCH、仅本地改状态等方式模拟成功。
- 捕获错误后只显示空数据。
- 共享组件读取具体应用 Store。

## 四、统一 API Contract 与 Adapter

### 4.1 唯一 BFF Wire Envelope

BFF 的成功响应固定为以下唯一顶层结构：

```typescript
export interface ApiEnvelope<T> {
  code: 0
  message: string
  data: T
  meta?: PaginationMeta
  requestId: string
  timestamp: number
}

export interface PaginationMeta {
  page: number
  pageSize: number
  total: number
}
```

列表接口 Wire 规则为 `data: T[]` 且顶层 `meta` 必填。Wire 层不得混用 `items`、`list`、`page_size`，也不得把分页嵌入 `data`。应用内部如需 `PageResult`，只能由共享 Adapter 在解包后生成，不能改变线上响应。Mock、测试 Fixture 和真实 BFF 必须使用同一份 strict Schema。

失败响应固定为：

```typescript
export interface ApiFailure {
  code: number
  message: string
  details?: Record<string, string[]>
  requestId: string
  timestamp: number
}
```

失败 `code` 必须是非零、稳定的整数业务码，并由版本化映射表维护；HTTP Status 不能代替业务码。相同错误语义跨实例、Mock 和真实 BFF 必须得到相同 `code`，变更既有映射视为破坏性 Contract 变更。

成功、列表和失败 Schema 均拒绝未声明的顶层字段。知乎官方 upstream 的 `success/data/error` 响应只允许进入 `alliance.adapter.ts`：Adapter 将成功数据映射为 `code: 0` Envelope，将 upstream 错误映射为稳定非零业务码；`success` 与 `error` 不得出现在 BFF 对外响应、View、Store 或公共 Mock 中。

#### M0 Contract 冻结与已实施切片一致性

M0 的 `A-001-SPEC` 只冻结目标 OpenAPI 3.1 Schema、唯一 `operationId`、权限/错误/幂等/审计/Test ID、共享 Mock Fixture 与目标注册表。目标注册表必须明确每个 operation 是 `planned`、`implemented` 还是 `legacy/deprecated`；`planned` 只接受 Schema 与 Fixture 静态 Contract 验证，不能冒充有真实路由或真实 BFF 覆盖。

`A-001-CONFORMANCE` 只对声明为 `implemented` 的切片执行：实际 route 无未登记项、runtime spec 无不存在的 implemented operation、Mock 与真实 BFF 共用本节 Schema，并通过真实 BFF Contract Test。该 Gate 按里程碑累计，M6 才要求全部 Required implementation 为 100%。

### 4.2 金额分层契约

金额分为两个不可混用的阶段：

| 阶段 | 字段 | Wire 类型 | 后端存储与计算 | 前端规则 |
|---|---|---|---|---|
| 来源/中间值 | `unitPrice`、`rawAmount`、`calculatedAmount` | 固定 4 位十进制字符串 | `DECIMAL(18,4)` 或等价精确十进制 | 保持字符串，不得转为 JS `number` |
| 审批后最终值 | 订单 `payableAmountFen` 及结算、提现、退款、支付的 `*AmountFen` | 安全整数 | 整数列；由服务端对应业务边界生成 | 可作为安全整数消费，不得反推覆盖来源值 |

共享 Contract 的最低校验：

```typescript
const decimal4Schema = z.string().regex(
  /^-?(?:0|[1-9]\d{0,13})\.\d{4}$/,
  '金额必须是 DECIMAL(18,4) 对应的固定 4 位十进制字符串'
)

export type Decimal4String = z.infer<typeof decimal4Schema>

const safeAmountFenSchema = z.number()
  .int()
  .refine(Number.isSafeInteger, '*AmountFen 必须是 JS 安全整数')

export interface CalculationAmounts {
  unitPrice: Decimal4String
  rawAmount: Decimal4String
  calculatedAmount: Decimal4String
}

export interface OrderActivationAmount {
  payableAmountFen: number
  roundingMode: 'HALF_UP'
  roundingDelta: Decimal4String
}
```

- 服务端从数据库读取 `DECIMAL(18,4)` 时必须保留字符串，禁止经浮点数往返后再序列化。
- 前端禁止对 4 位小数字符串使用 `Number`、`parseFloat`、一元 `+` 或原生浮点算术；校验、比较和展示统一走共享精确十进制/金额工具。
- 创建订单只接受来源字段并返回 `draft`；服务端精确生成 `calculatedAmount`，响应不得包含任意 `*AmountFen`。
- Admin 调用 `POST /api/v1/admin/orders/:id/submit`，或订单所属范围内 Leader 调用 `POST /api/v1/leader/orders/:id/submit`，只执行 `draft -> pending` 并锁定精确草稿，不生成整数分。
- 只有 Admin 调用 `POST /api/v1/admin/orders/:id/activate` 才执行 `pending -> active`。这是订单金额审批边界：服务端在事务内重算并核对草稿，再生成 `payableAmountFen = HALF_UP(calculatedAmount × 100)`；订单没有独立的“批准”动作。
- 所有 `*AmountFen` 在出站前必须通过 `Number.isSafeInteger`；超范围时拒绝处理，不能截断或转科学计数法。
- 订单激活记录原始 `calculatedAmount`、`HALF_UP`、最终 `payableAmountFen`、`roundingDelta`、操作者、时间和 `requestId`。`roundingDelta = payableAmountFen / 100 - calculatedAmount`，以固定 4 位十进制字符串保存。
- 后续 `paymentAmountFen/refundedAmountFen` 只能消费订单激活快照；结算、提现与打款使用各自契约定义的 `*AmountFen`。所有来源/中间字段保留用于审计，不能被最终值反向覆盖。

### 4.3 Camel Case 边界

- 前端与 BFF 的公开契约统一 camelCase。
- 数据库 snake_case 由服务端 Serializer 转换。
- 知乎联盟 snake_case 由 `alliance.adapter.ts` 转换。
- 原始响应只有 Adapter 和 Contract Test 可以读取。

示例：

```typescript
const earningsStatusSchema = z.enum(['pending', 'confirmed', 'paid'])
export type EarningsStatus = z.infer<typeof earningsStatusSchema>

const legacyEarningsStatus: Record<string, EarningsStatus> = {
  pending: 'pending',
  locked: 'confirmed',
  confirmed: 'confirmed',
  settled: 'paid',
  paid: 'paid'
}

export function toEarningsStatus(value: unknown): EarningsStatus {
  if (typeof value !== 'string') throw new ContractError('收益状态不是字符串')
  const normalized = legacyEarningsStatus[value]
  if (!normalized) throw new ContractError(`未知收益状态：${value}`)
  return normalized
}
```

状态转换只保留在兼容期 Adapter 中。兼容期结束后，未知旧值必须成为 Contract Error，而不是显示成错误标签。

### 4.4 HTTP Client 行为

- Base URL：`/api/v1`。
- 公共认证端点：`/api/v1/auth/login|refresh|logout|me`。
- 请求超时默认 15 秒；幂等 GET 最多自动重试 1 次，写请求不自动重试。
- 401 触发单飞 Refresh；Refresh 失败才清理内存状态并跳转登录。
- 403 保留会话，显示可追踪错误和 `requestId`。
- 请求取消使用 `AbortSignal`。
- 所有页面必须有 loading、empty、error、retry 四态。

## 五、认证、角色与权限

### 5.1 Token 安全模型

登录成功：

1. `POST /api/v1/auth/login` 返回短时 `accessToken`、`expiresIn` 和规范化用户；
2. 服务端同时写入 Refresh Cookie；
3. Access Token 只放 Pinia 内存，不写 `localStorage`、`sessionStorage`、IndexedDB 或可读 Cookie；
4. Refresh Token 不出现在 JSON、日志、埋点和前端 JavaScript 中。

Refresh Cookie 最低要求：

```text
Secure; HttpOnly; SameSite=Lax; Path=/api/v1/auth
```

跨站部署确需 `SameSite=None` 时必须同时启用 `Secure`、严格 CORS、Origin 校验和 CSRF Token，经安全评审后才能变更。

Logout：

1. 调用 `POST /api/v1/auth/logout`；
2. 服务端撤销当前 Refresh Token 家族并清除 Cookie；
3. 前端清理 Access Token 和用户状态；
4. 服务端失败时前端可清理本地状态，但必须记录失败，不能把服务端撤销标记为成功。

### 5.2 Store 示例

```typescript
interface SessionState {
  accessToken: string | null
  expiresAt: number | null
  user: AuthUser | null
}

export const useAuthStore = defineStore('auth', () => {
  const session = reactive<SessionState>({
    accessToken: null,
    expiresAt: null,
    user: null
  })

  const isLoggedIn = computed(() =>
    session.accessToken !== null &&
    session.expiresAt !== null &&
    session.expiresAt > Date.now()
  )

  async function login(input: LoginRequest): Promise<void> {
    const result = await authService.login(input)
    session.accessToken = result.accessToken
    session.expiresAt = Date.now() + result.expiresIn * 1000
    session.user = result.user
  }

  async function restore(): Promise<boolean> {
    const result = await authService.refreshWithCookie()
    if (!result) return false
    session.accessToken = result.accessToken
    session.expiresAt = Date.now() + result.expiresIn * 1000
    session.user = result.user
    return true
  }

  async function logout(): Promise<void> {
    await authService.logoutAndRevoke()
    session.accessToken = null
    session.expiresAt = null
    session.user = null
  }

  return { session, isLoggedIn, login, restore, logout }
})
```

### 5.3 角色迁移

| 旧值 | 目标值 | 兼容行为 |
|---|---|---|
| `boss` | `admin` | 服务端读旧值并输出 `admin` |
| `leader` | `leader` | 不变 |
| `member` | `creator` | 服务端读旧值并输出 `creator` |

- 新 Token、新 API 和新前端只使用目标值。
- 迁移期间服务端可双读，不得继续写入 `boss/member`。
- 角色迁移需审计未知值；未知值拒绝登录，不能默认提升权限。
- 每个应用 Router 在进入业务路由前验证唯一目标角色；服务端再次验证。

#### 6.1.1 财务多级审批界面状态

结算与提现详情使用同一套审批时间线和职责分离提示。资源进入审批时必须展示并保留服务端冻结的 `approvalPolicyVersion`、`requiredApprovalLevels`、`currentApprovalLevel` 与 `version`；后续策略发布新版本不能改写在途实例。默认策略至少有以下两个独立级次：

1. Level 1“业务复核”：核对来源批次、结算对象、申请信息与金额；
2. Level 2“财务批准”：由另一名具备财务批准权限的人员完成最终批准。

| 服务端状态与级次 | 页面状态 | 可用操作 | 必须禁止或提示 |
|---|---|---|---|
| `draft` | 可编辑，尚未进入审批 | 申请人提交；可放弃草稿 | 不显示批准或打款操作 |
| `pending_approval`，`currentApprovalLevel = 0` | “待业务复核”，时间线高亮 Level 1 | 当前级且具备业务复核权限的人员可批准或驳回；申请人可撤回 | 申请人和结算来源批次上传人不得自批；打款不可用 |
| `pending_approval`，`currentApprovalLevel = 1` | “业务已复核，待财务批准”，显示 Level 1 操作者与审计时间 | 当前级且具备财务批准权限的另一人可批准或驳回；申请人可撤回 | Level 1 审批人不得占用 Level 2；打款不可用 |
| `approved` | “审批完成”，完整展示策略版本、两级轨迹和 `requestId` | 仅具备打款权限者可尝试创建打款意图 | `D-001-DECISION`、`D-001-READINESS`、P0-008 或 M6 生产 Gate 任一未通过时按钮保持禁用；若服务端返回 `50310`，只按响应中的非空、去重、稳定顺序 `failedGates` 显示精确失败子集与 `requestId`，客户端不得猜测、补充或绕过 Gate |
| `payment_pending` | “打款处理中” | 查询支付渠道结果 | 禁止重复创建打款意图 |
| `paid` | “已打款” | 查看脱敏凭证和审计轨迹 | 全部资金操作只读 |
| `rejected` | “已驳回”，展示级次、原因和操作者 | 申请人修改后生成新版本并重新提交 | 禁止沿用旧审批级次或旧策略快照继续批准 |

申请人撤回应终止当前审批实例、回到可编辑草稿并递增 `version`；历史时间线保留“已撤回”记录，重新提交时创建新的策略快照和完整审批链。批准、驳回、撤回和打款提交都携带资源 `version` 与 `Idempotency-Key`：请求处理中禁用重复操作；重复请求复用同一结果；并发冲突时刷新服务端状态并显示可复制的 `requestId`，不得在客户端自行递增级次。

`50310 FINANCE_GATE_BLOCKED` 不是前端可恢复成成功的状态：页面只展示服务端返回的精确 `failedGates` 和 `requestId`，不得把“未创建打款”当作成功。服务端保留一次同一 `requestId` 与相同 `failedGates` 的拒绝审计，前端不创建 payment intent、支付流水、余额占用或任何资金状态。

订单详情不使用上述时间线。`POST /api/v1/admin/orders/:id/activate` 仅由 Admin 完成一次 `pending → active` 金额激活，不产生 Level 1/Level 2 财务审批记录，也不能解除 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6 对生产结算、余额、提现或打款的阻断。

## 七、响应式、国际化与可访问性

### 7.1 响应式断点

| 档位 | Viewport | 最低要求 |
|---|---|---|
| Mobile | 360-767 px | 单列；抽屉导航；表格可切卡片或安全横向滚动 |
| Tablet | 768-1199 px | 1-2 列；可折叠侧栏 |
| Desktop | >=1200 px | 完整侧栏和多列信息密度 |

- 不允许水平溢出遮挡主要操作。
- 触摸目标至少 44×44 CSS px。
- Modal 在手机上使用全屏或底部抽屉。
- 图表随容器 ResizeObserver 自适应，并在卸载时释放。

### 7.2 i18n

- Locale 固定为 `zh-CN`、`en-US`。
- Key 位于 `packages/shared-i18n/locales/<locale>/*.json`，按领域拆分。
- 日期、时区和普通数字使用 Intl。来源/中间金额以固定 4 位字符串进入共享金额格式器，业务边界后的金额以 `*AmountFen` 安全整数进入格式器；不得先转为浮点数再格式化。
- 用户选择保存为非敏感偏好；SSR 不适用时可存 `localStorage`，不得与认证凭证混用。
- CI 校验 Key 对称、插值参数一致和缺失翻译。

### 7.3 可访问性

- 目标 WCAG 2.2 AA。
- 所有核心流程支持键盘、可见焦点和合理焦点回退。
- 图标按钮必须有可翻译名称。
- 图表必须提供文本摘要或数据表替代。
- 自动化规则见《05-测试方案.md》。

## 八、WebSocket

共享连接管理器负责：

- 使用当前 Access Token 建连；Token 刷新后安全重连。
- 指数退避加抖动，最大 30 秒；离线期间暂停。
- 通过 `eventId` 去重，通过 `lastEventId` 补拉断线事件。
- 事件 Schema 校验、未知版本隔离、心跳和超时检测。
- 组件只订阅领域事件，不直接操作原生 Socket。

事件最小集合：

```typescript
type DomainEvent =
  | { type: 'order.updated'; eventId: string; orderId: string; occurredAt: string }
  | { type: 'settlement.updated'; eventId: string; settlementId: string; occurredAt: string }
  | { type: 'withdrawal.updated'; eventId: string; withdrawalId: string; occurredAt: string }
  | { type: 'notification.created'; eventId: string; notificationId: string; occurredAt: string }
```

WebSocket 不替代最终一致性查询。收到事件后 Service 按资源 ID 增量刷新；重连失败时展示离线状态并允许手动刷新。

## 九、迁移实施与回滚

### 9.1 分阶段实施

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| F0 契约冻结 | `A-001-SPEC`：唯一 Envelope、分页、upstream Adapter、金额分层、角色、状态、Token、目标 Schema、Mock Fixture 与 target registry | 静态 Schema/Fixture/注册表验证与评审记录签字；不要求未来全部真实 route 或真实 BFF Contract Test |
| F1 工程骨架 | Monorepo、3 应用、共享包、CI | 三应用独立启动/构建，尚不切生产流量 |
| F2 基础能力 | 认证、Router、i18n、响应式 Shell、WebSocket | 三角色登录隔离和基础非功能验收通过 |
| F3 业务迁移 | 按页面矩阵迁移，旧应用继续服务 | 新旧结果对账，关键流程 E2E 通过 |
| F4 灰度切换 | 按角色和租户逐步导流 | 错误率、P95、业务成功率满足门槛 |
| F5 收尾 | 旧 URL 兼容观察、旧应用归档 | 兼容窗口结束且回滚窗口关闭 |

禁止一次性删除 `platform/` 后再补功能。每个页面必须有负责人、目标 App、API、旧 URL、测试和回滚 Flag。

F1～F4 每新增一个已实施 API 切片，必须登记 `A-001-CONFORMANCE` 证据：真实 route/spec 双向 coverage、共享 Schema 的 Mock/真实 BFF Contract Test 和对应 Test ID。F0 的目标契约冻结不等同于前端或 BFF 已实现。

### 9.2 API 兼容

- 旧无角色前缀接口在兼容窗口内由 BFF Alias 转发，响应也必须进入统一 Envelope。
- 新前端不得调用旧 Alias；Contract Test 会阻止新增引用。
- 旧字段和旧状态只在 Adapter 双读，服务端只写目标格式。
- Alias 命中率、转换失败率和未知枚举进入监控。

### 9.3 Token 切换

旧 `localStorage` Token 不迁移、不上传、不兑换。首次进入新应用时：

1. 清理已知旧认证 Key；
2. 尝试 Refresh Cookie 恢复；
3. 无 Cookie 则要求重新登录；
4. 记录匿名迁移结果，不记录 Token。

### 9.4 回滚

- 每个应用使用独立 Feature Flag 和不可变镜像，可按角色回切旧前端。
- F0-F4 期间 API 和数据库变更保持向后兼容。
- 回滚只切前端流量，不回滚已成功业务写入。
- 若新旧状态含义不同，先停止写入、完成对账，再决定回切。
- 触发条件：5 分钟滚动窗口内前端未处理异常率 > 1%、关键流程成功率下降 > 2 个百分点，或认证失败率 > 0.5%。
- 回滚后保留日志、Trace 和失败样本，禁止用清缓存掩盖问题。

### 10.2 环境变量

```dotenv
VITE_API_BASE_URL=/api/v1
VITE_WS_URL=wss://api.example.com/ws
VITE_DEFAULT_LOCALE=zh-CN
VITE_SUPPORTED_LOCALES=zh-CN,en-US
```

- Nginx 支持 SPA fallback、API/WS 代理、安全 Header 和限流。
- WebSocket 代理必须配置 Upgrade/Connection、合理空闲超时和连接数监控。

## 十一、验收标准

### 11.1 架构与迁移

- [ ] 存在 3 个独立应用和约定共享包，三应用可独立构建、部署、回滚。
- [ ] `turbo.json` 使用 `tasks`，根脚本与实际包脚本一致。
- [ ] 当前页面全部进入迁移台账，每项都有目标路由、API、测试和 Flag。
- [ ] 旧 URL 兼容测试覆盖刷新、书签、查询参数和角色跳转。
- [ ] 新应用源码没有旧无角色前缀 API 的新增调用。

### 11.2 认证与权限

- [ ] 新应用没有认证 Token 的 `localStorage/sessionStorage/IndexedDB` 写入。
- [ ] Refresh Token 只存在于符合要求的 Cookie。
- [ ] Logout 服务端撤销测试通过。
- [ ] `boss/member` 迁移为 `admin/creator`，未知角色拒绝访问。
- [ ] 三应用与服务端的角色、权限和行级数据隔离测试全部通过。

### 11.3 Contract

- [ ] `A-001-SPEC` 的目标 Schema、Mock Fixture 和 target registry 已静态验证；只有标为 `implemented` 的切片才要求 Mock 与真实 BFF 通过同一 Envelope、分页和 Schema Contract Test，并计入 `A-001-CONFORMANCE`。
- [ ] 成功 `code: 0`，列表使用 `data: T[]` 与顶层 `meta`；失败使用稳定非零整数 `code`，且三类响应均无 upstream 顶层字段泄漏。
- [ ] View 中没有 snake_case、Envelope 解包、状态映射和显式 `any`。
- [ ] 收益状态统一为 `pending/confirmed/paid`。
- [ ] 订单 create 返回 `draft` 且无 `*AmountFen`，submit 只执行 `draft -> pending`，Admin activate 通过 `/api/v1/admin/orders/:id/activate` 执行 `pending -> active` 并生成安全整数 `payableAmountFen`；`HALF_UP` 与 `roundingDelta` 审计可追溯。
- [ ] 结算与提现默认“业务复核 → 财务批准”两级；页面展示冻结的策略版本和当前级次，并禁止申请人/批次上传人自批、同一人占两级、最后一级前打款及绕过 `D-001-DECISION`、`D-001-READINESS`、P0-008 与 M6；驳回、撤回、重复和并发操作状态可恢复且可审计。
- [ ] 订单 activate 与财务多级审批在页面、权限、时间线和 Test ID 中保持独立，不能互相替代。
- [ ] Contract Error 可观测，且不会伪装成空数据。

### 11.4 移动端、i18n、WebSocket

- [ ] 360、390、768、1024、1440 px 核心流程无阻断性溢出。
- [ ] `zh-CN/en-US` Key 完整率 100%，核心流程没有未翻译文案。
- [ ] 键盘和自动化可访问性检查达到 WCAG 2.2 AA 门槛。
- [ ] WebSocket 断线重连、事件去重、补偿和 Token 刷新测试通过。

### 11.5 性能与稳定性

详细负载模型以《05-测试方案.md》为准。前端发布最低门槛：

- 生产构建无 TypeScript/ESLint Error。
- 关键页面在规定数据量和测试环境下，API P95 < 500 ms、错误率 < 0.5%。
- 移动端 Web Vitals：LCP P75 <= 2.5 s、INP P75 <= 200 ms、CLS P75 <= 0.1。
- 30 分钟稳定性测试期间无持续增长的内存、Socket 或事件监听器泄漏。

任一必选项未通过时状态保持“实施中”或“阻塞”，不得标记完成。
