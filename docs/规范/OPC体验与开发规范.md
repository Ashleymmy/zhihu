## 2. 产品是什么，给谁用

OPC 是**项目聚合平台**：平台负责人员、团队、项目、任务、作品、收益和提现；每个推广项目以模块形式接入。知乎关键词推广是第一个试运行项目，不是平台本身。

| 使用者 | 是谁 | 主要设备 | 他想要什么 |
| --- | --- | --- | --- |
| 达人 | 人数最多，多为兼职或闲散人员，不懂系统、不看说明 | 手机（小程序为主） | 有什么任务、交什么、能拿多少钱、什么时候能提现 |
| 团长 | 带一个小团队的运营者 | 手机和电脑 | 给成员分任务、看谁没交、核验作品、看团队和自己的收益 |
| 管理员·运营 | 平台内部运营 | 电脑 | 建任务和分发、管人、处理数据问题 |
| 管理员·财务 | 平台内部财务 | 电脑 | 上传报表、核对金额、付款 |

**判断一个设计好不好，就问一句：一个第一次用、不看说明的达人，能不能在手机上完成他要做的事？**

## 3. 架构边界

### 3.1 平台和项目模块

- 平台公共核心：`server/src/core`、`server/src/auth`、`packages/shared-*`、`apps/platform-admin` 的公共页面。
- 项目模块：`server/src/modules/<项目>`、前端 `apps/module-views/<项目>`。知乎是 `zhihu`。
- **平台代码不能引用任何项目模块的实现，也不能查询项目模块的表。** 项目通过 `server/src/core/contracts.ts` 的契约接入。
- **新增通用能力（待办、任务、作品、收益明细、计费规则、分析过程）放在平台层**，项目只实现提供器或写入平台表。不要在知乎模块里再做一套平台已有的东西。
- 项目专属的功能（知乎的渠道名称映射、报表解析、盐选榜单等）放在项目内部，只通过“项目设置 → 项目工具”或任务详情进入，**不加一级导航**。

### 3.2 导航

- 一级导航按角色要做的事组织，见平台方案第 4 节。每个角色不超过 8 项。
- **不准新增“更多功能”、聚合页、模块自己的工具栏**这类平行导航。
- 占位功能（未接通、开发中）不出现在任何导航和首页。
- 旧页面下线时保留路由，打开后说明“已合并到 ××”并给出前往按钮。

### 3.3 资金

- 资金账在平台层（`core/finance.ts`、`opc_income_*`）。项目只负责算出“谁、因为什么、多少钱”，写入平台收益明细。
- 已确认的账不修改；任何变化用更正行表达。
- 所有金额用字符串和整数运算处理（现有 `money()` / `cash()`），不用浮点数。
- 金额计算和归属判断只用确定的规则，**不交给 AI 模型**。

## 4. 体验规范（“人味儿”）

### 4.1 十二条硬规则

1. **每个页面只有一个主要动作**，用主按钮样式；其他动作用次要样式或放进“更多”。
2. **每个“卡住”的状态都必须写清三件事**：为什么卡住、谁来处理、点哪里处理。格式为“下一步：谁：做什么”，后面跟按钮。
3. **不整份拒收。** 批量处理（报表、导入）时，好的部分照常处理，有问题的部分单独列出并给出原因。
4. **不静默丢弃。** 用户提交的每一条数据都要在结果里出现，并带状态。
5. **不设死路。** 不能出现“请联系管理员”“请到其他页面处理”之后就没有下文的提示；要么当场能处理，要么写明谁会处理，并让那个人在自己的首页待办里看到。
6. **修一处，自动更新。** 用户补齐资料后，相关结果自动重算，不要求重新上传，不要求点“重新计算”，不要求填写理由（系统自己记审计）。
7. **不暴露内部用语。** 见 4.3 节禁用词。
8. **空状态要说下一步。** 不写“暂无数据”，要写“还没有任务。去任务大厅领一个”，并给按钮。
9. **错误提示 = 发生了什么 + 怎么办 + 按钮。** 不显示错误码、接口名、英文报错。
10. **危险操作要说清后果。** 例如“停用后，王团长的 3 个进行中任务会暂停”，而不是“确定停用吗？”。
11. **不靠加说明文字解决流程问题。** 如果需要一大段文字解释怎么用，说明流程设计错了，应该改流程。
12. **数字可以点开看来源。** 金额、订单数、待办数量都能点开看到明细和计算过程。

### 4.2 写给谁看

- 达人页面用“你”，句子短，一句话一件事；不出现管理概念（项目配置、接入、规则代码）。
- 团长页面强调“团队”和“谁还没做”。
- 管理员页面可以出现业务术语，但仍然不出现技术术语。

### 4.3 用词

**统一用词**（与平台方案 3.1 节一致）：项目、渠道、任务、作品、业绩、收益、提现、执行人、团长、达人、独立达人、单价、团队分成。

**业绩类型**：同一项目可以有多种业绩类型，各自计量、各自计价，不能相加成一个数量。知乎目前有两种：**拉新**（订单量，单位“单”）和**拉活**（拉活量，单位“个”）。规则如下：

- 类型来自数据源本身（上传前的类型选择 + 表头核对），**前端不按价格、文件名、角色猜测类型**，也不在客户端计算金额。
- 同一天同一关键词的不同类型业绩是两条独立数据，不互相覆盖。
- 页面上凡是出现数量和金额，都要标明类型；汇总时分类型显示，再给出金额合计。

**状态用词**：

| 对象 | 用词 |
| --- | --- |
| 任务 | 可领取、待分配、待交作品、作品审核中、生效中、有争议、已停用 |
| 作品 | 待审核、已通过、已退回 |
| 收益 | 平台核对中（团长和达人看到的“待处理”）、待确认、已确认、可提现、提现中、已到账 |
| 分析步骤 | 进行中、完成、需要你看一下、失败 |

**禁用词**（界面上不准出现，左边是代码里的概念，右边是界面用词）：

| 不要写 | 写成 |
| --- | --- |
| 绑定、binding | 执行人 / 分配 |
| 归因、归因引擎 | 计算归属 / 算钱（或不提） |
| 事实、fact、义务、obligation | 一行数据 / 应得金额 |
| 批次、batch | 这份报表 |
| 快照、版本、修订、revision | 原值 / 新值 / 更正 |
| 草稿、draft | 待确认 |
| 切换边界、生效边界、引擎路由、试算 | 试运行 / 正式（只在项目设置里出现） |
| 接入账号、integration、legacy、module | 项目接入（只在项目设置里出现） |
| 渠道映射 | 报表里的渠道名称 |
| 原因码（`BINDING_MISSING` 等） | 4.4 节的状态用词 |
| OPC / WORKSPACE、Desk、Powered by | 不写 |
| 推广任务（知乎上游） | 推广活动 |

**格式**：

- 金额：`¥1,234.00`；收益相关一律保留两位小数。
- 日期：同一年内写 `10-08`，跨年或表头写 `2026-10-08`；时间写 `10-08 14:30`。
- 人：显示姓名，不显示用户 ID、用户名；需要区分角色时加角色标签。
- 数量：“3 个任务”“5 单”，数字和量词之间不加空格以外的符号。

### 4.4 原因与下一步对照（知乎项目）

| 原因 | 状态用词 | 下一步 |
| --- | --- | --- |
| 渠道名称没对上 | 渠道没对上 | 运营：确认渠道 |
| 关键词不存在 | 系统里没有这个关键词 | 运营：登记并指定执行人 |
| 没有执行人 | 没有执行人 | 运营：指定执行人 |
| 团长领了未分配 | 待分配 | 团长：分配执行人 |
| 执行人开始日期晚于报表日期 | 早于执行人开始日期 | 运营：确认从哪天算 |
| 没登记作品 | 还没有登记作品 | 达人：补登记作品 |
| 作品未核验 | 作品待核验 | 团长或管理员：核验作品 |
| 缺单价 | 单价还没设置 | 财务：设置单价 |
| 两份报表数字不同 | 两份报表数字不同 | 财务：选用哪个数 |
| 风险判定 | 知乎标了风险 | 运营：核实 |

新项目接入时，按同样的格式补充自己的原因对照。

## 5. 交互模式库

新页面优先套用以下模式；需要新模式时，先在本节补充，再实现。共享组件放在 `packages/shared-components`。

### 5.1 分析过程面板

**用在哪里**：任何超过一步的后台处理，包括报表上传、批量导入作品、数据同步。

**长什么样**：参照 `prototypes/report-analysis/index.html` 的左栏。

- 顶部：文件或任务名、来源、时间。
- 中部：步骤列表。每步有状态图标、标题、一句话结论；需要人决定的步骤显示橙色提问框，框内直接放选项按钮。
- 底部：结论卡片，包括最重要的一个数字、还需要做几件事，以及 1–2 个按钮（例如“先处理待办”“按人员核对”）。

**规则**：

- 每一步的结论是一句完整的人话，由后端按模板生成。
- 提问只问人能回答的问题，选项不超过 3 个，必须有一个“先跳过”或“这行不计费”之类的退路。
- 关掉页面再打开，能看到同一次处理的进度和结果。

### 5.2 多维表格

**用在哪里**：任何需要核对、跟进的列表，包括报表结果、任务列表、作品核验、收益明细、提现审核。

**长什么样**：参照原型的右栏。

- 视图切换（2–3 个，一个默认视图，一个“需要跟进”带数量角标）。
- 分组：默认按状态分组，最需要处理的组排最前面，组标题写行数和这一组意味着什么。
- 状态列用颜色标签：绿色表示完成或可确认，橙色表示等别人，红色表示需要处理，灰色表示中性，紫色表示团长标识。
- 最后一列是“下一步”：“谁：做什么” + 按钮。
- 底部合计行，随筛选变化。
- 点击一行打开右侧抽屉，显示详细信息和计算过程。
- 手机宽度下变成卡片列表，每张卡片包括标题、状态、关键数字、下一步。

**规则**：

- 不在表格里显示数据库编号、哈希、状态码。
- 列数控制在 8 列以内；更多信息放抽屉。
- 表格内的按钮只放这一行的主要动作，最多 1 个。

### 5.3 抽屉、弹窗、整页

| 场景 | 用什么 |
| --- | --- |
| 查看一行的详情、计算过程 | 右侧抽屉 |
| 设置类内容（单价设置、渠道设置） | 右侧抽屉，不离开当前页 |
| 单个动作需要填 1–3 项（指定执行人、退回原因） | 小弹窗 |
| 危险操作确认 | 小弹窗，写清后果 |
| 多步骤流程 | 整页，或分析过程面板 |

不准弹窗套弹窗，不准抽屉里再开整页跳转。

### 5.4 待办卡片（首页）

- 一条待办 = 数量 + 一句话 + 点击直达处理位置，例如“3 个作品待核验”。
- 按角色只显示自己能处理的；全部处理完显示“都处理完了”和本期关键数字。

### 5.5 进度线（任务详情）

固定步骤：领取 → 分配 → 交作品 → 核验 → 出业绩 → 算钱 → 确认 → 可提现。完成的步骤显示绿色，当前步骤显示橙色并写明负责人，未开始的显示灰色。

## 6. 视觉规范

- 使用 `packages/shared-tokens` 的颜色和间距变量；不新建设计体系。
- 状态颜色固定：绿色（完成、可确认）、橙色（等待别人）、红色（需要处理）、灰色（中性）、紫色（团长）、蓝色（主操作、链接、选中）。
- 页面结构：标题（一行）、一句话说明（可选）、主操作，然后是内容。不要在标题上方放英文小标签。
- 表格行高 40–44px，数字右对齐，金额用等宽数字（`font-variant-numeric: tabular-nums`）。
- 所有页面在 375px 宽度下不出现横向滚动；表格在窄屏变卡片。
- 小程序与 Web 使用同样的状态颜色和用词。

---

## 7. 权限与数据隔离

- 权限在后端接口和 SQL 层面校验，前端隐藏只是辅助。
- **读接口同样校验岗位**：金额相关的读接口只对财务和全部职责开放；运营可以看业绩（订单数），看不到金额。
- 达人只能查到自己的数据；团长只能查到自己和自己团队的数据，并且看不到团队达人的个人金额（团队分成除外）。
- 每个新接口都要有一条“越权访问被拒绝”的测试。

## 8. 开发流程（给 AI 编码助手）

### 8.1 动手前

1. 读 `AGENTS.md` 和本文第 1 节列出的文档。
2. 说清楚这次改动影响哪些角色、哪些页面、哪些接口。
3. 如果改动涉及钱、权限、导航结构，先对照平台方案和本文，确认没有冲突。

### 8.2 实现时

- 新的通用能力放平台层（第 3 节）。
- 界面文案对照第 4 节；新状态先补到 4.3、4.4 节的表里。
- 不新增一级导航；不新增“更多功能”类入口。
- 不引入新依赖，除非现有依赖确实做不到，并在提交说明里写原因。

### 8.3 验证

每次改动至少完成：

1. 后端：`cd server && npm run typecheck`，以及相关测试，例如 `npx vitest run tests/attribution`。
2. 前端：在仓库根目录运行 `pnpm typecheck && pnpm build`。
3. 小程序改动：`cd weixin-app && npm test`。
4. **页面改动必须实际打开看**：用本地演示数据（8.4 节），以受影响的每个角色登录，在 1440px 和 375px 两个宽度下截图，逐条对照第 9 节的自查表。
5. 涉及钱的改动：补充或更新金额测试，覆盖财务方案 2.3 节的示例数据。

### 8.4 本地演示环境

```bash
# 依赖：MySQL 8、Redis 7（本机或 Docker 均可）。先按 .env.example 中的 DB_* 建库和用户，例如：
#   CREATE DATABASE zhihu_koc CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
#   CREATE USER 'zhihu'@'127.0.0.1' IDENTIFIED BY 'zhihu_local_password'; GRANT ALL ON zhihu_koc.* TO 'zhihu'@'127.0.0.1';
cp server/.env.example server/.env    # 把 OPC_MODULES 改成 zhihu，其余可保持默认
cd server && npm ci && npm run migrate && ADMIN_PASSWORD='Admin123456!' npm run bootstrap:admin
cd .. && corepack pnpm@9.15.0 install && corepack pnpm@9.15.0 build
cd server && npm run demo:review      # 启动服务并写入演示数据（仅首次写入），访问 http://127.0.0.1:3000/app/
```

### 8.5 提交

- 一次提交只做一件事；提交信息用英文祈使句，例如 `fix: keep unassigned keywords assignable after reports`。
- PR 描述用中文，写清：改了什么、为什么、影响哪些角色、怎么验证的（附截图）。

- [ ] 一个不看说明的达人能完成这个页面要做的事吗？

- [ ] 有没有数据被静默丢掉或整批拒收？
- [ ] 有没有出现禁用词、编号、状态码、英文？
- [ ] 空状态和错误提示都告诉了用户下一步吗？
- [ ] 数字都能点开看来源吗？
- [ ] 375px 宽度下没有横向滚动吗？
- [ ] 有没有新增导航入口？如果有，是否符合平台方案第 4 节？
