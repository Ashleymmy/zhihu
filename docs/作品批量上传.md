# 作品批量上传

入口在“推广作品 → 登记作品”弹窗右上角。管理员、团长、达人复用同一上传组件。

## 使用流程

1. 选择 Excel（`.xlsx` / `.xls`）或 CSV，单文件不超过 5 MB，每张工作表最多 1000 条、100 列。
2. 服务器读取真实文件内容，默认选择数据最多的工作表，并识别前 30 行内的表头。可以切换工作表、调整表头行和字段对应关系。
3. 检查预览中的可上传、重复、需补充记录。缺少分类时可指定默认分类，或主动选择“视频子分类均衡随机填充”；后者是按用户设置补填，不代表分析了视频内容。
4. 确认上传，仅保存通过校验的新作品。重复及不完整的记录跳过，可下载待补充清单。保存后列表刷新。

也可选择“保存本地，稍后推送”：将原文件、字段映射、分类设置和所有行的核对结果保存到数据库中的待推送批次，不向知乎提交。缺少本地计划或字段的行也会保留。作品列表下方可查看明细、下载原表、导出待推送 CSV，或“继续处理”重新读取原表并核对。相同账号再次保存同一文件和工作表会更新原批次，不新增第二个批次。

如果附有既有线上核对快照，匹配到的链接标注为“线上快照已存在”，不再次加入待推送数据。快照只表示当时的核对结果；统一推送前应在目标站点重新查重。CSV 导出保留已经补填的分类，不输出重复行。

支持“日期、平台id、平台、视频链接、关键词”等达人登记表列名；微信/QQ 联系方式不作为媒体账号。账号数字超出安全精度时要求修正为文本。日期按北京时间处理，只含日期时使用该日 00:00，并在预览说明。空日期不自动沿用前一行。

关键词必须精确匹配当前账号有权使用的未结束计划，同名计划要求提供计划编号。指定的默认计划只用于缺少关键词/计划编号的行，不能替换无法匹配的关键词。链接域名与媒体平台冲突时显示错误。

## 去重与保存

- 以规范化后的作品链接对比数据库已有作品及本次文件；所有既有状态（包括同步失败）都视为已登记，不修改已有作品。
- 去除首尾空白、链接片段及明确的分享跟踪参数。抖音分享文案提取出作品链接，保留短链接标识的大小写。
- 不请求或解析外部短链，因此同一视频使用不同短链接或长短链接时，不能据此保证识别为同一作品。
- 提交时重新分析文件并核对数据库，不接受客户端伪造的预览结果。导入之间用数据库锁串行化，事务内保存作品与审计记录，防止重复点击、网络重试和并发批量导入重复新增。
- 写入现有 `compositions` 表，使用原有计划权限和作品所属人规则，再提交原有知乎同步队列。同步排队不是知乎同步成功；列表继续显示真实同步和审核状态。
- 队列不可用时返回已保存数量及未入队作品编号，不把已经提交的数据库事务误报为全部失败。
- 演示账号不能调用真实导入，不返回虚构成功记录。

接口为 `POST /api/v1/modules/zhihu/compositions/import/analyze`、`/import/commit` 和 `/import/draft`，均使用登录与 `composition.create` 权限。请求为 multipart，包含 `file` 和 JSON 字符串 `options`。`GET /import/drafts` 获取批次列表，`GET /import/drafts/:id` 读取明细，`GET /import/drafts/:id/file` 下载原表；服务端按当前账号权限隔离批次。

部署需同时更新前后端，并执行 `server/schema/zhihu/027_composition_import_drafts.sql`（容器启动迁移会自动执行）。批次和原表存储在 MySQL 持久卷，不依赖临时目录，也不会由定时同步任务自动推送。

## 验证

- `npm --prefix server run test:unit -- composition-import-parser.spec.ts`
- 在 `server` 目录运行 `npx vitest run --config vitest.attribution.config.ts tests/attribution/composition-import.spec.ts`，需要 Docker；使用独立 MySQL 容器验证 multipart、实际落库、列表读取、审计、去重、并发和权限。外部同步队列在测试中隔离，不代表向知乎发送了测试数据。
- `npm --prefix server run build`
- `pnpm --filter platform-admin build`
