## 一、签名是干什么用的

### 类比理解

想象你要给银行寄一张纸质转账单。银行需要确认两件事：

1. **这张单子真的是你写的吗**（身份认证）
2. **单子在路上有没有被人改过**（防篡改）

签名机制就是解决这两个问题的。

- `access_token` 相当于你的**账号名**，告诉知乎「我是谁」
- `signature` 相当于你的**手写签名+防伪水印**，证明「这些参数确实是我发的，且没被改过」

如果有人在传输途中把 `keyword` 从「测试词」改成「垃圾词」，
那么参数变了，服务端重新算出来的签名就和你带的签名不一致，请求会被拒绝。

### 为什么还要 timestamp

`timestamp` 防的是**重放攻击**。

假设攻击者截获了你的一个「创建推广计划」请求（包含合法签名），
如果没有时间戳，他可以把这个请求重复发 10000 次，创建 10000 个垃圾计划——
因为每次的参数和签名都是合法的。

加上 `timestamp` 后，服务端会检查时间戳是否在允许的时间窗口内
（通常是几分钟），过期的请求直接拒绝。

> 官方 PDF 未明确说明时间窗口的具体长度。实践中按「本机时间误差不超过 1 分钟」
> 来要求即可。如果频繁遇到 `timestamp 无效`，先校准系统时间。

## 二、需要的两个凭证

向知乎运营申请开发者账号后，会拿到两个字符串：

| 凭证 | 字段名 | 作用 | 敏感级别 | 能否放前端 |
| --- | --- | --- | --- | --- |
| 开发者 Token | `access_token` | 身份标识，随请求发送 | 中 | ✅ 可以（本来就要发出去） |
| 签名公钥 | `secret_key` | 计算签名的密钥 | **极高** | ❌ **绝对不可以** |

### 关于 `secret_key` 命名的说明

文档里叫它「签名公钥」，但从密码学角度看它其实是**对称密钥**（HmacSHA256 的密钥），
行为上等同于**私钥**——泄露了就完蛋。

不要被「公钥」这个名字误导以为可以公开。

### 官方示例凭证

本文档全程使用官方 PDF 的示例数据。**这是假数据，仅用于验证算法，不能真调接口**：

```
access_token: Db6j0Yq0eppBb
secret_key:   a735eb11da74123074675fa3522a90d1
```

## 三、签名六步法

以官方示例为例，完整走一遍。

### 起点：业务参数

假设我们要创建一个推广计划，业务上需要传这 5 个参数：

```json
{
  "task_id": "1443567656205545123",
  "channel_id": "1462106336904909960",
  "content_url": "https://www.zhihu.com/market/paid_column/1550452094749851648/section/1590711798218661888",
  "popularize_type": 0,
  "keyword": "这是一个测试关键词"
}
```

---

### 步骤 ① 补充 `access_token` 和 `timestamp`

把身份信息和时间戳加进去。

```json
{
  "task_id": "1443567656205545123",
  "channel_id": "1462106336904909960",
  "content_url": "https://www.zhihu.com/market/paid_column/1550452094749851648/section/1590711798218661888",
  "popularize_type": 0,
  "keyword": "这是一个测试关键词",
  "timestamp": 1672899103,
  "access_token": "Db6j0Yq0eppBb"
}
```

**要点：**

- `timestamp` 是**秒级**时间戳，不是毫秒级
- JavaScript 里 `Date.now()` 返回的是毫秒，必须除以 1000 并取整

```typescript
// ✅ 正确
const timestamp = Math.floor(Date.now() / 1000)   // 1672899103

// ❌ 错误：这是毫秒，会导致 timestamp 无效
const timestamp = Date.now()                       // 1672899103000
```

这是新人第一个高频错误。

---

### 步骤 ② 按 key 字典升序排序

把所有参数按 **key 的字典顺序**从小到大排列。

排序前：

```
task_id, channel_id, content_url, popularize_type, keyword, timestamp, access_token
```

排序后：

```
access_token, channel_id, content_url, keyword, popularize_type, task_id, timestamp
```

```json
{
  "access_token": "Db6j0Yq0eppBb",
  "channel_id": "1462106336904909960",
  "content_url": "https://www.zhihu.com/market/paid_column/1550452094749851648/section/1590711798218661888",
  "keyword": "这是一个测试关键词",
  "popularize_type": 0,
  "task_id": "1443567656205545123",
  "timestamp": 1672899103
}
```

**要点：**

- 排的是 **key**，不是 value
- 「字典升序」= 按字符的 ASCII/Unicode 码点比较，即 JS 里 `Array.prototype.sort()` 的默认行为
- 注意大写字母的码点小于小写字母（`Z`(90) < `a`(97)），本项目参数名全是小写下划线风格，不涉及这个问题

```typescript
// JS 默认 sort 就是字典升序，直接用即可
Object.keys(params).sort()
```

---

### 步骤 ③ 拼接成 kv 字符串

按排好的顺序，拼成 `key=value&key=value&...` 的形式。

```
access_token=Db6j0Yq0eppBb&channel_id=1462106336904909960&content_url=https://www.zhihu.com/market/paid_column/1550452094749851648/section/1590711798218661888&keyword=这是一个测试关键词&popularize_type=0&task_id=1443567656205545123&timestamp=1672899103
```

**这一步有三个极易踩的坑：**

#### 坑 1：值不做 URL 编码 ⚠️

注意上面字符串里的中文「这是一个测试关键词」是**原样出现**的，
`content_url` 里的 `://` 和 `/` 也都**原样保留**，没有转成 `%3A%2F%2F`。

这和大多数签名算法（如支付宝、微信支付）的习惯**不同**，是本项目最反直觉的一点。

```typescript
// ❌ 错误：不要用 encodeURIComponent
const kvStr = `keyword=${encodeURIComponent('这是一个测试关键词')}`
// 得到 keyword=%E8%BF%99%E6%98%AF... → 签名一定错

// ❌ 错误：不要用 URLSearchParams，它会自动编码
const kvStr = new URLSearchParams(params).toString()
// 得到 content_url=https%3A%2F%2Fwww.zhihu.com... → 签名一定错

// ✅ 正确：手动拼，原样保留
const kvStr = Object.entries(sorted).map(([k, v]) => `${k}=${v}`).join('&')
```

#### 坑 2：数字类型直接转字符串，不加引号

```typescript
// popularize_type 的值是数字 0
// ✅ 正确：popularize_type=0
// ❌ 错误：popularize_type="0"
```

#### 坑 3：末尾不加 `&`，键值之间不加空格

```
✅ ...&timestamp=1672899103
❌ ...&timestamp=1672899103&
❌ ... & timestamp = 1672899103
```

---

### 步骤 ④ 计算 MD5 并转小写

对上一步的字符串做 MD5 摘要，结果**全部转为小写**。

```
输入：access_token=Db6j0Yq0eppBb&channel_id=...&timestamp=1672899103
输出：112f078ecdb75d76b38e4d9e661772bd
```

**要点：**

- MD5 计算基于字符串的 **UTF-8 字节序列**（中文按 UTF-8 编码，一个汉字 3 字节）
- 结果是 32 位十六进制字符串
- **必须转小写**。有些库默认输出大写，忘了转小写签名就错

```typescript
// ✅ 正确
const md5Str = CryptoJS.MD5(kvStr).toString().toLowerCase()

// ❌ 危险：不同库大小写行为不一致，不要省略 toLowerCase()
const md5Str = CryptoJS.MD5(kvStr).toString()
```

---

### 步骤 ⑤ HmacSHA256 加密生成签名

用 `secret_key` 作为密钥，对上一步的 **MD5 字符串**做 HmacSHA256。

```
message（消息）= 112f078ecdb75d76b38e4d9e661772bd     ← 步骤④的结果
key（密钥）     = a735eb11da74123074675fa3522a90d1     ← secret_key

signature = 794a1d97ffdd4af53c7064d697d686e2da4177bc2ccdcb4168e2f829b0f5c579
```

**要点：注意参数顺序，这是第二个高频错误**

HmacSHA256 有两个入参，顺序反了结果完全不同：

```typescript
// ✅ 正确：CryptoJS 的签名是 HmacSHA256(message, key)
const signature = CryptoJS.HmacSHA256(md5Str, secretKey).toString()

// ❌ 错误：顺序反了
const signature = CryptoJS.HmacSHA256(secretKey, md5Str).toString()
```

不同语言的库参数顺序不一样，容易混。记住语义：
**被加密的是 MD5 值，密钥是 secret_key**。

```python
# Python 的顺序是相反的：hmac.new(key, message, digestmod)
hmac.new(secret_key.encode(), md5_str.encode(), hashlib.sha256).hexdigest()
```

- 输出是 64 位十六进制小写字符串
- CryptoJS 的 `.toString()` 默认输出小写十六进制，符合要求

---

### 步骤 ⑥ 把签名放回请求参数

```json
{
  "task_id": "1443567656205545123",
  "channel_id": "1462106336904909960",
  "content_url": "https://www.zhihu.com/market/paid_column/1550452094749851648/section/1590711798218661888",
  "popularize_type": 0,
  "keyword": "这是一个测试关键词",
  "timestamp": 1672899103,
  "access_token": "Db6j0Yq0eppBb",
  "signature": "794a1d97ffdd4af53c7064d697d686e2da4177bc2ccdcb4168e2f829b0f5c579"
}
```

**要点：**

- 最终请求体里参数**不需要保持排序**，排序只是签名计算过程中的中间步骤
- `signature` 自己当然不参与签名计算
- 传参形式跟随接口定义：Body JSON 接口放 body，Query Param 接口放 URL 查询串，Form-Data 接口放表单字段

---

### 流程图

```
   业务参数
  { task_id, channel_id, content_url, popularize_type, keyword }
        │
        │ ① 补充凭证与时间戳
        ▼
  { ..., access_token, timestamp }
        │
        │ ② 剔除不参与签名的字段（offset/limit/file/second_channel_id...）
        ▼
  待签参数集
        │
        │ ③ 按 key 字典升序排序
        ▼
  { access_token, channel_id, content_url, keyword, popularize_type, task_id, timestamp }
        │
        │ ④ 拼接 kv 字符串（值不编码！）
        ▼
  "access_token=Db6j0Yq0eppBb&channel_id=...&timestamp=1672899103"
        │
        │ ⑤ MD5 → 转小写
        ▼
  "112f078ecdb75d76b38e4d9e661772bd"
        │
        │ ⑥ HmacSHA256(md5Str, secret_key)
        ▼
  "794a1d97ffdd4af53c7064d697d686e2da4177bc2ccdcb4168e2f829b0f5c579"
        │
        │ ⑦ 塞回请求
        ▼
   发出请求
```

## 四、哪些参数参与签名

**这一节比算法本身更容易出错。** 算法写对了但参数集算错了，签名照样失败。

### 全局不参与签名的字段

依据 OpenAPI V1.4.17 文档中各接口的明确标注：

| 字段 | 出现位置 | 文档原文依据 |
| --- | --- | --- |
| `signature` | 所有接口 | 签名本身不能参与自己的计算 |
| `file` | 批量类接口 | 「签名，file&header 参数不需要参与签名生成」 |
| `image` | 评论截流截图上传 | 「签名，image&header 参数不参与签名生成」 |
| `X-Requested-With` | Form-Data 类接口 | 「固定值：openApi，不参与签名」 |
| `offset` | 分页类接口 | 「分页偏移量，不传默认为 0，不参与签名」 |
| `limit` | 分页类接口 | 「分页条数，不传默认为 10，不参与签名」 |
| `second_channel_id` | 推广计划创建 | 「二代渠道 id，不参与签名」 |

### 特别注意：`composition_sub_type` 参与签名

文档在「推广作品管理」的版本迁移说明里明确写道：

> `composition_sub_type` 会参与单个创建和更新接口的签名。

这是 v2 接口相比 v1 的**新增签名字段**。从 v1 迁移到 v2 时，
如果漏了这个字段，签名会失败。

| 接口 | `composition_sub_type` 是否参与签名 |
| --- | --- |
| 单个创建推广作品（v2） | ✅ 参与 |
| 单个更新推广作品（v2） | ✅ 参与 |
| 批量创建推广作品（v2） | 该接口走 Form-Data + Excel，分类信息在 Excel 里，不作为签名字段 |

### 只有 `access_token` 的接口不需要签名

有 3 个接口的请求参数**只有 `access_token`**，文档中没有列出 `signature` 参数：

| 接口 | 路径 |
| --- | --- |
| 查询代理商渠道信息 | `GET /alliance/api/get_agent_channels` |
| 查询批量任务结果 | `GET /alliance/api/get_batch_task_result/:batch_task_id` |
| 查询榜单列表 | `GET /alliance/api/vip/content/rule/labels` |
| 查询上新内容 | `GET /alliance/api/online_sections` |
| 获取投放实时数据 | `GET /alliance/api/data_report/real_time_data` |
| 查询有声书列表 | `GET /alliance/api/vip/audio/contents` |
| 查询有声书音频地址 | `GET /alliance/api/vip/audio/:section_id/download` |
| 查询漫剧剧目列表 | `GET /alliance/api/comic_dramas` |
| 查询漫剧剧集列表 | `GET /alliance/api/comic_drama/:drama_id/episodes` |
| 查询榜单内容数据列表 | `GET /alliance/api/vip/rule_contents` |
| 查询榜单内容详情 | `GET /alliance/api/vip/rule_content/:content_id` |
| 单个内容标签查询 | `GET /alliance/api/content_tag` |
| 查询评论截流词列表 | `GET /alliance/api/intercept_words` |
| 获取风险词列表 | `GET /alliance/api/risk_words` |

> **实现建议**：不要为这些接口单独写一套无签名逻辑。
> 统一都算签名并附带上去——多带一个 `signature` 参数通常不会导致失败。
> 更稳妥的做法是在 `constants/sign-rules.ts` 里维护一份「免签接口白名单」，
> 联调时如果发现某接口带签名反而报错，再登记进白名单。
>
> 具体行为需在联调阶段逐个验证，验证结果请回填到本节表格。

### 实现：签名参数集的计算

```typescript
// src/constants/sign-rules.ts

/** 全局不参与签名的字段 */
export const GLOBAL_SIGN_EXCLUDED_KEYS: readonly string[] = [
  'signature',
  'file',
  'image',
  'offset',
  'limit',
  'second_channel_id',
  'X-Requested-With',
]

/**
 * 接口级额外排除字段。
 * 联调发现某接口有特殊规则时，登记在这里，不要去改签名算法本体。
 */
export const PER_API_SIGN_EXCLUDED_KEYS: Record<string, readonly string[]> = {}

/**
 * 免签接口白名单（请求不需要 signature 参数）。
 * 需联调逐个验证后填入。
 */
export const SIGN_FREE_API_PATHS: readonly string[] = []
```

```typescript
// src/utils/signature.ts

/**
 * 从完整参数中筛出真正参与签名计算的参数集。
 *
 * 三条规则：
 * 1. 剔除全局排除字段
 * 2. 剔除该接口的额外排除字段
 * 3. 剔除值为 undefined / null / 空字符串的字段
 *    （可选参数没填时不应参与签名，否则会算出 key= 这样的空值项）
 */
export function pickSignableParams(
  params: Record<string, unknown>,
  apiPath?: string,
): Record<string, string | number> {
  const excluded = new Set<string>([
    ...GLOBAL_SIGN_EXCLUDED_KEYS,
    ...(apiPath ? PER_API_SIGN_EXCLUDED_KEYS[apiPath] ?? [] : []),
  ])

  const result: Record<string, string | number> = {}
  for (const [key, value] of Object.entries(params)) {
    if (excluded.has(key)) continue
    if (value === undefined || value === null || value === '') continue
    if (value instanceof File || value instanceof Blob) continue   // 兜底：文件一律排除
    result[key] = value as string | number
  }
  return result
}
```

> **关于空值处理的说明**：官方文档未明确说明「可选参数未填时是否参与签名」。
> 本项目采用「值为空则不参与」的策略，理由是官方示例中未出现空值参数。
> 如联调中发现某接口行为不符，请在此处补充说明并调整实现。

## 五、代码实现

### 完整签名工具（工具层）

```typescript
// src/utils/crypto.ts
import CryptoJS from 'crypto-js'

/**
 * 计算字符串的 MD5 摘要，输出 32 位小写十六进制。
 *
 * 注意：CryptoJS 内部按 UTF-8 处理字符串，中文无需额外编码。
 *
 * @example
 * md5Lower('abc')  // => '900150983cd24fb0d6963f7d28e17f72'
 */
export function md5Lower(input: string): string {
  return CryptoJS.MD5(input).toString().toLowerCase()
}

/**
 * 计算 HmacSHA256，输出 64 位小写十六进制。
 *
 * ⚠️ 参数顺序：第一个是被加密的消息，第二个是密钥。反了结果完全不同。
 *
 * @param message 被加密的消息（本项目中是小写 MD5 字符串）
 * @param key     密钥（本项目中是 secret_key）
 */
export function hmacSha256Hex(message: string, key: string): string {
  return CryptoJS.HmacSHA256(message, key).toString(CryptoJS.enc.Hex).toLowerCase()
}
```

```typescript
// src/utils/signature.ts
import { md5Lower, hmacSha256Hex } from './crypto'
import { sortObjectByKey, buildKvString } from './object'
import { GLOBAL_SIGN_EXCLUDED_KEYS, PER_API_SIGN_EXCLUDED_KEYS } from '@/constants/sign-rules'

/** 生成秒级时间戳 */
export function currentTimestampInSeconds(): number {
  return Math.floor(Date.now() / 1000)
}

/**
 * 计算知乎 OpenAPI 接口签名。
 *
 * 六步法（详见 docs/04-签名机制.md）：
 *   ① 参数中已含 access_token 与 timestamp（由调用方保证）
 *   ② 剔除不参与签名的字段
 *   ③ key 字典升序排序
 *   ④ 拼接 key=value&key=value，**值不做 URL 编码**
 *   ⑤ MD5 摘要转小写
 *   ⑥ HmacSHA256(md5Str, secretKey)
 *
 * @param params    完整请求参数（含 access_token、timestamp）
 * @param secretKey 签名密钥
 * @param apiPath   接口路径，用于查接口级排除规则，可选
 * @returns 64 位小写十六进制签名
 *
 * @example
 * // 官方 PDF § 1.2 示例，本项目已验证输出一致
 * buildSignature({
 *   task_id: '1443567656205545123',
 *   channel_id: '1462106336904909960',
 *   content_url: 'https://www.zhihu.com/market/paid_column/1550452094749851648/section/1590711798218661888',
 *   popularize_type: 0,
 *   keyword: '这是一个测试关键词',
 *   timestamp: 1672899103,
 *   access_token: 'Db6j0Yq0eppBb',
 * }, 'a735eb11da74123074675fa3522a90d1')
 * // => '794a1d97ffdd4af53c7064d697d686e2da4177bc2ccdcb4168e2f829b0f5c579'
 */
export function buildSignature(
  params: Record<string, unknown>,
  secretKey: string,
  apiPath?: string,
): string {
  if (!secretKey) {
    throw new Error('[signature] secretKey 为空，无法计算签名。请检查凭证配置。')
  }

  // ② 剔除不参与签名的字段
  const signable = pickSignableParams(params, apiPath)

  // ③ 字典升序
  const sorted = sortObjectByKey(signable)

  // ④ 拼接 kv 字符串（不编码）
  const kvStr = buildKvString(sorted)

  // ⑤ MD5 转小写
  const md5Str = md5Lower(kvStr)

  // ⑥ HmacSHA256
  return hmacSha256Hex(md5Str, secretKey)
}

/**
 * 返回签名计算的所有中间结果，用于调试。
 *
 * 当签名对不上时，用这个函数把每一步的中间值打印出来，
 * 和服务端或 Postman 的结果逐步对比，就能定位到具体是哪一步错了。
 */
export function buildSignatureWithTrace(
  params: Record<string, unknown>,
  secretKey: string,
  apiPath?: string,
) {
  const signable = pickSignableParams(params, apiPath)
  const sorted = sortObjectByKey(signable)
  const kvStr = buildKvString(sorted)
  const md5Str = md5Lower(kvStr)
  const signature = hmacSha256Hex(md5Str, secretKey)

  return {
    step2_signableKeys: Object.keys(signable),
    step3_sortedKeys: Object.keys(sorted),
    step4_kvString: kvStr,
    step5_md5: md5Str,
    step6_signature: signature,
  }
}
```

### 签名拦截器（基础设施层）

```typescript
// src/infra/http/interceptor-sign.ts
import type { AxiosInstance, InternalAxiosRequestConfig } from 'axios'
import { buildSignature, currentTimestampInSeconds } from '@/utils/signature'
import { useCredentialStore } from '@/stores/credential.store'

/**
 * 请求拦截器：自动注入 access_token / timestamp / signature。
 *
 * 这是**整个项目唯一**计算签名的调用点。
 * 在其他任何地方看到签名相关代码，都视为架构违规。
 *
 * 三种传参形式的处理差异：
 * - Body JSON   → 注入到 config.data
 * - Query Param → 注入到 config.params
 * - Form-Data   → 注入到 FormData 实例（append）
 */
export function installSignInterceptor(instance: AxiosInstance): void {
  instance.interceptors.request.use((config: InternalAxiosRequestConfig) => {
    const credential = useCredentialStore()

    // 生产环境不在前端签名，直接交给 BFF 处理
    // 详见 docs/01-架构设计.md 「安全边界」
    if (!credential.enableLocalSign) {
      return config
    }

    const accessToken = credential.accessToken
    const secretKey = credential.secretKeyForDevOnly
    const timestamp = currentTimestampInSeconds()
    const apiPath = config.url ?? ''

    if (!accessToken || !secretKey) {
      throw new Error('[sign] 凭证未配置，请先到「凭证配置」页填写 access_token 与 secret_key')
    }

    const isFormData = config.data instanceof FormData

    if (isFormData) {
      // Form-Data：从 FormData 中读出已有字段参与签名
      const form = config.data as FormData
      const plainParams: Record<string, unknown> = { access_token: accessToken, timestamp }
      form.forEach((value, key) => {
        if (!(value instanceof File) && !(value instanceof Blob)) {
          plainParams[key] = value
        }
      })
      const signature = buildSignature(plainParams, secretKey, apiPath)

      form.append('access_token', accessToken)
      form.append('timestamp', String(timestamp))
      form.append('signature', signature)
    } else if (config.method?.toLowerCase() === 'get' || config.method?.toLowerCase() === 'delete') {
      // Query Param
      const params = { ...(config.params ?? {}), access_token: accessToken, timestamp }
      const signature = buildSignature(params, secretKey, apiPath)
      config.params = { ...params, signature }
    } else {
      // Body JSON
      const data = { ...(config.data ?? {}), access_token: accessToken, timestamp }
      const signature = buildSignature(data, secretKey, apiPath)
      config.data = { ...data, signature }
    }

    return config
  })
}
```

> **注意 URL Param 类接口**：像 `PUT /popularize_composition/v2/:composition_id`
> 这类接口，`composition_id` 是路径参数。文档将其标注为 `Url Param` 且**必填**。
> 它是否参与签名需在联调阶段验证：
> - 若参与，需在拦截器中额外把路径参数并入签名参数集
> - 若不参与，则维持现有实现
>
> 建议联调时先按「参与」实现（因为文档把它列在了参数表里且必填），
> 失败则改为「不参与」重试，并把结论回填到本文档。

## 七、排错手册

签名失败时，按这个顺序排查。**不要瞎改代码，按步骤定位。**

### 第一步：确认是不是签名问题

看接口返回的 `error.message`：

| 返回内容 | 判断 |
| --- | --- |
| `timestamp 无效` | 可能是时间戳问题，**也可能是签名问题**（知乎的报错不精确） |
| 提到 `signature` / `签名` | 确定是签名问题 |
| 提到具体字段名 | 是参数问题，不是签名问题，去查 03 文档的参数要求 |
| `无效id` | 是业务 ID 不存在，不是签名问题 |

> ⚠️ 知乎在签名错误时也可能返回 `timestamp 无效`。
> 所以看到这个报错，**不要只怀疑时间戳**，签名也要一起查。

### 第二步：跑黄金用例

```bash
npm run test -- signature
```

- **黄金用例失败** → 算法实现有 bug，去看第三步
- **黄金用例通过** → 算法是对的，问题在参数集，跳到第四步

### 第三步：算法实现自查（黄金用例失败时）

按这张表逐项对照：

| # | 检查项 | 错误症状 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 时间戳单位 | 值有 13 位数字 | `Math.floor(Date.now() / 1000)`，应为 10 位 |
| 2 | 值是否被 URL 编码 | kv 字符串里出现 `%` | 手动拼接，不用 `URLSearchParams` / `encodeURIComponent` |
| 3 | MD5 是否转小写 | MD5 结果有大写字母 | 加 `.toLowerCase()` |
| 4 | HmacSHA256 参数顺序 | 签名长度对但值不对 | `HmacSHA256(md5Str, secretKey)`，消息在前 |
| 5 | Hmac 的输入是 MD5 还是原串 | 签名值完全不对 | 输入必须是**步骤⑤的 MD5 字符串** |
| 6 | 排序是按 key 还是 value | 签名值完全不对 | 按 **key** 排序 |
| 7 | 数字是否被加了引号 | 只有含数字参数的接口失败 | `String(0)` → `"0"`，不要 `JSON.stringify(0)` → `"0"` 带引号 |
| 8 | 拼接符是否正确 | 签名值完全不对 | `key=value`，用 `&` 连接，无空格、无尾随 `&` |

用 `buildSignatureWithTrace()` 打印中间值，和文档的黄金用例逐步对比，
第一个不一致的步骤就是出错的地方。

```typescript
const trace = buildSignatureWithTrace(params, secretKey)
console.log('待签字段：', trace.step2_signableKeys)
console.log('排序后：  ', trace.step3_sortedKeys)
console.log('kv 串：   ', trace.step4_kvString)
console.log('MD5：     ', trace.step5_md5)
console.log('签名：    ', trace.step6_signature)
```

### 第四步：参数集自查（黄金用例通过时）

算法对了但真实接口还是失败，说明**参与签名的参数集不对**。

| # | 检查项 | 说明 |
| --- | --- | --- |
| 1 | 是否漏了 `access_token` | 它**必须**参与签名 |
| 2 | 是否漏了 `timestamp` | 它**必须**参与签名 |
| 3 | 是否误把 `offset` / `limit` 算进去了 | 文档明确：不参与 |
| 4 | 是否误把 `second_channel_id` 算进去了 | 文档明确：不参与 |
| 5 | 是否误把 `file` / `image` 算进去了 | 文档明确：不参与 |
| 6 | 是否误把 `X-Requested-With` 算进去了 | Header 参数，不参与 |
| 7 | v2 作品接口是否漏了 `composition_sub_type` | 文档明确：**参与**签名 |
| 8 | URL Param（如 `composition_id`）该不该算 | 需联调验证，见第五节末尾说明 |
| 9 | 可选参数没填时是否算了空值 | 本项目策略：空值不参与 |
| 10 | Form-Data 接口是否漏了某个表单字段 | 除 file 外的表单字段都要参与 |

### 第五步：环境与凭证自查

| # | 检查项 | 怎么查 |
| --- | --- | --- |
| 1 | `secret_key` 是否正确 | 对照运营给的原始凭证，注意首尾空格 |
| 2 | `secret_key` 是否被环境变量截断 | `console.log(secretKey.length)`，示例长度为 32 |
| 3 | 本机系统时间是否准确 | 与 `https://time.is` 对比，误差应 < 1 分钟 |
| 4 | 是否用了错误环境的凭证 | 测试凭证不能调生产接口，反之亦然 |
| 5 | 日配额是否已用完 | 配额耗尽的报错可能被误读为签名失败 |

### 常见错误速查表

| 你看到的现象 | 最可能的原因 | 修复 |
| --- | --- | --- |
| 所有接口都报 `400400` | 时间戳用了毫秒 | 除以 1000 取整 |
| 只有带中文参数的接口失败 | 值被 URL 编码了 | 去掉 `encodeURIComponent` |
| 只有分页查询接口失败 | `offset`/`limit` 算进签名了 | 加入排除清单 |
| 只有 v2 作品接口失败 | 漏了 `composition_sub_type` | 补进签名参数集 |
| 只有批量上传接口失败 | `file` 或 Header 算进签名了 | 加入排除清单 |
| 昨天好的今天全挂 | 系统时间偏移 / 配额耗尽 | 校时；查配额 |
| 本机好的同事机器挂 | 同事的 `.env.local` 没配或配错 | 检查同事的环境变量 |
| 签名长度不是 64 位 | Hmac 输出编码不对 | 用 `CryptoJS.enc.Hex` |

## 八、安全注意事项

### `secret_key` 的处理红线

| 场景 | 允许 | 禁止 |
| --- | --- | --- |
| 存储位置 | 服务端环境变量 / 密钥管理服务 | 前端源码、`.env`（非 local）、Git |
| 本地开发 | `.env.local`（已 gitignore） | 任何会被提交的文件 |
| 日志输出 | 打印长度、前 4 位打码 | 打印完整值 |
| 错误提示 | 「secret_key 未配置」 | 「secret_key 为 a735eb…」 |
| 生产构建 | 不包含 | 包含 |

### 日志脱敏实现

```typescript
// src/utils/mask.ts
/**
 * 敏感字符串脱敏，用于日志输出。
 *
 * @example
 * maskSecret('a735eb11da74123074675fa3522a90d1')  // => 'a735****90d1 (len=32)'
 */
export function maskSecret(secret: string): string {
  if (!secret) return '(empty)'
  if (secret.length <= 8) return `**** (len=${secret.length})`
  return `${secret.slice(0, 4)}****${secret.slice(-4)} (len=${secret.length})`
}
```

请求日志拦截器里，凡是 `secret_key`、`signature` 字段一律走脱敏：

```typescript
const SENSITIVE_KEYS = ['secret_key', 'secretKey', 'signature', 'access_token']

function sanitizeForLog(obj: Record<string, unknown>): Record<string, unknown> {
  const result: Record<string, unknown> = {}
  for (const [key, value] of Object.entries(obj)) {
    result[key] = SENSITIVE_KEYS.includes(key) ? maskSecret(String(value)) : value
  }
  return result
}
```

### 凭证 Store 的设计约束

```typescript
// src/stores/credential.store.ts
export const useCredentialStore = defineStore('credential', () => {
  /** 开发者 Token。非高敏，可持久化到 localStorage */
  const accessToken = ref(localStorage.getItem('zhihu_access_token') ?? '')

  /**
   * 签名密钥。
   *
   * ⚠️ 命名故意加 ForDevOnly 后缀，让任何读到这行代码的人立刻意识到风险。
   *
   * 三条约束：
   * 1. 只从 import.meta.env 读，不接受用户在页面上输入后持久化
   * 2. 不写入 localStorage / sessionStorage / cookie
   * 3. 生产构建时 VITE_DEV_SECRET_KEY 必须为空
   */
  const secretKeyForDevOnly = ref(import.meta.env.VITE_DEV_SECRET_KEY ?? '')

  /** 是否在前端本地签名。生产环境必须为 false */
  const enableLocalSign = computed(
    () => import.meta.env.VITE_ENABLE_LOCAL_SIGN === 'true' && !!secretKeyForDevOnly.value,
  )

  return { accessToken, secretKeyForDevOnly, enableLocalSign }
})
```

> **为什么 `secret_key` 不允许用户在页面上输入并保存？**
> 因为一旦支持保存，它就会进 `localStorage`，而 `localStorage` 里的内容
> 任何同域 JS（包括被注入的第三方脚本）都能读取。
> 开发期从环境变量读，生产期根本不该有这个字段。
