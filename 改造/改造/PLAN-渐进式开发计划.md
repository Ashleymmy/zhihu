# 渐进式开发计划 - 分模块实施

> **核心原则**：先保证核心链路能跑通业务，再逐步完善边际功能  
> **开发策略**：小步快跑，每个模块独立上线，降低返工风险  
> **创建时间**：2025-01-XX

---

## 📌 项目背景

**问题**：
- 项目已返工 3 次，需求不断变动
- 不能一次性全量开发，风险太高
- 需求评审等流程不走，文档主要内部使用

**策略**：
- ✅ 按模块拆分，逐个开发上线
- ✅ 优先保证核心业务链路
- ✅ 每个模块独立验证，降低返工成本
- ✅ 后续模块可根据实际情况调整或放弃

**核心逻辑**：
```typescript
// 简化版：假设所有数据都正常，直接计算
async function performSimpleAttribution(taskId: string) {
  // 1. 查询作品
  const works = await findWorksByKeyword(task.keyword);
  
  // 2. 计算质量分和权重
  const results = calculateWeights(works);
  
  // 3. 写入 attribution_results
  await saveAttributionResults(taskId, results);
  
  // 4. 生成 settlement_batch（关键：对接现有定价体系）
  const batchId = await createSettlementBatch(taskId, results);
  
  // 5. 自动审批（应用定价规则）
  await approveBatch(batchId);
  
  return { success: true, batchId };
}
```

**验收标准**：

## 🔧 技术实施建议

### 1. 代码分支策略

```
main（生产）
 ↑
dev（开发）
 ↑
feature/attribution-mvp（P0 核心链路）
 ↑
feature/attribution-p1（P1 功能）
```

**原则**：
- P0 完成并验证后才合并到 dev
- P1 可以在 P0 上线后单独开发
- 每个模块独立分支，便于回滚

### 2. 数据库迁移策略

```
migrations/
├── 010_attribution_core.sql        # P0 核心表
├── 011_attribution_enhance.sql     # P1 增强字段（可选）
└── 012_attribution_optional.sql    # P2 可选功能（暂不执行）
```

**原则**：
- P0 迁移脚本必须可逆（有 down.sql）
- P1/P2 迁移脚本只有在确定要开发时才写

### 3. 功能开关（Feature Flag）

```typescript
// config.ts
export const features = {
  attributionAudit: false,        // P1：归因审核
  confidenceScore: false,         // P1：置信度评估
  workApproval: false,            // P1：作品审核
  imapAutoFetch: false,           // P2：IMAP 自动收取
};
```

**原则**：
- P0 功能无开关（必须有）
- P1/P2 功能用开关控制
- 可以先开发，后开启

## 🎓 风险控制

### 风险 1：需求再次变动

**缓解措施**：
- ✅ 模块化设计，每个模块可独立替换
- ✅ P1/P2 功能可随时放弃
- ✅ 核心链路保持简单，易于调整

### 风险 2：定价规则变更

**缓解措施**：
- ✅ 归因引擎与定价规则分层
- ✅ 定价规则在数据库配置，不写死在代码
- ✅ 变更只影响第 2 层，不影响第 1 层

### 风险 3：作品数据不准确

**缓解措施**：
- ✅ P0 阶段：达人手动填写，责任在达人
- ✅ P1 阶段：增加审核机制
- ✅ P2 阶段：考虑自动采集（如果需要）

## 🎉 总结

### 核心策略

1. **小步快跑**：先做 P0（9 天），上线验证，再决定 P1
2. **降低风险**：模块化设计，每个模块可独立替换或放弃
3. **灵活调整**：P1/P2 功能根据实际情况决定是否开发

- **第 1-2 周**：P0 核心链路（9 天开发 + 2 天测试）
- **第 3 周**：观察运行情况，决定 P1 优先级
