# P0 风险控制清单

> **目标**：降低返工风险，确保 P0 稳定上线  
> **原则**：提前识别风险，制定应对措施

---

## 🎯 核心风险

### 风险 1：需求再次变更 🔴 高

**描述**：项目已返工 3 次，存在需求再次变更的风险。

**影响**：
- 已开发的功能需要重构
- 时间和人力成本浪费
- 团队士气受挫

**缓解措施**：

✅ **模块化设计**
```
每个模块独立，变更影响范围小

如果归因算法变更 → 只改 processAttribution.ts
如果定价规则变更 → 只改数据库配置，代码不动
如果前端交互变更 → 只改前端组件
```

✅ **功能开关**
```typescript
// 可以先开发，后开启
const features = {
  dataPreview: false,    // P1：数据预览
  workApproval: false,   // P1：作品审核
};
```

✅ **最小化 P0 范围**
```
只做核心链路，边际功能全部 P1/P2
变更影响 P1/P2 → 直接不做，无成本
```

---

### 风险 2：定价规则变更 🟡 中

**描述**：业务方可能调整定价规则（如从 60% 改为 50%）。

**影响**：
- 如果定价逻辑写死在代码，需要重新部署
- 历史数据可能需要重算

**缓解措施**：

✅ **数据库配置，不写死代码**
```typescript
// ✅ 正确：从数据库读取
const rules = await getPricingRules();
const amount = source * rules.percentage;

// ❌ 错误：写死在代码
const amount = source * 0.6; // 如果改成 0.5 需要重新部署
```

✅ **复用现有定价体系**
```
归因引擎不管定价规则
定价规则在 pricing_rules 表统一管理
业务方自己改配置，不需要改代码
```

✅ **双层架构隔离**
```
第 1 层：归因引擎（计算归因收益）
第 2 层：定价规则（应用 pricing_rules）

定价规则变更不影响归因引擎
```

---

### 风险 3：数据不准确 🟡 中

**描述**：达人手动填写的作品数据可能不准确（浏览量、点赞数虚报）。

**影响**：
- 归因不公平
- 达人之间产生纠纷
- 系统公信力下降

**缓解措施**：

✅ **P0 阶段：责任在达人**
```
明确告知达人：数据需真实
虚报数据后果自负
系统只做基础校验（非负数）
```

✅ **P1 阶段：增加审核**
```
管理员审核作品
发现异常数据拒绝
```

✅ **P2 阶段：自动采集（可选）**
```
通过爬虫或 API 自动获取
但不是 P0 重点，避免过度复杂
```

✅ **申诉机制（P1）**
```
如果达人认为分配不公，可申诉
管理员介入调查
```

---

### 风险 4：归因算法不合理 🟡 中

**描述**：质量加权算法可能不符合实际业务逻辑。

**影响**：
- 达人认为分配不公平
- 需要调整算法并重算历史数据

**缓解措施**：

✅ **权重可配置**
```typescript
// 不写死在代码，放到配置文件
const QUALITY_WEIGHTS = {
  viewCount: 0.5,
  likeCount: 2.0,
  shareCount: 5.0,
};
```

✅ **P0 快速验证**
```
上线后观察 1-2 周
收集达人反馈
调整权重系数
```

✅ **保留人工兜底（P1）**
```
如果自动归因不合理
管理员可手动调整
```

---

### 风险 5：性能问题 🟢 低

**描述**：1000+ 个作品时归因计算可能较慢。

**影响**：
- 归因任务执行时间过长
- 用户等待时间长

**缓解措施**：

✅ **异步队列**
```
归因任务放到 Bull 队列
不阻塞主流程
```

✅ **数据库索引**
```sql
INDEX idx_keyword (keyword, published_at)
INDEX idx_creator (creator_id)
```

✅ **P0 不做优化**
```
先上线，观察性能
如果慢（>30 秒）再优化
避免过早优化
```

---

### 风险 6：邮件格式变更 🟢 低

**描述**：知乎官方可能改变邮件数据的格式。

**影响**：
- 数据解析失败
- 无法导入数据

**缓解措施**：

✅ **智能字段匹配**
```typescript
// 支持多种列名
const FIELD_MAPPINGS = {
  keyword: ['关键词', 'keyword', '推广关键词'],
  revenue: ['收益', 'revenue', '收益金额'],
};
```

✅ **明确错误提示**
```typescript
if (!row.keyword) {
  throw new AppError(400, 40003, '缺少必填字段：关键词');
}
```

✅ **P1 增强验证**
```
导入前预览数据
管理员确认字段映射
```

## 🚨 应急预案

### 预案 1：归因计算错误

**现象**：达人收益明显不对

**应对**：
```
1. 立即暂停归因任务（停止队列）
2. 回滚错误的 earnings 记录
3. 排查 processAttribution.ts 逻辑
4. 修复后重新运行归因任务
```

### 预案 2：定价规则配置错误

**现象**：达人应得金额错误（如 80% 而非 60%）

**应对**：
```
1. 检查 pricing_rules 表配置
2. 如果是配置错误，修改配置
3. 找到受影响的 settlement_batches
4. 重新审批批次（覆盖 earnings）
```

### 预案 3：数据导入错误

**现象**：邮件数据导入失败或数据不对

**应对**：
```
1. 删除错误的 attribution_tasks 记录
2. 检查文件格式是否正确
3. 修改解析逻辑（如果格式变更）
4. 重新导入
```

### 预案 4：性能问题

**现象**：归因任务执行时间过长（>5 分钟）

**应对**：
```
1. 短期：增加队列 worker 数量
2. 中期：优化 SQL 查询（添加索引）
3. 长期：考虑分批处理或缓存
```

## 🎓 经验教训（避免返工）

### 已返工 3 次的教训

1. **不要一次做太多**
   - ❌ 一次性开发所有功能
   - ✅ 先做核心链路（P0），再迭代

2. **不要过度设计**
   - ❌ 考虑各种边界情况和扩展性
   - ✅ 够用即可，后续按需优化

3. **模块化，降低返工成本**
   - ❌ 所有逻辑耦合在一起
   - ✅ 每个模块独立，变更影响小

4. **需求变了，灵活应对**
   - ❌ 死磕原有方案
   - ✅ 快速调整或放弃边际功能

### P0 的做法

1. **小步快跑**
   - 9 天完成，快速验证
   - 不对就调整，成本低

2. **功能最小化**
   - 只做核心链路
   - 边际功能全部 P1/P2

3. **灵活架构**
   - 双层架构（归因 + 定价）分离
   - 每个模块可独立替换

4. **拥抱变化**
   - 功能开关控制
   - 配置数据库化
   - P1/P2 随时可放弃

## 📝 总结

### 关键原则

1. **够用即可**：P0 不做过度设计
2. **模块化**：降低变更影响
3. **快速验证**：9 天上线，观察反馈
4. **灵活调整**：P1/P2 按需决定

### 风险控制

1. **需求变更** → 模块化 + 功能开关
2. **定价变更** → 数据库配置，不写死
3. **数据不准** → P0 责任在达人，P1 增加审核
4. **算法不合理** → 权重可配置 + 人工兜底
5. **性能问题** → 异步队列 + 按需优化
6. **格式变更** → 智能匹配 + 明确错误
