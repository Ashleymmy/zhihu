## 0. 一句话结论

OPC 是项目聚合平台，知乎关键词业务只是第一个试运行项目。平台骨架（身份、组织、项目、模块、公共资金账）的方向是对的，要保留并加强。现在“乱”的根源有两个：

1. **平台概念被当成日常导航。** “业务模块”“接入账号”“运营账户”这类配置项直接摆在每个人面前。
2. **知乎模块绕开平台外壳，自己另搭了一套导航。** 知乎有自己的工具栏、“更多功能”、“知乎故事”聚合页，旧版功能也都挂在里面。

本方案的核心是：**平台按“角色要做的事”组织统一入口，每个项目模块按统一的环节接入（任务、作品、数据、收益），项目自己的特殊工具收进项目内部。** 财务与收益链路按这个骨架落在平台层，知乎是第一个接入的项目。

## 1. 定位与设计原则

### 1.1 平台和项目的分工

| 层 | 负责什么 | 例子 |
| --- | --- | --- |
| 平台（OPC 公共核心） | 账号、角色与岗位、团队、项目与成员、统一导航、首页待办、任务和作品的统一列表、计费规则、公共资金账、提现与付款、学院、公告、审计 | 达人在一个“我的收益”里看到所有项目的钱 |
| 项目模块（知乎是第一个） | 接入上游、任务资源怎么产生、作品怎么校验、业绩数据怎么取得、按什么口径计数、项目专属工具 | 知乎的关键词、渠道映射、报表 Excel 解析、盐选榜单 |

现有代码已经按这个分工拆开：公共核心在 `server/src/core`，知乎在 `server/src/modules/zhihu`，模块通过 `server/src/core/contracts.ts` 接入【已核实】。本方案补上缺的一环：**模块不仅要向平台提供“汇总数字”，还要按统一环节提供“待办、任务、作品、收益明细”**，平台才能把多个项目的内容放进同一套页面里。

小程序首页已经有“业务渠道矩阵”，知乎已开通，番茄小说、抖音、小红书预留【已核实：`weixin-app/miniprogram/pages/home/index.js`】，说明产品定位一直是多项目。

### 1.2 设计原则

1. **按角色的工作组织入口，不按开发模块组织。** 达人关心“我有什么任务、交什么、拿多少钱”，不关心钱来自哪个模块。
2. **所有项目共用同一套环节和状态用词。** 新项目接入时套用平台页面，只补充项目特有的字段和工具。
3. **每个页面只有一个主要动作，每件事只有一个入口。**
4. **每一步都能看到“现在卡在哪、该谁处理”。**
5. **旧功能不和新功能并列。** 新流程承接日常工作，历史数据只读查询，旧链接给出明确导向。
6. **不对普通用户展示内部用语。** 绑定、批次、快照、接入账号、引擎、legacy 这类词只出现在维护工具里。
7. **手机优先。** 达人主要用小程序，Web 端的达人页面也要在手机宽度下可用。
8. **钱要分清（沿用财务方案）。** 每一分钱都能追溯到“哪个项目、哪天、哪个任务、谁做的、多少单、什么单价”；已确认的账不因后续调价而改变。

### 2.3 流程看不出来，下一步不知道该谁做

- **钱算漏了却不提示**：财务页显示订单 42，应付只按 37 单计算；“悬疑短篇”的 5 单因为缺归属直接消失（截图 02）【已核实】。原因见财务方案 1.2 节。
- **任务被永久锁死**：“悬疑短篇”从未分配，出现在报表后变成“系统管理员 / 历史计划，保留原归属”，只读，再也分配不了（截图 04）。原因是 `unusedKeywordSql` 把“已有报表数据”也算作“已使用”【已核实】。
- **状态文案误导**：小张、王团长都没有登记作品，进度栏却写着“已登记作品，查看提交结果”。这句话是按“点过开始使用”（`usedEverAt`）显示的，不看实际作品数【已核实：`Keywords.vue` 第 75 行】。
- **“下一步”不说责任人**：财务账单的“下一步”写的是“等待作品提交成功，系统将自动核对归属”，实际在等团长核验作品（截图 03）。
- **一条任务要跨 5 个页面、4 种角色**：创建、领取或分发、开始使用、登记作品、核验、上传报表、确认账单、开放款项、提现、付款，没有任何页面能看到单个任务走到哪一步。

### 2.5 内部用语和半成品直接暴露

- 小程序“工具”标签 6 个工具里 5 个不可用，唯一可用的“数据查询”实际是收入提现页【已核实：`pages/tools/index.js`】。
- 已入团的达人在“加入团队”页仍看到入团申请表。
- 项目页直接摆着“解除关联”“禁用项目”“停用接入账号”等危险按钮，没有说明。

### 2.6 小程序

- 钱分散在“收益”标签、“工具 → 数据查询”、“我的 → 提现记录”三处【已核实】。
- 关键词和作品要从首页进入“知乎”二级页才能找到；底部标签中“工具”基本不可用。
- “收益”页直接调用 `/modules/zhihu/workbench`，团长会看到达人金额，运营职责管理员也能看到全部金额【已核实，详见第 6.3 节】。

### 2.7 原因

1. **页面按开发顺序和后端模块组织**：公共核心、知乎模块、旧版功能各有一套入口。
2. **旧功能从不下线**：新流程上线后，旧页面被塞进“更多功能”。
3. **问题靠加说明文字解决，而不是改流程。**
4. **平台抽象没有翻译成用户语言**：平台层的“项目、模块、接入账号”直接作为页面出现，而“任务、作品、收益”这些用户真正关心的统一概念，平台层反而没有。

## 3. 平台统一业务模型

### 3.1 名词表（全平台统一）

| 平台用词 | 含义 | 知乎项目里对应 | 其他项目举例【待确认】 |
| --- | --- | --- | --- |
| 项目 | 一条具体业务线，有成员、计费规则、负责人 | “知乎故事推广”（现名“知乎历史业务”，建议改名） | 番茄小说推文、抖音挂载 |
| 渠道 | 项目来自哪个外部平台 | 知乎 | 番茄、抖音、小红书 |
| 任务 | 成员领取并执行的最小单位 | 一个关键词 | 一本书的推文链接、一个挂载商品 |
| 作品 | 成员为任务提交的交付物，通常是链接 | 发布的视频或图文链接 | 同左 |
| 业绩 | 上游给出的效果数据 | 报表里的订单量、搜索量 | 阅读量、成交量 |
| 收益 | 按计费规则从业绩算出的钱 | 订单 × 单价 | 同左，或按比例 |
| 提现 | 把可提现收益申请付款 | 公共资金账 | 同左 |

调整：

- 知乎上游的“推广任务”（`tasks` 表，管理员同步的产品或活动）在界面上改称 **“推广活动”**，只出现在项目设置里，避免和平台“任务”混淆【待确认：第 9 节事项 A1】。
- 小程序已经把关键词称为“任务”，与本表一致，不需要改。
- “运营账户（MCN）”如仍有业务用途，并入“项目设置 → 接入”；否则隐藏【待确认：A6】。

### 3.2 统一状态

**任务状态**（所有项目共用，模块负责把自己的状态映射过来）：

| 平台状态 | 含义 | 知乎映射【已核实：现有字段】 |
| --- | --- | --- |
| 可领取 | 在任务大厅，符合条件的人可以领 | `lifecycle_status=available` 且就绪 |
| 待分配 | 团长已领取，还没指定执行人 | `reserved` |
| 待交作品 | 已有执行人，还没有作品 | `assigned`，或 `active` 但作品数为 0 |
| 作品审核中 | 已交作品，等待团长或管理员核验 | 绑定 `verification_status=pending` 且作品数大于 0 |
| 生效中 | 作品已通过，产生的业绩可以计费 | `verification_status=passed` |
| 有争议 | 归属或作品存在争议 | `disputed` 或 `ownership_conflict` |
| 已停用 | 计划暂停、结束或停用 | `retired`、`paused`、`ended` |

“开始使用”这一步不再单独让用户操作，**提交作品时自动完成**。

**作品状态**：待审核、已通过、已退回（附原因和重新提交入口）。

**收益状态**：沿用财务方案 3.5 节，即待处理（团长和达人看到的是“平台核对中”）、待确认、已确认、可提现、提现中、已到账。

### 3.3 每一条都要回答“下一步谁做什么”

每个任务、每笔收益在列表中都显示一列 **“下一步”**，格式为“谁 + 做什么”，并且可以直接点击执行：

| 情况 | 显示 |
| --- | --- |
| 待分配 | 团长 王团长：分配执行人 |
| 待交作品 | 达人 小张：提交作品 |
| 作品审核中 | 团长 王团长：核验作品 |
| 业绩缺归属 | 管理员：指定归属人 |
| 待确认 | 财务：确认本期账单 |
| 可提现 | 本人：申请提现 |

## 4. 信息架构（导航）

### 4.1 Web 端导航（按角色）

项目不再作为独立应用出现在导航里，而是作为**筛选条件**（页面顶部的项目切换，默认“全部项目”）。

| 角色 | 一级导航 | 说明 |
| --- | --- | --- |
| 达人 | 首页、任务大厅、我的任务、我的收益、学院、我的 | “我的”包含资料、团队、账号安全 |
| 团长 | 首页、任务大厅、团队任务、作品核验、我的团队、我的收益、学院、我的 | “团队任务”用于分配和跟进，“作品核验”是团长的关键待办 |
| 管理员·运营 | 首页、任务管理、作品管理、成员与团队、项目设置 | 数据问题可在首页待办和财务待处理中处理（看不到金额） |
| 管理员·财务 | 首页、财务、计费规则 | 财务页包含上传识别、待处理、核对确认、付款与提现 |
| 管理员·全部 | 以上全部，另加“系统”（账号与岗位、公告、审计日志、运维监控） | “系统”默认折叠 |

具体调整：

- **取消“已接入业务 → 知乎”这一套平行导航**，包括知乎工具栏、“更多功能”、“知乎故事”聚合页。原先的日常功能分别并入上表对应入口。
- **“业务项目 / 业务模块 / 接入账号 / 运营账户”合并为“项目设置”**，只对管理员显示。每个项目一张卡片：基本信息、成员、计费规则、接入状态、项目工具。
- **项目专属工具收进项目内部**。知乎的“渠道与任务（推广活动）”“报表中的渠道名称”“盐选榜单、评论截流、内容标签”等，放在“项目设置 → 知乎故事推广 → 项目工具”，或作为任务详情里的辅助信息。
- **占位页全部从导航移除**，包括订单管理、知识付费、创意工具坊、小程序工具里不可用的 5 个工具。上线时再加回来。
- **旧资金页面不再出现在导航里**（结算管理、收益结算、提现审批、财务申诉、历史邮件 / Excel 导入、订单管理）。统一收进财务页底部的“历史账目（只读）”；旧路由保留，打开时显示“该功能已合并到 ××，前往”【待核实：逐页检查只读状态下是否还有写操作按钮，即财务方案 V9】。
- **工作台的“操作引导”只保留一处**：放在首页，并按角色和完成情况显示，做完的步骤自动收起。

### 4.2 首页：待办优先

首页不再是“项目筛选 + 日期 + 查询 + 一串说明”，而是**我现在要做的事**。数据由各项目模块的待办提供器汇总（见 5.2 节）：

| 角色 | 首页待办示例 |
| --- | --- |
| 达人 | 2 个任务待交作品、1 个作品被退回待修改、可提现 ¥160 |
| 团长 | 1 个任务待分配、3 个作品待核验、团队本期收益 ¥97 |
| 运营 | 2 行业绩缺归属、1 个渠道名称未识别、5 个任务待分发 |
| 财务 | 本期待确认 ¥313、2 笔提现待审核、1 笔待登记付款 |

每条待办可以点击，直接进入可以处理的位置。没有待办时显示“都处理完了”，以及本期关键数字。

下方保留“我参与的项目”卡片（对应小程序的业务渠道矩阵），已开通的显示本期数字，未开通的显示“即将开放”，但不作为导航入口。

### 4.3 关键页面

**我的任务（达人）/ 团队任务（团长）/ 任务管理（运营）**：同一个页面组件，按角色显示不同的列和动作。

- 列：项目、任务名（知乎即关键词）、执行人、状态、下一步、本期业绩、操作。
- 主动作：达人是“提交作品”，团长是“分配执行人 / 核验作品”，运营是“分发 / 指定归属”。
- 点击任务打开侧边抽屉，显示**任务进度线**：领取 → 分配 → 交作品 → 核验 → 出业绩 → 算钱 → 确认 → 可提现。当前步骤高亮并写明负责人。
- 项目专属字段（知乎的小说原名、原文链接、推广活动）在抽屉里由模块提供【待补充：字段清单】。

**任务大厅**：所有项目中当前用户可以领取的任务，按项目分组；显示单价、优先期等规则说明，主动作为“领取”。

## 5. 平台与项目模块的接入约定（模块契约 v2）

### 5.1 现状

现有契约（`server/src/core/contracts.ts`，版本 1）只定义了：模块清单、路由、汇总数据提供器 `summary()`、财务汇总提供器【已核实】。平台因此只能显示“某模块的几个数字”，任务、作品、待办和收益明细只能各个模块自己做页面。知乎正是这样做的，结果就是第 2 节的平行导航。

### 5.2 新增的提供器

在不破坏版本 1 的前提下增加可选能力，版本号升到 2。新增能力都是可选的，模块没实现时，平台对应区域显示“该项目暂不支持”。

interface TodoProvider {

  kind: 'task.assign' | 'task.submit' | 'work.review' | 'fact.unassigned' | 'fact.unmapped' | string;

## 6. 财务与收益链路（整合财务方案）

本节在财务方案基础上调整两件事：一是放到平台层，二是吸收 10-08 审阅中发现的问题。财务方案里未提到的部分仍按原文执行。

### 6.1 放到平台层的部分

| 内容 | 财务方案原设计 | 本方案调整 | 理由 |
| --- | --- | --- | --- |
| 角色单价表 | 知乎 schema 下的 `zh_role_rates` | 平台计费规则表 `opc_rate_rules`（项目、规则代码、计价单位、单价、生效区间、状态、审计字段） | 团队结构和角色是平台概念，每个项目都要“管理员、团长、达人单价 + 团长分成”；放在平台才能统一“单价设置”和“我的收益” |
| 规则代码 | `staff_self / leader_self / creator / leader_override` | 不变，作为平台标准规则代码 | — |
| 计价单位 | 元 / 单 | 首期只支持“按单”，预留“按比例”【待确认：A2】 | 其他项目可能按成交额分成 |
| 计价计算 | 知乎 `quoteByRole()` | 平台提供 `quote(projectId, ruleCodes, date, quantity)`；模块负责判断“谁执行、是否有团长、业绩多少” | 模块只管归属和计数，钱怎么算由平台统一 |
| 收益明细 | 只在快照 JSON 里；`myEarnings()` 在知乎模块 | 平台收益明细表 `opc_earning_lines`：项目、来源键、业务日期、任务名、收款人、规则代码、数量、单价、金额、状态、阻塞原因 | 按收款人用 SQL 过滤和分页；跨项目汇总；确认前也能显示预估（财务方案事项 14） |
| 我的收益 | 知乎 `GET /modules/zhihu/my-earnings` | 平台 `GET /api/v1/core/earnings/mine` | 一个接口覆盖所有项目 |
| 确认入账 | `confirmBills()` 调用 `syncIncome()` | 不变；`syncIncome()` 按收益明细表生成 | 公共资金账已在平台层【已核实：`core/finance.ts`】 |

模块写入收益明细的时机：每次归因或重算后，覆盖该来源未确认的明细；已确认的明细不修改，差额由更正行体现（沿用 `refreshAdjustments()` 的思路）。

### 6.3 可以简化或删掉的部分
