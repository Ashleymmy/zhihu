# 知乎拉新拉活改造分工与衔接计划

修订草案，2026 年 10 月 8 日。Excel 上传和财务相关功能由同事编写修改与优化方案，方案完成后由用户交给另一个对话实施。本会话保留业务数据展示、关键词与作品查看方面的计划，并在接口确定后与上述工作对接。

整体目标是让用户看清自己和团队完成了多少作品、产生了多少拉新与拉活，以及对应的收入。达人继续按现有流程创建或领取关键词、登记作品；类型识别和金额计算由统一的后端结果提供。

用户已确认两组单价的业务分类：8 / 8.5 / 10 元属于拉新收益，1.2 / 1.6 / 2 元属于拉活（旧）收益。后文的拉活沿用“拉活（旧）”这一业务名称。

本次修订只调整计划与分工。后续开发、对话交接和发布按确认后的方案推进。

**1. 责任范围**

| 工作范围 | 负责人及安排 |
| --- | --- |
| Excel 上传、解析、预览、确认、导入历史、错误提示、重复与更正处理 | 同事出方案，另一个对话实施，包含前端和后端 |
| 拉新与拉活的来源识别、归属计算、数据入库及相关数据库迁移 | 纳入导入与财务方案统一设计，另一个对话实施 |
| 拉新价、拉活价、成员报价、生效日期、价格校验 | 纳入财务方案，另一个对话负责 Web、小程序及后端 |
| 收入计算、活动补贴、账单、对账、余额、提现、历史补算 | 纳入财务方案，另一个对话负责前后端全流程 |
| 个人与团队的作品数量、拉新数量、拉活数量展示 | 本会话保留双端展示计划；使用约定的数据接口 |
| 从成员、关键词进入业务明细及关联作品详情 | 本会话保留双端交互计划，沿用现有权限和关键词唯一归属 |
| 业务统计查询与共享接口 | 先约定字段和文件负责人；本会话按约定接入或补充只读查询，来源和财务计算由另一个对话负责 |

收入卡片、适用价格、账单跳转等即使位于业务数据页，也属于财务方案的衔接部分。双方先约定页面区域和文件负责人，再接入同一页面，避免同时重写页面。

**2. 本会话保留的业务展示计划**

| 页面或入口 | 预期体验 |
| --- | --- |
| 个人数据 | 展示作品数量、拉新数量、拉活数量，支持日期范围筛选 |
| 团队数据 | 团长区分本人和团队，可按成员展开；管理员查看权限范围内的数据 |
| 关键词明细 | 显示关键词、小说原名、原文链接、归属和两类业绩，提供关联作品入口 |
| 作品详情 | 从列表进入已有作品详情，查看提交信息、链接和状态；不把关键词汇总业绩直接算作每件作品的业绩 |
| 数据状态 | 区分已确认的零数量、尚未同步和类型未明确；接口暂未返回的数据不显示为零 |

Web 和小程序采用同一业务口径、日期范围和权限规则。前端直接展示后端给出的类型与数量，不按价格、文件名或用户角色猜测拉新与拉活，也不在客户端计算财务金额。

同一关键词可以有两类业绩，继续保持唯一使用归属。登记作品不增加选择收益类型的步骤，也不因本次展示调整增加逐条管理员审批。

**3. 与导入和财务方案的接口衔接**

同事方案完成后，双方需要对齐以下内容。这里只列信息需求，具体字段名、接口路径和表结构随最终方案确定。

| 对接内容 | 需要明确的信息 |
| --- | --- |
| 指标定义 | 拉新与拉活各自含义、计量单位，是否能相加，以及历史订单如何标记 |
| 计价维度 | 拉新与拉活（旧）分别匹配各自价格；本人执行与团队分成作为另一维度，不替代业务类型 |
| 查询范围 | 业务项目、渠道、日期、本人或团队、成员、关键词，以及分页方式 |
| 返回数据 | 作品数、拉新量、拉活量、业务日期、数据更新时间和数据是否齐全 |
| 明细关联 | 成员、关键词、作品的稳定标识；只有关键词汇总时，应明确作品仅为关联展示 |
| 权限 | 哪个角色能查看哪些成员与明细，由服务端约束并统一返回 |
| 财务展示衔接 | 财务侧提供的已计算金额、状态和详情入口，以及业务页面哪些区域由其实现 |
| 更正与兼容 | 导入修订后的刷新方式、旧数据的显示方式，以及旧版小程序的接口兼容 |

接口准备好前，可以整理展示文案和页面草图。依赖新数据的功能在接口可用、口径明确后联调，不通过另建一套导入、定价或结算逻辑填补接口缺口。

**4. 移交给同事方案的业务背景**

| 已确认业务类型 | 已确认单价组 | 方案调整要求 |
| --- | --- | --- |
| 拉新 | 8 / 8.5 / 10 元 | 同事方案中的这组价格明确标为拉新价格 |
| 拉活（旧） | 1.2 / 1.6 / 2 元 | 补齐这一类型的数量、价格、收入明细及验收用例 |

报表数据、定价和账单均需保留业务类型。角色只决定对应类型内适用哪一档价格，不能只按角色统一套一组价格。同一天、同一渠道、同一关键词的拉新与拉活数据应同时保留，不作为互相覆盖的来源修订。

- 官方拉活表样例包含日期、代理名称、渠道名称、关键词、结算金额和拉活量。只有拉活数据的报表应能独立处理，同一天同一关键词的两类数据需要分别保留。
- 所提供活动规则的新手期拉活结算为 2 元/个，聊天中的团长 1.6 元、团员 1.2 元已明确属于拉活（旧）。适用范围、生效日期、独立达人适用档位，以及上游结算与管理员内部业绩的账务定位，仍由财务方案明确。
- 在上述报价示例中，团长的 1.6 元包含给团员的 1.2 元。100 个拉活对应上游 200 元、平台付团长 160 元、团长付团员 120 元；平台与团长各留 40 元差额，未扣其他成本。
- 所提供活动规则中，满足转正要求后，第二月日均订单环比增长达到 10%，按第一月拉活量 × 1 元补发；第三月增长达到 5%，按第一月拉活量 × 2 元补发。活动周期、适用性和下游分配由财务方案确认，补贴不应重复增加拉活数量。
- 两组单价所属类型已确认；之前邮件报表的“订单量”是否全部为拉新、历史数据如何分类，以及额外补贴是否下发，仍列入同事方案的待确认项。统一角色报价、团长定价权限和实际付款路径属于单独的业务决定，不由单价分类直接推定。

这些内容用于交接已有讨论。导入和财务的具体页面、算法、存储及实施顺序由同事方案统一确定，再与业务展示接口对齐。

**5. 推进顺序**

| 阶段 | 交付内容 |
| --- | --- |
| 当前 | 更新本计划，明确责任范围和业务展示需求 |
| 同事完成方案后 | 用户将方案交给另一个对话实施；对齐业务口径、接口和共享文件负责人 |
| 接口明确后 | 本会话按确认范围改造 Web 与小程序的数量展示及明细入口；另一个对话实施导入和财务 |
| 集成验证 | 使用同一批样例核对两端数量、归属、权限，以及财务入口衔接 |
| 发布准备 | 合并两边已验证的改动，检查旧客户端兼容，再统一安排部署、体验版验证和提审 |

协作按功能和文件划分，避免把“另一个对话写后端、本会话写全部前端”作为默认分工。共享的数据合同、路由、页面容器及数据库迁移由双方确定一个修改负责人，另一方配合接入。

**6. 分开验收再联调**

| 验收范围 | 重点场景 | 负责方 |
| --- | --- | --- |
| 业务数量展示 | 同一关键词同一天有 3 个拉新、5 个拉活，分别正确显示 | 本会话范围 |
| 个人与团队 | 本人和团队范围清晰，成员汇总与明细一致，无法查看无权限成员 | 本会话范围 |
| 详情入口 | 从成员或关键词进入正确明细，能打开关联作品详情 | 本会话范围 |
| 两端与空数据 | Web 和小程序一致；未知数据与零数量有区别 | 本会话范围 |
| 导入与财务 | 两类收益分别匹配已确认的价格组，同日同词两类数据互不覆盖；另覆盖独立拉活报表、重复上传、更正、改价、缺价、补贴和历史兼容 | 另一个对话按同事方案验收 |
| 最终联调 | 官方样例导入后，数量、归属与已计算收入在相应页面正确呈现 | 双方共同核对 |

本会话保留业务展示和交互目标；Excel 与财务的完整设计和实现统一交由同事方案及后续对话负责。
