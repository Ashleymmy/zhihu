## 0. 背景与目标

系统已经上线，但“上传知乎报表 → 算出每个人的钱”这条链路断了：传完看不到钱，原因不显示，修复要绕很多页面；拉活报表完全传不进来。本任务书分三批：

| 批次 | 目标 | 要求 |
| --- | --- | --- |
| **P0 止血** | 线上能正确上传拉新、拉活两类报表，钱不再悄悄丢失，能当场找回 | 改动小、风险低；拉新已有的计价和已确认的账不变 |
| P1 体验重做 | 分析过程面板 + 多维表格 + 就地处理 + 自动重算 | P0 全部完成后开始 |
| P2 平台整合 | 按角色的导航、首页待办、平台“我的收益”、拉新迁移到角色单价、小程序同步 | 按平台方案执行 |

**P0 共 10 项，每项单独提交、单独可上线**，按编号顺序做。P0-10（导航清理）不依赖其他任务，可以和 P0-1 同时开始。

## 1. 已确认的业务规则

| 编号 | 规则 |
| --- | --- |
| R1 | 知乎有两类业绩：**拉新**（订单量，单位“单”）和**拉活**（拉活量，单位“个”）。两类分开计量、分开计价、分开存储，同一天同一关键词互不覆盖 |
| R2 | 上传前由用户选择报表类型（拉新订单 / 拉活），系统再按表头核对；前端不按价格、文件名猜测类型 |
| R3 | **历史上已上传的“订单量”数据全部算拉新** |
| R4 | 拉活单价：团长本人执行 1.60 元 / 个；团队达人 1.20 元 / 个，所属团长另得团长分成 0.40 元 / 个；**独立达人 1.20 元 / 个**；管理员本人执行 2.00 元 / 个 |
| R5 | **管理员本人执行产生的金额（拉新 10 元、拉活 2 元）只计入“管理员业绩”**：显示在财务页，但不进入应付合计、不写入公共资金账、不能提现 |
| R6 | 拉活上游结算单价 2.00 元 / 个，只用于核对报表中的“结算金额”，不作为付款依据 |
| R7 | 拉活与拉新一样：作品核验通过后才能确认 |
| R8 | 起量期补贴、红线规则本期**不实现**，只在数据结构上不挡路 |
| R9 | 拉新的现有计价方式（按推广任务 × 收款人报价）在 P0 保留，**缺价时按角色单价兜底**（10 / 8.5 / 8 / 0.5，见 P0-9）；P2 再完整迁移到角色单价 |

## 2. 通用约束（所有任务都适用）

- 不修改已确认的账（`zh_statement_entries.status='confirmed'`、`opc_income_entries`）；变化只能通过现有更正机制体现。

- 每个任务完成后：`cd server && npm run typecheck`；`npm run test:attribution`（需要 Docker）；根目录 `pnpm typecheck && pnpm build`；涉及页面的用 `npm run demo:review` 打开，按 1440px 和 375px 截图放进 PR。

### P0-2 文件解析容错（两类报表共用）

**问题**：任何一行有问题就整份拒收（E3）；“合计”行导致拒收；日期、数字、文件格式要求过严。

**改动**：`server/src/modules/zhihu/attribution/report.ts`、`workbench.ts` 的 `uploadReport()`，以及上传路由的文件校验。

1. **不整份拒收**：`uploadReport()` 第 38–43 行不再因为有错误行就 `fail`。错误行照常由 `previewImport()` 写入 `zh_import_rows`（现有逻辑已经是 `processing_status='invalid'`），`error_text` 改为下表的人话原因，其他行正常处理。只有以下情况才拒收整个文件：文件打不开、不是支持的格式、找不到必需的表头、没有任何数据行。
2. **汇总行自动跳过**：任意维度列（日期、渠道名称、关键词）的值为“合计 / 总计 / 小计 / 汇总 / 总和”（去空格后完全相等），或者日期列是这些字样而渠道和关键词都为空 → 标记 `processing_status='skipped'`，`error_text='汇总行，已跳过'`，不算错误。
3. **日期格式**：抽出一个共用的日期解析函数，接受：
   - Excel 日期数值（含 1904 日期系统，沿用现有逻辑）
   - `2026-09-14`、`2026/9/14`、`2026.9.14`、`2026年9月14日`、`20260914`
   - 带时间的写法：`2026-09-14 10:00:00`、`2026/9/14 10:00`（只取日期部分）
   - 解析失败时 `error_text` 写“第 N 行日期写成了“××”，请改成 2026-09-14 这样的格式”
4. **数字格式**：数量和金额去掉千分位逗号、空格、`¥`、`￥`、`元`、`个`、`单` 后再解析；空单元格视为没有值；负数和小数数量判为错误行（“第 N 行拉活量不是整数”）。
5. **多工作表**：依次查找所有工作表，使用第一个能识别出必需表头的工作表（拉活表的工作表可能叫“试用期拉活补贴”，不一定排第一）。
6. **文件格式**：
   - `.xlsx`：沿用现有安全校验 `validateAllianceXlsx`。
   - **`.csv`**：新增。编码自动识别：有 BOM 或能按 UTF-8 正确解码就用 UTF-8，否则按 GBK 解码（Node 自带 `TextDecoder('gbk')`）；分隔符支持逗号和制表符；大小上限与 xlsx 相同（10 MB）；包含 NUL 字节的文件拒收。解析可用 `XLSX.read(text, { type: 'string' })`。
   - `.xls`：拒收，提示“这是旧版 Excel（.xls）。请在 Excel 或 WPS 里点‘另存为’，选择 .xlsx 格式后再上传。”
   - 前端上传控件的 `accept` 改为 `.xlsx,.csv,.xls`，这样选到 .xls 时能看到上述提示，而不是选不了。
7. **表头别名**：拉新保持现有别名不变；拉活别名见 P0-5。表头比较前去除所有空白、全角括号转半角（沿用 `headerText()`）。

**错误原因文案**（写入 `error_text`，前端原样展示）：

| 情况 | 文案 |
| --- | --- |
| 日期解析失败 | 第 N 行日期写成了“××”，请改成 2026-09-14 这样的格式 |
| 日期在未来 | 第 N 行日期是 ××，还没到这一天 |
| 渠道或关键词为空 | 第 N 行缺少渠道名称或关键词 |
| 关键词超长 | 第 N 行关键词超过 128 个字 |
| 数量不是整数 | 第 N 行订单量（或拉活量）不是整数 |
| 缺少数量 | 第 N 行没有订单量（或拉活量） |

**验收**：

- 报表末尾有“合计”行：上传成功，合计行状态为“已跳过”。
- 报表中一行日期写错、其余正确：上传成功，错误行单独显示原因，其余行正常计算。
- 日期写成 `2026/9/14`、`2026年9月14日`、Excel 日期数值：都能识别。
- 同一份数据分别保存为 .xlsx、UTF-8 .csv、GBK .csv：结果一致。
- 上传 .xls：显示另存为提示。
- 知乎官方订单样例（`知乎_OrderData_…_20260927.xlsx`，表头：日期时间、渠道名称、关键词、推广任务、风险判定、搜索量、订单量、搜索转化率（单位%））解析结果与改动前完全一致。

### P0-9 拉新缺价兜底

**问题**：拉新按“推广任务 × 具体收款人”逐个报价，新成员、新任务没设价就算不出钱；上级是管理员的达人永远缺价，因为 `pricing.ts` 第 38、106 行要求“上级为空”，与 `relationships.ts` 的“直属达人”判断矛盾。

**做法**：现有报价优先，缺价时用角色单价兜底，不改动已有报价和已确认的账。

1. `029_metric_types.sql` 末尾同时写入拉新的 4 条角色单价（`metric_type='new_user'`，生效日 `2026-01-01`）：`staff_self` 10.00、`leader_self` 8.50、`creator` 8.00、`leader_override` 0.50。
2. `pricing.ts` 的 `quote()`：每条付款路径先按现有方式查报价；**查不到时**，按下表从 `opc_rate_rules` 取兜底价。关系类型名称保持原样（`agency_leader / leader_creator / agency_creator`），因此现有确认和更正链不受影响：

| 绑定类型 | 付款路径 | 兜底单价 |
| --- | --- | --- |
| `leader_self` | `agency_leader` | `leader_self`（8.50） |
| `team_creator` | `agency_leader` | `leader_self`（8.50） |
| `team_creator` | `leader_creator` | `creator`（8.00），团长净得 0.50 |
| `direct_creator` | `agency_creator` | `creator`（8.00） |

   **保护规则**：团队达人的两条路径中只有一条用了兜底价时，如果算出来团长净得为负（`leader_creator` 单价高于 `agency_leader` 单价），这一行**不使用兜底价**，记为 `PRICE_MISSING`（下一步：财务：设置单价）。现有 `workbench.allocations()` 遇到负数会抛错，导致整个账单页打不开，必须避免。同时为 `overview()` 加一层保护：单条事实的分配出错时，只把这一行标为“单价有冲突”，其他行照常显示。
3. 收款义务中记录价格来源 `priceSource: 'agreement' | 'role_rate'`，抽屉和明细中显示“按成员报价”或“按角色单价”。
4. `pricing.ts` 第 38 行和第 106 行，“直属达人必须上级为空”改为使用 `independentCreatorSql()`：上级是管理员的达人也算直属达人，可以单独报价。
5. 上线后执行一次：对 `reason_code IN ('PRICE_MISSING','PRICE_OVERLAP')` 且**未确认**的拉新事实重新归因（可以合并到 P0-8 的修复脚本，同样默认只预览）。

**验收**：

- 已有报价的成员：金额与改动前完全一致（L1）。
- 新加入、未设报价的团队达人做了 10 单：达人 80.00，团长 5.00；明细显示“按角色单价”。
- 上级是管理员的达人：不再缺价。
- 团长给达人的报价为 9.00、平台给团长没有报价：这一行显示“单价还没设置”，账单页其他行正常显示，不报错。
- 已确认的账不变。

#### 4. 金额、次数和期限如何保证一致

1. **金额分开存、同一处计算。** 用字符串及整数金额计算，分别保存申请总额、手续费、实付净额。余额占用总额；实付净额与手续费之和必须等于总额。已有 `amount` 的总额语义保持兼容，付款清单、导出、记录和统计要区分“余额扣减”与“实际到账”，不得把两个数混用。1% 不是项目收益扣点，也不写成税率。
2. **次数不能只在手机上限制。** 建议同一平台账号按北京时间自然日跨项目 / Web / 小程序计数，最终以审定方案为准。当前资金锁只覆盖项目接入范围，新增每日限制要在数据库事务中以账号和日期保证并发互斥；余额占用与次数占用同时成功或同时失败。两个客户端同时申请不能各通过一次。
3. **重试不重复扣款。** 继续使用原请求键；已成功请求的重放先返回原申请，不因后来余额不足、次数已满或规则改变而重复计数 / 拒绝恢复。相同键但参数不同应拒绝；跨日重试仍回到原记录。重复审批和付款也不能重复计费。
4. **原申请留住原规则。** 新申请保存规则版本、确认时间、分档、费用计算依据、日历依据及截止时间；已受理后调整规则不重算这笔记录。费用确认、拒绝 / 取消释放占用及付款失败恢复按业务审定口径执行；更正保留原记录，撤销付款标记不等于款项已经退回。
5. **审核与打款分开计时。** 小额截止覆盖审核加结算全过程；大额保存 15 个工作日的审核截止与申请次月的结算月份、月末最迟付款日，由服务端按北京时间计算。工作日采用国家公布的节假日及调休日历，调休补班周末计入、放假日排除；日历需可维护并覆盖跨年，不能只排除周六周日。起算方式审定后落地，跨年、闰年和月末申请均按同一规则。建议最迟财务处理日在月末休息时提前至当月最后一个工作日，审核与交票排期也应服从月末结算上限；不能因审核跨月、假日或补资料自动顺延至再次月。
6. **按身份闭合发票流程。** 团长大额申请保存发票要求，补交、退回、核验和付款相互衔接，适用申请不能从其他付款入口绕过已审定的材料要求。达人及独立达人完全跳过发票要求，不能因为大额统一进入待交票。提交时保存适用身份和规则，后续角色变化不静默改写原申请。操作留痕，团长能在原记录补充资料；缺票异常处理仍需业务审定，不擅自改变已确认的结算上限。
7. **旧客户端必须被妥善处理。** 新规则启用后，未支持费用展示与规则确认的旧客户端不能悄悄按旧页面扣新手续费；拟返回明确的更新提示并提供刷新 / 重新进入路径。新规则未生效时继续按当前有效规则处理，不能提前展示已经收费的文案。兼容读取和规则发布开关的方案须在上线前验证。
